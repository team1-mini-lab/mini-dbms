# 결정 기록 (0\~3단계)

0\~3단계 코드를 만들면서 **"이건 이렇게 하자"고 정한 것**을 한곳에 모은 문서입니다.

- 각 결정이 실제로 어떻게 동작하는지는 단계별 문서에 예시와 함께 있습니다: [STEP0](./STEP0.md) · [STEP1](./STEP1.md) · [STEP2](./STEP2.md) · [STEP3](./STEP3.md)
- 처음 왔다면 [인수인계 문서(HANDOFF)](./HANDOFF.md)를 먼저 읽으세요.
- 여기 있는 것은 모두 **아직 팀 합의 전(제안)**입니다. 회의에서 합의된 것만 [DESIGN.md](../DESIGN.md) 4절로 옮깁니다.

## 표 읽는 법

각 줄 맨 오른쪽 **출처**는 그 결정이 어디서 나왔는지입니다.

| 출처 | 뜻 |
| --- | --- |
| DESIGN 제안 | 팀 설계 문서 [DESIGN.md](../DESIGN.md)에 이미 제안으로 적혀 있던 것을 그대로 따름 |
| 새로 정함 | DESIGN에 없어서, 코드를 만들다가 필요해서 정함 |
| 교차 검토 | 다 만든 뒤 두 검토자(설계 쪽, 구현 쪽)가 코드를 돌려 보다가 문제를 찾아서, 고치면서 정함 |

**번호(D1, D2 …)**는 STEP 문서에서 "D12 참고"처럼 가리키려고 붙였습니다.

## 0단계: 준비

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| D1 | 파이썬에 기본으로 들어 있는 기능만 씀 (따로 설치할 것 없음) | 누구나 받자마자 실행할 수 있음. 파서·인덱스·서버를 직접 만들어야 발표 때 설명할 수 있음 | DESIGN 제안 |
| D2 | 테이블에 어떤 열이 있는지는 `data/schema.json` 파일에 직접 적어 둠. 타입은 숫자(`INT`)와 글자(`TEXT`) 두 가지 | 우리 과제는 `CREATE TABLE`(테이블 만들기 SQL)을 지원하지 않아서, 열 정보를 적어 둘 곳이 따로 필요함 | DESIGN 제안 |
| D3 | 모든 테이블의 첫 열은 `id` (숫자) | id가 자동 번호와 인덱스의 기준이 됨 | DESIGN 제안 |
| D4 | `schema.json`과 데이터 파일(`users.tbl`)을 `data/` 폴더 하나에 둠 | 엔진에 폴더 이름 하나만 알려 주면 됨: `Engine("data")` | 새로 정함 |
| D5 | 단계마다 확인용 SQL 파일을 `examples/` 폴더에 둠 | 누구나 같은 명령으로 "제대로 되는지" 확인할 수 있음 | 새로 정함 |

## 1단계: CLI (터미널에서 SQL 실행)

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| D6 | SQL을 읽는 부분(파서)은 지금은 **임시**. 예제에 나오는 두 가지 모양만 읽음 | 지금 목표는 "처음부터 끝까지 한 번 돌아가게"임. 제대로 된 파서는 4\~5단계에서 만듦 | DESIGN 제안 |
| D7 | 파서는 읽은 결과를 `Insert(...)`, `Select(...)`라는 **정해진 모양**으로 엔진에 넘김 | 모양만 같으면 4\~5단계에서 파서를 통째로 바꿔도 엔진은 안 고쳐도 됨 (접점 2) | DESIGN 제안 |
| D8 | SQL 파일에 문장이 여러 개면, 지금은 `;`가 나올 때마다 자름 | 가장 간단한 임시 방법. 단점이 있어서(STEP1 참고) 4단계에서 바꿈 | 새로 정함 (임시) |
| D9 | 문장 하나가 틀려도 멈추지 않음. 그 문장만 오류로 표시하고 다음 문장을 계속 실행 | 100줄 중 한 줄이 틀렸다고 나머지 99줄이 안 들어가면 안 됨 | DESIGN 제안 |
| D10 | 엔진이 켜질 때 데이터 파일을 한 번 읽어서, "지금 가장 큰 id + 1"을 다음 번호로 정함 | CLI는 실행할 때마다 새로 켜짐. 이걸 안 하면 두 번째 실행에서 id가 또 1부터 붙음 | DESIGN 제안 |
| D11 | 다음 번호는 테이블마다 따로 셈 | 테이블이 늘어도 번호가 섞이지 않게 | 새로 정함 |
| D12 | INSERT는 **① 검사 → ② 파일에 쓰기 → ③ 번호 올리기** 순서로 함 | 번호를 먼저 올리면, 검사에서 실패한 INSERT도 번호를 하나 써 버려서 1, 3처럼 건너뜀 | 교차 검토 |
| D13 | INSERT의 값을 `schema.json`의 열 순서대로 다시 놓음. 없는 열, 빠진 열, 같은 열 두 번, id를 직접 넣기는 오류 | 이걸 안 하면 `(age, name)` 순서로 쓸 때 나이와 이름이 뒤바뀌어 저장됨 | 교차 검토 |
| D14 | 파일에는 한 줄에 데이터 하나를 `[1, "현지", 25]` 모양으로 저장 (JSON 배열) | 값에 쉼표나 한글이 있어도 안전하고, 파일을 열어 눈으로 읽을 수 있음 | DESIGN 제안 |
| D15 | 한 줄을 쓸 때 "그 줄이 파일의 몇 바이트째에서 시작하는지"를 기억해서 돌려줌 | 2단계 인덱스가 이 숫자로 그 줄에 바로 감. 한글은 한 글자가 3바이트라서 글자 수가 아니라 바이트로 셈 | 새로 정함 |

## 2단계: 임시 인덱스

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| D16 | 인덱스는 일단 파이썬 `dict`로 만들고, 엔진은 `insert`(적기)와 `search`(찾기) 두 함수로만 씀 | 10\~12단계에서 B+ 트리로 바꿀 때, 같은 두 함수만 만들면 엔진은 안 고쳐도 됨 (접점 3) | DESIGN 제안 |
| D17 | 인덱스에서 못 찾으면 `None`(없음)을 돌려줌. SELECT 결과는 빈 목록 | 접점 3 제안과 같게 | DESIGN 제안 |
| D18 | `WHERE id = 숫자`일 때만 인덱스를 써서 그 한 줄만 읽음 | 과제가 "id로 찾을 때는 인덱스를 쓰라"고 함 | DESIGN 제안 |
| D19 | id가 아닌 열(`WHERE name = '민수'`)은 파일을 처음부터 읽으면서 조건에 맞는 줄만 남김 | 과제가 이 두 방법의 속도를 비교하라고 함. 처음에는 거르지 않고 전부 돌려주는 실수가 있어서 검토 때 고침 | DESIGN 제안 + 교차 검토 |
| D20 | WHERE에 쓴 열이 실제로 있는지, 값의 종류(숫자/글자)가 열과 맞는지 확인. 틀리면 오류 | 없는 열로 찾으면 전부 돌려주던 문제를 막음. `id = '2'`(글자)도 막아서, B+ 트리로 바꿔도 결과가 같게 함 | 교차 검토 |
| D21 | 아직 못 하는 SELECT(`SELECT name`, `WHERE id > 3`)는 오류로 막음 | 틀린 결과를 조용히 내는 것보다 "아직 안 됨"이라고 알려 주는 게 나음 | 교차 검토 |
| D22 | 엔진이 켜질 때 데이터 파일을 읽으면서 인덱스도 다시 만듦 | 인덱스는 메모리에만 있어서 끄면 사라짐. 파일을 기준으로 다시 만드니 항상 파일과 맞음 | DESIGN 제안 |
| D23 | SELECT 결과에 인덱스를 썼는지 표시: 썼으면 `used_index: True`, 처음부터 읽었으면 `False` | 눈으로 확인할 수 있고, 14단계 속도 비교에도 씀 | 새로 정함 |

## 3단계: API 서버

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| D24 | 서버는 파이썬 기본 기능 `http.server`로 만들고, 받는 주소는 `POST /query` 하나 | 설치할 게 없음. SQL 안에 "넣기인지 찾기인지"가 이미 들어 있어서 주소를 나눌 필요가 없음 | DESIGN 제안 |
| D25 | 서버 번호(포트)는 8000 | Mac은 5000번을 다른 기능(AirPlay)이 쓰는 경우가 있음. 지난 과제(mini-redis)와 같은 번호 | 새로 정함 |
| D26 | 서버가 켜질 때 엔진을 하나만 만들고, 모든 요청이 그 엔진을 같이 씀 | 요청마다 엔진을 새로 만들면 매번 파일을 다시 읽어야 하고, 다음 번호가 어긋날 수 있음 | 새로 정함 |
| D27 | 성공하면 엔진 결과를 `{"results": [...]}`로 감싸서 돌려줌 | 접점 4 제안과 같게 | DESIGN 제안 |
| D28 | 요청 자체가 잘못되면(JSON이 아님, `sql`이 없음) 400 오류와 `{"error": ...}`로 답함 | 이걸 안 하면 서버가 아무 답 없이 연결을 끊어 버림 | 교차 검토 |
| D29 | 데이터를 쓰는(INSERT) 건 CLI와 서버 중 **하나만**. 서버가 켜져 있으면 INSERT는 서버로만 보냄 | CLI와 서버는 따로 실행되어서 "다음 번호"를 각자 기억함. 둘이 같이 쓰면 id가 겹침 (STEP3 참고) | 교차 검토 |
