# 결정 기록 · 지도 만들기(0\~3단계), Phase 2(10\~14단계), Phase 3(15\~17단계)

지도 만들기(0\~3단계)·Phase 3(15\~17단계, 은기)와 Phase 2(10\~14단계 B+ 트리, 소망) 코드를 만들면서 **"이건 이렇게 하자"고 정한 것**을 한곳에 모은 문서입니다. Phase 2 결정은 소망 님의 [BPTREE.md](../somang/BPTREE.md) "결정 기록"에서 번호(S1\~S7)를 그대로 옮겨 왔습니다.

- 각 결정이 실제로 어떻게 동작하는지는 단계별 작업 기록에 예시와 함께 있습니다: [STEP0](./STEP0.md) · [STEP1](./STEP1.md) · [STEP2](./STEP2.md) · [STEP3](./STEP3.md) · [BPTREE](../somang/BPTREE.md) · [STEP16](./STEP16.md) · [STEP15](./STEP15.md) · [STEP17](./STEP17.md)
- 아래 각 절의 제목 옆 링크를 누르면 그 단계의 작업 기록으로, 작업 기록의 "이 단계에서 정한 것"에서 링크를 누르면 다시 이 문서의 해당 절로 옵니다.
- 처음 왔다면 [인수인계 문서(HANDOFF)](./HANDOFF.md)를 먼저 읽으세요.
- 여기 있는 것은 모두 **아직 팀 합의 전(제안)**입니다. 회의에서 합의된 것만 [DESIGN.md](../DESIGN.md) 4절로 옮깁니다.

> 🔄 **수정사항**: 처음 공유한 뒤 **D30**(서버의 틀린 SQL 응답: 200 → 첫 오류에서 멈추고 400)을 추가했습니다. Phase 3에서는 교차 검토로 **D32, D35, D37**을 고쳤습니다 (각 줄의 "변경:" 참고). 전체 수정 목록은 [HANDOFF 맨 위](./HANDOFF.md#-수정사항-처음-공유한-뒤-바뀐-것)에 있습니다.

> 📖 **처음 읽는다면**: 이 문서는 결정만 짧게 모은 목록이라, 낱말 설명 없이 결론만 적혀 있습니다. 표의 한 줄이 어렵게 느껴지면 그 단계의 STEP 문서(예: D34는 [STEP15](./STEP15.md#왜-직접-만들었나요-d34))를 먼저 읽고 오세요. 모르는 말은 [용어 사전](./GLOSSARY.md)에 있습니다. 표에 자주 나오는 말은 이렇습니다.
>
> | 말 | 뜻 |
> | --- | --- |
> | lock | 한 번에 한 스레드만 들어갈 수 있게 잠그는 도구 (16단계) |

## 표 읽는 법

각 줄 맨 오른쪽 **출처**는 그 결정이 어디서 나왔는지입니다.

| 출처 | 뜻 |
| --- | --- |
| DESIGN 제안 | 팀 설계 문서 [DESIGN.md](../DESIGN.md)에 이미 제안으로 적혀 있던 것을 그대로 따름 |
| 새로 정함 | DESIGN에 없어서, 코드를 만들다가 필요해서 정함 |
| 교차 검토 | 다 만든 뒤 두 검토자(설계 쪽, 구현 쪽)가 코드를 돌려 보다가 문제를 찾아서, 고치면서 정함 |
| 수정 | 처음 공유한 뒤에 바꾼 것. 이유 끝에 "(변경: 전에는 ...)"을 적어 둠 |

**번호(D1, D2 …)**는 STEP 문서에서 "D12 참고"처럼 가리키려고 붙였습니다.

## Phase 2(10\~14단계): B+ 트리 인덱스 · 담당 소망 · [작업 기록 BPTREE →](../somang/BPTREE.md)

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| S1 | 값에는 데이터 전체가 아니라 **파일 위치(바이트)**를 담음 | 100만 줄을 메모리에 다시 두지 않음. 파일이 원본이고 트리는 목차 | DESIGN 제안 (11단계) |
| S2 | 노드의 키가 `max_keys`개를 **넘으면** 나눔. 기본 `max_keys=256`, `BPlusTree(max_keys=3)`처럼 바꿔 실험 | 100만 건, `max_keys` 8\~8192 측정에서 128\~512 구간이 가장 빨라서 256 (변경: 처음에는 32였음. 테스트용 작은 값과 측정용 값은 상수로 빼서 정하기로 함, 11/17 회의) | 새로 정함 · 측정으로 수정 |
| S3 | 리프를 나눌 때 `mid = 키 수 // 2`. 오른쪽 리프의 **첫 키를 부모로 복사** (리프에도 남음) | 모든 키와 값이 리프에 있어야 리프만 옆으로 훑어 범위 조회가 됨. 예: 10,20,30,40 → [10,20] [30,40], 30이 올라감 | 새로 정함 |
| S4 | 내부 노드를 나눌 때 **가운데 키를 부모로 옮김** (양쪽에 안 남음) | 내부 노드는 길 안내만 하므로 같은 표지판이 두 번 있을 필요 없음 | 새로 정함 |
| S5 | 내려갈 때 표지판 키와 **같으면 오른쪽**으로 (`bisect_right`) | S3에서 올린 키는 오른쪽 리프의 첫 키이므로 | 새로 정함 |
| S6 | 노드마다 `parent`를 둠 | 나눈 뒤 키를 올려 보낼 곳을 바로 앎 | 새로 정함 |
| S7 | 노드 안에서 위치 찾기는 표준 라이브러리 `bisect`(이진 탐색) | 노드 안 키는 정렬되어 있음 | 새로 정함 |

- 엔진에는 `engine.py` 두 줄(`DictIndex` → `BPlusTree`)만 바꿔 붙였습니다(12단계). 접점 3(`insert`, `search`)은 그대로이고, `range_search`는 만들어 두었지만 엔진이 아직 부르지 않습니다(`WHERE id > ?`는 D21로 막혀 있음, 20단계 후보).
- 엔진 전체 lock(D31) 덕분에 B+ 트리는 동시성을 신경 쓰지 않아도 됩니다.
- 성능 비교(14단계), 알아 둔 한계, 확인 방법은 [BPTREE.md](../somang/BPTREE.md)에 있습니다.

---

> Phase 3는 **코드보다 결정을 먼저** 적습니다. 그리고 표의 칸을 **무엇이 왜 문제였나 → 무엇을 바꾸나 → 왜 이 방식인가(비교한 것과 대가)** 순서로 나눴습니다. 처음 보는 사람은 맨 앞 칸만 따라 읽어도 흐름을 잡을 수 있습니다.
>
> 번호가 단계 순서와 다른 이유: Phase 3는 16 → 15 → 17단계 순서로 만들었고, D38·D39는 17단계용으로 미리 잡아 둔 번호입니다. 번호는 한번 붙이면 바꾸지 않습니다 (STEP 문서가 번호로 가리키기 때문).

| D31 | 15단계에서 서버가 요청을 여러 스레드로 동시에 처리하면, INSERT 두 개가 같은 "다음 번호"를 읽어 같은 id가 두 번 붙음. lock 없이 스레드 100개로 넣어 보니 서로 다른 id가 16개뿐 | 엔진 안에 lock **하나**를 두고 `execute` 전체를 감쌈. ## Phase 3(15단계): Thread Pool · [작업 기록 STEP15 →](./STEP15.md)

| 번호 | 무엇이 왜 문제였나 | 무엇을 바꾸나 | 왜 이 방식인가 | 출처 |

| D34 | 3단계 서버(`HTTPServer`)는 요청을 끝까지 처리해야 다음 연결을 받음. 한 번에 1개만 처리되고, 한 명이 느리면 뒤에 온 사람이 모두 기다림. 과제는 "Thread Pool로 병렬 처리" | 요청을 줄 세우는 `queue.Queue(maxsize=16)`와 서버를 켤 때 미리 만든 스레드 N개로 **직접** 만듦. 받는 스레드는 연결을 줄에 넣기만 하고, 일하는 스레드가 꺼내 처리. 줄이 꽉 차면 바로 503 | 비교한 것: ① `ThreadingHTTPServer`: 요청마다 스레드를 새로 만들어 수가 정해지지 않음. | D35 | 스레드와 줄의 수를 정해야 함. 너무 적으면 느린 손님에게 스레드가 다 붙잡히고, 너무 많으면 자원을 씀 | 기본 스레드 4개, 줄 16칸. `--workers`, `--queue`로 바꿀 수 있음 | **측정으로 찾은 최적값은 아님.** `bench/load_test.py`로 재 보니 스레드 수가 동시에 오는 느린 연결 수보다 많으면 빠른 손님이 안 막히고(느린 3명·스레드 4개 → 0.7ms), 같으면 막힘(느린 4명·스레드 4개 → 664ms, 8개면 0.5ms). 빠른 손님만 있을 때는 스레드를 늘려도 빨라지지 않음(1·4·16개 = 44·70·68ms). 그래서 "동시에 느린 연결 3개까지 견디는" 4개로 둠. 줄 16칸은 숫자가 정해 준 값이 아니라 판단(짧으면 503이 많고, 길면 오래 기다림) (변경: 전에는 다른 방식의 부하 테스트 숫자를 근거로 적었으나, 교차 검토에서 그 방식이 실제 서버를 재지 못한다고 확인해서 바꿈) | 새로 정함 · 교차 검토로 수정 |
| D36 | mini-redis 데모 서버와 같은 컴퓨터에서 띄우면 둘 다 8000번이라 겹침 | `--port`로 바꿀 수 있음. 기본 8000. 주식 데모에 붙일 때는 8002 | 기본값은 3단계(D25) 그대로 두고, 필요할 때만 바꾸게 | 새로 정함 |
| D37 | 일하는 스레드는 요청을 다 받아야 처리할 수 있음. 연결만 열어 두거나 아주 천천히 보내는 손님이 스레드 수(4)만큼 오면, 모든 스레드가 받기만 기다리다 서버 전체가 멈춤 | 15단계: 한 번 받을 때 5초까지 기다림(`Handler.timeout`). 17단계(엣지 방어): 요청을 받기 시작해서 본문을 다 받을 때까지 **전체에 5초**. 넘으면 408. 요청을 다 받은 뒤 lock 기다림·실행 시간은 세지 않음 | 비교한 것: ① 소켓 timeout(한 번 받을 때마다 5초): 조금씩이라도 계속 보내면 못 막음. ② 요청마다 타이머 스레드: 스레드가 요청 수만큼 늘어 Pool의 뜻과 어긋남. ③ 서버 전체에 감시 스레드 하나 → ③. 대가: 코드가 늘어서 `server_guard.py`로 따로 둠 (D48) (변경: 전에는 ①만 있었음) | 새로 정함 · 17단계에서 더함 |

| D41 | 3단계에서는 엔진을 `server.py` 맨 위에서 만들어서, `import server`만 해도 `data/`의 엔진이 만들어짐. 확인 스크립트가 임시 폴더로 서버를 따로 띄울 수 없음 | 엔진은 `main()`에서 만들어 서버에 넘기고, `Handler`는 `self.server.engine`으로 씀 | 서버를 만들 때 엔진을 넘기면 어느 폴더든 쓸 수 있음. 모든 스레드가 같은 엔진 하나를 쓰므로 엔진 안의 lock(D31)이 서버 전체에 적용됨 | 새로 정함 |
