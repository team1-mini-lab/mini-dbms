# 결정 기록 · 지도 만들기(0\~3단계)와 Phase 3(15\~17단계)

은기가 맡은 지도 만들기(0\~3단계)와 Phase 3(15\~17단계) 코드를 만들면서 **"이건 이렇게 하자"고 정한 것**을 한곳에 모은 문서입니다.

- 각 결정이 실제로 어떻게 동작하는지는 단계별 작업 기록에 예시와 함께 있습니다: [STEP0](./STEP0.md) · [STEP1](./STEP1.md) · [STEP2](./STEP2.md) · [STEP3](./STEP3.md) · [STEP16](./STEP16.md) · [STEP15](./STEP15.md) · STEP17(작성 예정)
- 아래 각 절의 제목 옆 링크를 누르면 그 단계의 작업 기록으로, 작업 기록의 "이 단계에서 정한 것"에서 링크를 누르면 다시 이 문서의 해당 절로 옵니다.
- 처음 왔다면 [인수인계 문서(HANDOFF)](./HANDOFF.md)를 먼저 읽으세요.
- 여기 있는 것은 모두 **아직 팀 합의 전(제안)**입니다. 회의에서 합의된 것만 [DESIGN.md](../DESIGN.md) 4절로 옮깁니다.

> 🔄 **수정사항**: 처음 공유한 뒤 **D30**(서버의 틀린 SQL 응답: 200 → 첫 오류에서 멈추고 400)을 추가했습니다. 전체 수정 목록은 [HANDOFF 맨 위](./HANDOFF.md#-수정사항-처음-공유한-뒤-바뀐-것)에 있습니다.

## 표 읽는 법

각 줄 맨 오른쪽 **출처**는 그 결정이 어디서 나왔는지입니다.

| 출처 | 뜻 |
| --- | --- |
| DESIGN 제안 | 팀 설계 문서 [DESIGN.md](../DESIGN.md)에 이미 제안으로 적혀 있던 것을 그대로 따름 |
| 새로 정함 | DESIGN에 없어서, 코드를 만들다가 필요해서 정함 |
| 교차 검토 | 다 만든 뒤 두 검토자(설계 쪽, 구현 쪽)가 코드를 돌려 보다가 문제를 찾아서, 고치면서 정함 |
| 수정 | 처음 공유한 뒤에 바꾼 것. 이유 끝에 "(변경: 전에는 ...)"을 적어 둠 |

**번호(D1, D2 …)**는 STEP 문서에서 "D12 참고"처럼 가리키려고 붙였습니다.

| D11 | 다음 번호는 테이블마다 따로 셈 | 테이블이 늘어도 번호가 섞이지 않게 | 새로 정함 |

## Phase 3(16단계): lock · [작업 기록 STEP16 →](./STEP16.md)

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| D31 | lock은 **엔진 안에 하나**, `execute` 전체를 감쌈. INSERT뿐 아니라 SELECT도 잠금 | CLI든 서버든 `execute`를 거치므로 lock을 빠뜨릴 수 없음. SELECT를 안 잠그면 INSERT가 반쯤 쓴 줄을 읽거나, B+ 트리가 노드를 나누는 도중에 찾을 수 있음. 그래서 Phase 2의 B+ 트리는 동시성을 신경 쓰지 않아도 됨 | DESIGN 제안 (결정 16) |
| D32 | lock은 `execute` 위에 `@locked` 한 줄로 검. `execute` 안의 코드는 들여쓰지 않음 | `with self._lock:`으로 안을 감싸면 안쪽 전체가 한 칸 들여쓰기돼서, 같은 곳을 고치는 Phase 1(4\~5단계)과 합칠 때 충돌함 | 새로 정함 |
| D33 | "lock이 없으면 id가 겹친다"는 시연은 확인 스크립트 안에서만 끼어들 틈을 넓혀서 보여 줌. 실제 코드에는 쉬는 부분을 넣지 않음 | INSERT가 너무 빨라서 lock 없이도 우연히 안 겹칠 때가 많음. 시연용 코드가 실제 코드에 섞이지 않게 함 | 새로 정함 |

## Phase 3(15단계): Thread Pool · [작업 기록 STEP15 →](./STEP15.md)

| 번호 | 정한 것 | 이유 | 출처 |
| --- | --- | --- | --- |
| D34 | Thread Pool은 `queue.Queue` + 미리 만든 스레드 N개로 **직접** 만듦. 큐가 가득 차면 503 | 파이썬 `ThreadingHTTPServer`는 요청마다 스레드를 새로 만들어 Pool이 아님. `ThreadPoolExecutor`는 원리가 안 보여 발표에서 설명하기 어려움 | DESIGN 제안 (결정 15) |
| D35 | 기본 스레드 4개, 큐 16칸. 실행할 때 `--workers`, `--queue`로 바꿀 수 있음 | 스레드 1→4개로 전체 처리 시간이 3292ms→850ms(3.9배)로 줄고, 큐 1·4칸은 70% 안팎 즉시 503, 큐 64칸은 최대 대기가 550ms까지 늘어 기본 `16칸`(최대 163ms)으로 대기 폭증과 503 사이의 균형을 맞춤 (`bench/load_test.py`) (변경: 전에는 "503 시연 때 큐를 작게 줄여야 함"만 적었으나, 부하 테스트 수치로 근거 보완) | 보완 (17단계 부하 테스트) |
| D36 | 서버 포트를 `--port`로 바꿀 수 있음. 기본 8000 | mini-redis와 같은 곳에서 띄울 때 둘 다 8000이라 충돌함 | 새로 정함 |
| D37 | 요청 하나당 **받는 시간 전체** 5초 timeout (`408 timeout`) | 연결만 하거나 0.35초마다 1바이트씩 천천히 보내는 공격을 막기 위해 감시 스레드가 읽기 시작부터 5초를 재고 `SHUT_RD`로 깨워 `408`을 돌려줌 (변경: 전에는 소켓 `recv` 한 번당 5초만 걸어 느린 전송 공격을 막지 못했음) | 수정 (17단계) |
| D40 | 처리한 스레드 이름을 로그 앞(`[worker-2] ...`)과 응답 머리(`X-Worker: worker-2`)에 남김 | DESIGN 15단계 완료 기준이 "여러 스레드 이름으로 처리된 로그". 응답 머리에도 있으면 확인 스크립트가 셀 수 있음 | 새로 정함 |
| D41 | 엔진은 `server.py`의 `main()`에서 만들어 서버에 넘기고, `Handler`는 `self.server.engine`으로 씀 (전에는 파일 맨 위 `engine = Engine("data")`) | `import server`만 해도 `data/`의 엔진이 만들어지던 것을 막고, 확인 스크립트가 임시 폴더로 서버를 따로 띄울 수 있게 | 새로 정함 |

| D42 | 요청 본문 최대 크기를 1MB(`MAX_BODY`)로 제한하고, 초과하면 읽지 않고 `413 too_large` | 거대한 `Content-Length` 하나로 메모리가 바닥나는 것을 막음 | 새로 정함 |

| D44 | `server_close()`가 감시 중인 소켓을 `SHUT_RD`로 깨우고 큐를 비운 뒤 종료 신호를 보냄 | 큐가 꽉 찬 상태에서도 워커 스레드가 읽기에서 풀려나 1초 안에 안전하게 꺼짐 | 새로 정함 |
| D45 | `--workers`·`--queue`는 1 이상, `--port`는 `1~65535`만 허용. 포트 충돌 시 친절한 메시지 후 종료 | `0`이나 음수로 `Queue(0)`(무한 큐)이 되거나 스택 트레이스가 쏟아지는 실수를 실행 전에 막음 | 새로 정함 |
