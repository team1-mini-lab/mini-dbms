# 실제 DBMS와 다른 점

[← README로 돌아가기](../README.md)

| 항목 | 실제 DBMS (MySQL, PostgreSQL) | mini-dbms | 이유 |
| --- | --- | --- | --- |
| SQL 처리 | 실행 계획을 여러 개 비교해 가장 빠른 것 선택 | id 조건이면 B+ 트리, 아니면 전체 스캔 | 테이블 하나를 조회하는 문장이라 규칙 하나로 충분함 |
| 저장 방식 | 8~16KB 페이지 단위, 자주 쓰는 페이지는 메모리에 | 한 줄에 한 행, 파일 끝에 붙이기만 | 파일을 눈으로 바로 확인할 수 있음 |
| 인덱스 | 디스크에 저장, 여러 열에 만들 수 있음 | 메모리에만, `id` 하나 | 켤 때 파일로 다시 만들면 파일과 항상 일치함 |
| 동시성 | 행 단위 잠금 + 옛 버전 읽기(MVCC) | 엔진 입구의 읽기·쓰기 lock 하나 | 기존 행을 고치지 않아 다투는 곳이 테이블에 하나씩뿐 |
| 트랜잭션·복구 | 여러 문장을 묶어 모두 되거나 모두 안 되게, 로그로 복구 | 없음, 잘린 마지막 줄만 정리 | 파서·인덱스·서버에 집중 |
| 연결 처리 | 자체 통신 방식 | HTTP + JSON + 직접 만든 Thread Pool | `curl`·브라우저로 바로 시험, 과부하 방어를 직접 제어 |
| 오류 | 표준 오류 코드(SQLSTATE) | 정해 둔 JSON 코드 (`bad_sql`, `busy` 등) | 코드 하나로 원인을 나누고, 내부 경로를 밖에 보이지 않음 |

## SQL 처리

실제 DBMS는 SQL을 구문 트리로 만든 뒤, 같은 결과를 내는 실행 방법을 여러 개 떠올리고 비용을 따져 가장 빠른 것을 고릅니다(옵티마이저). 인덱스가 여러 개 있거나 테이블을 여러 개 합칠 때, 어느 순서로 무엇을 쓸지에 따라 속도가 수백 배 차이 나기 때문입니다.

mini-dbms는 규칙 하나로 고릅니다. 조건이 `id`에 대한 `=`나 범위면 B+ 트리를 쓰고, 그 밖에는 전체 스캔합니다. 테이블 하나를 조회하는 문장만 다루고 인덱스도 `id` 하나뿐이라, 비교할 후보가 사실상 둘뿐이기 때문입니다. 대신 `id > 0`처럼 거의 모든 행이 해당하는 범위도 B+ 트리로 가서, 줄마다 위치로 읽느라 전체 스캔보다 느릴 수 있습니다.

## 저장 방식

실제 DBMS는 파일을 8~16KB 크기의 페이지로 나눠, 페이지 안에 여러 행을 담습니다. 자주 쓰는 페이지는 메모리(버퍼 풀)에 올려 두고, 행을 고치거나 지우면 그 페이지 안에서 자리를 바꿉니다.

mini-dbms는 한 줄에 한 행을 탭으로 나눠 적고, 새 행은 파일 끝에 붙이기만 합니다. 파일을 텍스트 편집기로 열어 바로 확인할 수 있고, 값에 쉼표나 한글이 들어가도 깨지지 않습니다. 기존 줄을 고치지 않으므로 줄의 시작 위치(몇 번째 바이트)가 바뀌지 않고, B+ 트리는 그 위치만 기억하면 됩니다. 대신 `UPDATE`·`DELETE`를 넣으려면 기존 줄을 고치거나 지운 표시를 남기는 방법을 새로 정해야 합니다.

## 인덱스

실제 DBMS는 B+ 트리를 디스크 페이지에 저장해서, 껐다 켜도 다시 만들지 않습니다. 원하는 열마다 인덱스를 만들 수 있고, 같은 값이 여러 행에 있어도 됩니다.

mini-dbms의 B+ 트리는 메모리에만 있고, `id` → 파일 위치만 담습니다. 켤 때 데이터 파일을 처음부터 읽어 다시 만들기 때문에(100만 건에 약 1.9초), 비정상 종료 뒤에도 트리와 파일이 어긋날 일이 없습니다. 트리는 사라져도 원본인 파일에서 다시 만들 수 있는 사본이라는 점에서, 원본 DB가 따로 있는 캐시와 같은 관계입니다. 다른 열에는 인덱스가 없어서 `name`으로 찾으면 전체 스캔입니다.

## 동시성

실제 DBMS는 여러 요청이 같은 테이블을 동시에 고칠 수 있게, 고치는 행만 잠급니다(행 단위 잠금). 읽는 요청은 잠긴 행을 기다리지 않고 고치기 전 옛 버전을 읽습니다(MVCC). 대신 두 요청이 서로의 행을 기다리는 교착 상태(deadlock)를 찾아 풀어야 합니다.

mini-dbms는 엔진 입구에 읽기·쓰기 lock 하나를 둡니다. 파일을 읽기만 하는 SELECT끼리는 같이 들어가고, 파일에 쓰는 INSERT는 혼자 들어갑니다. 기존 행을 고치지 않으므로 INSERT끼리 다투는 곳은 행이 아니라 테이블에 하나뿐인 다음 id·파일 끝·B+ 트리이고, 행을 잠가도 INSERT는 어차피 한 번에 하나입니다. lock이 하나라 교착 상태도 생기지 않습니다. 대신 긴 SELECT가 도는 동안 INSERT는 기다리고, 파이썬은 GIL(파이썬 안에 들어 있는 lock 하나) 때문에 한순간에 한 스레드만 코드를 돌려서 SELECT를 같이 실행해도 총 처리 속도는 늘지 않습니다. 얻는 것은 짧은 SELECT가 긴 SELECT 뒤에서 기다리지 않는 것입니다(`python3 checks/check_rw.py`).

## 트랜잭션·복구

실제 DBMS는 여러 문장을 트랜잭션으로 묶어, 중간에 하나라도 실패하면 앞에서 한 것까지 되돌립니다. 바꾸기 전에 무엇을 바꿀지 로그(WAL)에 먼저 적어 두어서, 전원이 나가도 켤 때 로그를 보고 반쯤 된 작업을 정리합니다.

mini-dbms는 문장마다 바로 파일에 씁니다. 문법이 틀린 문장이 섞이면 파싱 단계에서 걸러 하나도 실행하지 않지만, 실행 도중 두 번째 문장이 실패하면 첫 번째 INSERT는 이미 저장되어 있고 되돌리지 않습니다. 그래서 응답에 앞 문장까지의 결과를 함께 돌려줘, 클라이언트가 이미 들어간 행을 다시 넣지 않게 합니다. 쓰다 꺼진 경우는 켤 때 파일 끝에 잘린 줄이 있으면 잘라 내는 것까지만 합니다.

## 연결 처리

실제 DBMS는 자체 통신 방식(프로토콜)과 전용 드라이버로 연결을 받고, 연결마다 프로세스(PostgreSQL)나 스레드(MySQL)를 둡니다.

mini-dbms는 HTTP로 SQL을 받고 JSON으로 답합니다. 드라이버 없이 `curl`이나 브라우저로 바로 시험할 수 있습니다. 연결은 직접 만든 Thread Pool(스레드 4개, 대기열 16칸)이 받고, 대기열이 꽉 차면 기다리게 하지 않고 바로 503으로 돌려보내며, 5초 안에 요청을 다 보내지 않는 연결은 408로 끊습니다.


### 왜 이벤트 루프가 아닌가

| | 느린 연결 (요청을 천천히 보내는 손님) | 실행이 긴 SQL (100만 줄 전체 스캔) |
|---|---|---|
| 이벤트 루프 (스레드 하나) | 강함. 요청이 아직 다 오지 않은 손님은 건너뛰고, 다 온 손님부터 처리 | 약함. 실행하는 1초 동안 아무도 못 받음 |
| 스레드 풀 (mini-dbms, 스레드 4개) | 약함. 느린 손님이 스레드 하나를 붙잡음 → 스레드 4개로 버티고, 5초가 지나면 감시 스레드가 408로 끊음 | 강함. 한 스레드가 1초짜리 SQL을 실행하는 동안 나머지가 다른 손님을 받음 |

실제 Redis는 스레드 하나(이벤트 루프)로 모든 연결을 번갈아 처리합니다. 운영체제가 "요청이 다 도착한 연결"을 알려 주면 그것만 처리하고, 덜 온 연결은 기다리지 않습니다. Redis는 명령이 모두 짧아 이 방식이 맞고 lock도 필요 없지만, mini-dbms는 실행에만 1초가 넘는 SQL이 있어 스레드 풀을 골랐습니다.

## 오류

실제 DBMS는 표준 오류 코드(SQLSTATE)로 원인을 알려 줍니다. 예를 들어 `42601`은 문법 오류입니다.

mini-dbms는 `bad_sql`, `busy`처럼 뜻이 보이는 코드를 정해 JSON으로 답합니다. 요청이 틀린 경우(4xx)와 서버 문제(5xx)를 나누고, 서버 내부 경로나 예외 내용은 밖으로 내보내지 않습니다. 어느 단계에서 어떤 코드로 답하는지는 README의 [요청이 틀리면 어디서 무엇이라고 답하나요?](../README.md#요청이-틀리면-어디서-무엇이라고-답하나요)에 있습니다.
