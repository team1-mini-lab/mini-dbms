# 6단계: 엣지 케이스

## 목표

Phase 1 전체를 끝에서 끝까지 두드려, 사용자 입력이나 데이터 상태 때문에 처리기가 트레이스백을 내며 죽는 경우를 없앤다.

이 단계가 끝나면 어떤 SQL 파일과 어떤 데이터 폴더를 주더라도 CLI는 알아볼 수 있는 한 줄 메시지와 정해진 종료 코드(0, 1, 2)로 끝난다. 새 기능은 없다. 대신 Phase 2로 넘어가기 전에 "Phase 1은 믿을 수 있다"는 근거가 테스트로 남는다.

## 이 단계의 위치

0단계 문서의 여섯 순서 전체다. 특정 층을 새로 만들지 않고, 1번(CLI 입력)부터 6번(CLI 출력)까지 이어진 흐름에 이상한 입력을 넣어 본다.

## 1. 왜 따로 단계를 두는가

1~5단계는 층마다 단위 테스트를 썼다. 단위 테스트는 "그 층이 약속한 일을 하는가"를 본다. 그런데 문제는 주로 **층과 층 사이, 그리고 층과 바깥 세계 사이**에서 생긴다.

0단계에서 세운 원칙은 "사용자 입력 때문에 생긴 오류는 모두 `MiniDBError`이고, 그 외 예외가 새어 나오면 우리 코드의 버그"였다. 이 원칙이 지켜지는지는 단위 테스트로는 잘 안 보인다. 예를 들어 저장소 테스트는 저장소가 쓴 파일을 읽으므로, 저장소가 쓰지 않은 바이트(외부 편집, 다른 인코딩)를 만날 일이 없다.

그래서 이 단계는 "바깥에서 들어올 수 있는 이상한 것"을 목록으로 만들고, 각각을 CLI 끝까지 통과시켜 본다.

## 2. 실제로 찾은 버그

직접 실행해 본 결과, 다음 네 경우가 원칙을 어겼다.

| 입력 | 고치기 전 | 원인 |
| --- | --- | --- |
| UTF-16 등 UTF-8이 아닌 SQL 파일 | `UnicodeDecodeError` 트레이스백 | CLI가 `OSError`만 잡았다. 디코딩 오류는 `ValueError` 계열이다 |
| BOM(`EF BB BF`)이 붙은 SQL 파일 | `1:1: 허용되지 않는 문자 '﻿'` | 윈도우 메모장 등이 붙이는 BOM을 토크나이저가 문자로 봤다. 죽지는 않지만 사용자는 원인을 알 수 없다 |
| 테이블 파일에 UTF-8이 아닌 바이트 | `UnicodeDecodeError` 트레이스백 | `decode_row`가 `bytes.decode` 오류를 `StorageError`로 바꾸지 않았다 |
| `--data-dir` 자리에 일반 파일 | `FileExistsError` 트레이스백 | `TableFile._open`의 `mkdir`과 `touch`가 `try` 바깥에 있었다 |

### 고친 방법

- **SQL 파일 읽기**: `utf-8-sig`로 읽는다. BOM이 있으면 떼고, 없으면 일반 UTF-8과 같다. 디코딩 오류는 `오류: UTF-8 로 읽을 수 없는 파일입니다`와 종료 코드 1로 바꾼다. 입력 파일을 고치면 되는 문제이기 때문이다.
- **테이블 파일 디코딩**: `decode_row`에서 `UnicodeDecodeError`를 잡아 `StorageError("손상된 행: UTF-8 이 아닙니다")`로 바꾼다. 실행 오류이므로 종료 코드 2다.
- **테이블 파일 열기**: 디렉터리 생성부터 파일 열기까지를 하나의 `try`로 묶어 모든 `OSError`를 `StorageError`로 바꾼다.

세 경우 모두 해결 방식이 같다. **바깥 세계와 닿는 지점에서, 바깥 세계의 예외를 우리 예외로 번역한다.** 번역 지점이 CLI(파일 읽기)와 저장소(테이블 파일) 두 곳뿐인 것은 층을 나눈 덕분이다. 파서와 실행기는 바깥 세계를 직접 만지지 않는다.

## 3. 확인만 하고 고칠 것이 없던 경우

다음은 이미 올바르게 동작했지만, 끝에서 끝까지의 테스트가 없었다. 테스트를 추가해 앞으로 깨지지 않게 한다.

| 경우 | 기대 동작 |
| --- | --- |
| 2만 행 INSERT 후 SELECT | 모든 행이 들어가고, id가 1부터 연속이며, 조건 검색과 전체 조회가 맞다 |
| 테이블 파일 중간에 손상된 행 | 종료 코드 2, 메시지에 테이블 이름과 "손상된 행" |
| 테이블 파일이 아직 없음 | SELECT는 헤더와 `(0 rows)`, 빈 파일이 생긴다 |
| 쓰다 만 마지막 행이 있는 상태에서 INSERT | 반쪽 행은 사라지고, 새 행은 온전하며, id는 온전한 행 기준으로 이어진다 |
| 아주 긴 문자열(10만 자)과 빈 문자열 | 그대로 저장되고 그대로 읽힌다 |
| 탭, 줄바꿈, 백슬래시, 따옴표, 한글이 섞인 값 | SQL에서 파일을 거쳐 SELECT까지 원래 값 그대로 |
| 정수 경계(아주 큰 수, 음수) | 그대로 저장되고 비교된다. Python 정수는 크기 제한이 없다 |

## 4. 고치지 않고 한계로 남기는 것

### 두 프로세스가 같은 데이터 폴더를 동시에 쓰는 경우

CLI 두 개를 동시에 실행하면 둘 다 시작할 때 최대 id를 세므로 **같은 id를 부여**한다. 파일 쓰기도 서로를 모른다. Phase 1은 이것을 막지 않는다.

막으려면 파일 잠금 같은 프로세스 간 조정이 필요하다. 그런데 이것이 바로 Phase 3이 푸는 문제다. 개요 문서의 설명대로, DBMS는 엔진을 가진 프로세스를 **하나만** 띄우고 클라이언트는 그 서버에 요청하는 방식으로 이 문제를 없앤다. 그래서 Phase 1에서는 고치지 않고 README에 "한 번에 한 프로세스만 실행한다고 가정"으로 적는다. Phase 3의 출발점이 된다.

### 표 출력의 폭

한글처럼 화면에서 두 칸을 차지하는 글자, 값 안의 줄바꿈은 표 정렬을 깨뜨린다. 저장과 조회는 올바르므로 표시 문제로 두고 README에 적는다(5단계에서 이미 기록).

## 5. 오류 경계 테스트

이 단계의 핵심 테스트는 "어떤 경우에도 `MiniDBError`가 아닌 예외가 CLI 밖으로 나오지 않는다"는 것이다. 실제 서브프로세스로 CLI를 실행하고, 표준 에러에 `Traceback`이 없으며 종료 코드가 1 또는 2인지 확인한다. 2절의 네 버그가 모두 이 형태의 테스트로 재현된다.

## 산출물

```
minidb/
├── cli.py         # utf-8-sig, 디코딩 오류 처리
└── storage.py     # decode_row 의 UnicodeDecodeError, _open 의 OSError
tests/
└── test_edge_cases.py
README.md          # 단일 프로세스 가정 추가
```

## 완료 기준

```sh
pytest tests/test_edge_cases.py
```

- 2절의 네 경우가 트레이스백 없이 정해진 메시지와 종료 코드로 끝난다.
- 3절의 경우들이 끝에서 끝까지 통과한다.
- 전체 테스트가 여전히 통과한다.
