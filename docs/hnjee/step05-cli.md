# 5단계: CLI

## 목표

SQL 파일을 명령줄에서 받아 실행하고, 결과를 화면에 찍는다.

이 단계가 끝나면 0단계 문서 맨 앞의 예시가 실제로 동작한다.

```sh
$ python -m minidb examples/students.sql
1 row inserted (id=1)
1 row inserted (id=2)
id | name | grade
---+------+------
1  | Kim  | 3
```

Phase 1의 요구사항("텍스트 파일로 작성된 SQL 문을 Command Line 명령을 통해 전달")이 여기서 충족된다. 남는 것은 6단계의 엣지 케이스 보강이다.

## 이 단계의 위치

0단계 문서의 여섯 순서 중 **1번과 6번**, 즉 양 끝이다.

| 순서 | 하는 일 |
| --- | --- |
| **1** | **CLI가 파일에서 문장을 꺼낸다 (5단계)** |
| 2 | 토크나이저가 문자열을 토큰으로 자른다 (1단계) |
| 3 | 파서가 토큰 열을 구조화된 객체로 만든다 (2단계) |
| 4 | 실행기가 무엇을 할지 정하고 저장소에 시킨다 (4단계) |
| 5 | 저장소가 파일을 읽고 쓴다 (3단계) |
| **6** | **CLI가 결과를 화면에 찍는다 (5단계)** |

CLI는 바깥 세계(파일, 터미널, 종료 코드)와 엔진(파서, 실행기) 사이의 번역기다.

## 1. 왜 CLI는 얇아야 하는가

CLI에 넣고 싶은 유혹이 드는 것들이 있다. 결과 정렬, 행 수 제한, 컬럼 이름 검사 같은 것들이다. 전부 넣지 않는다.

이유는 Phase 3이다. 13단계 서버는 CLI와 똑같이 "SQL을 받아 실행기에 넘기고 결과를 돌려주는" 일을 하는데, 입구가 파일이 아니라 네트워크고 출력이 표가 아니라 JSON일 뿐이다. CLI에 로직을 넣으면 서버에 같은 로직을 복제해야 한다. 그래서 CLI가 하는 일은 다음 넷으로 제한한다.

1. 인자를 해석하고 파일을 읽는다.
2. 파서와 실행기를 부른다.
3. `QueryResult`를 글자로 바꾼다.
4. 예외를 메시지와 종료 코드로 바꾼다.

이 중 2번은 한 줄짜리 호출이다. 나머지는 전부 "형식 변환"이다.

## 2. 호출 형태

```
python -m minidb <sql파일> [--data-dir DIR] [--schema FILE]
```

| 인자 | 기본값 | 뜻 |
| --- | --- | --- |
| `sql파일` | 필수 | 실행할 SQL 문장들이 든 텍스트 파일 |
| `--data-dir` | `data` | 테이블 파일(`*.tbl`)이 있는 디렉터리 |
| `--schema` | `<data-dir>/schema.json` | 카탈로그 파일 |

### 결정 1: 데이터 디렉터리를 바꿀 수 있게 한다

기본값 `data/`만으로 과제 요구는 충족된다. 그래도 옵션을 두는 이유는 테스트와 10단계 벤치마크다. 테스트는 임시 디렉터리에 써야 하고, 벤치마크는 100만 건짜리 파일을 저장소 안에 두고 싶지 않다. 옵션 하나로 둘이 해결된다.

## 3. 처리 흐름

```
파일 읽기
  → parse(전체)             문법 오류가 하나라도 있으면 여기서 끝 (종료 코드 1)
  → 카탈로그 로딩, 저장소 열기
  → 문장마다: 실행 → 결과 출력
       실행 오류가 나면 거기서 끝 (종료 코드 2). 앞 문장의 결과는 이미 출력됨
  → 저장소 닫기 (오류가 나도 반드시)
```

파싱을 전부 먼저 끝내는 것은 2단계의 결정이고, 첫 실행 오류에서 멈추는 것은 4단계의 결정이다. CLI는 그 결정을 그대로 따른다.

저장소는 `with` 블록 안에서 열어, 실행 중에 예외가 나도 파일이 닫히게 한다. 매 INSERT 뒤에 flush하므로(3단계) 닫히기 전에 죽어도 그때까지의 행은 파일에 있다.

## 4. 출력 형식

### 결정 2: SELECT는 표, INSERT는 한 줄

SELECT 결과는 컬럼 너비를 맞춘 표로 찍는다.

```
id | name | grade
---+------+------
1  | Kim  | 3
2  | Lee  | 2
```

- 각 컬럼의 너비는 헤더와 모든 값 중 가장 긴 것이다. 그래서 행을 다 받은 뒤에야 찍을 수 있다.
- 값은 `str()`로 바꿔 왼쪽 정렬한다. INT와 TEXT를 구분해 정렬하지 않는다.
- 결과가 0행이면 헤더와 구분선을 찍고 `(0 rows)`를 붙인다. 헤더가 있어야 "컬럼은 맞는데 조건에 맞는 행이 없다"가 드러난다.
- 값 안의 줄바꿈과 탭은 그대로 찍힌다. 표가 깨지지만, 저장은 올바르게 됐으므로 표시 문제일 뿐이다. 한글처럼 폭이 두 칸인 글자도 한 칸으로 셈한다. 둘 다 한계로 둔다.

INSERT 결과는 `QueryResult(("id",), ((1,),))` 모양이지만 표로 찍으면 어색하다. 문장이 `Insert`이면 `1 row inserted (id=1)` 한 줄로 찍는다. CLI는 문장 객체를 들고 있으므로 종류를 알 수 있다.

### 결정 3: 오류는 표준 에러로, 종료 코드로 종류를 구분한다

| 상황 | 표준 에러 메시지 | 종료 코드 |
| --- | --- | --- |
| 성공 | | 0 |
| SQL 파일을 읽을 수 없음 | `오류: 파일을 열 수 없습니다: ...` | 1 |
| 문법 오류 | `문법 오류: 3:12: FROM 이 와야 하는데 ...` | 1 |
| 카탈로그 오류 | `실행 오류: 스키마 파일이 없습니다: ...` | 2 |
| 실행 오류 | `실행 오류 (5번째 줄): 테이블 'teachers' 이 없습니다` | 2 |

결과는 표준 출력, 오류는 표준 에러로 나뉘어야 `python -m minidb q.sql > out.txt`로 결과만 저장할 수 있다. 종료 코드가 나뉘어야 셸 스크립트가 "고칠 것은 SQL인가, 데이터인가"를 구분할 수 있다. 1은 "입력 파일을 고치면 된다", 2는 "실행 환경이나 데이터 상태의 문제"다.

실행 오류 메시지의 줄 번호는 2단계에서 문장마다 남긴 `line`이다. 파일에 문장이 수십 개일 때 어느 것인지 바로 찾을 수 있다.

## 5. 코드 구조

- `minidb/cli.py`
  - `main(argv=None, stdout=sys.stdout, stderr=sys.stderr) -> int`: 흐름 전체. 종료 코드를 돌려주고 직접 `sys.exit`하지 않는다. 테스트가 함수로 부를 수 있게 하기 위해서다.
  - `format_insert(result) -> str`, `format_table(result) -> str`: `QueryResult`를 글자로. 순수 함수라 따로 테스트한다.
- `minidb/__main__.py`: `sys.exit(main())` 한 줄. `python -m minidb`가 이 파일을 실행한다.
- `examples/students.sql`: 0단계 문서의 예시 그대로. README에서 첫 실행으로 안내한다.

## 완료 기준

```sh
pytest tests/test_cli.py
python -m minidb examples/students.sql --data-dir /tmp/minidb-demo
```

- 예시 파일이 위의 출력 그대로 나온다. 두 번 실행하면 id가 3, 4로 이어진다.
- 문법 오류는 아무 문장도 실행하지 않고 종료 코드 1, 실행 오류는 앞 문장만 반영하고 줄 번호가 붙은 메시지와 종료 코드 2다.
- 결과는 표준 출력에, 오류는 표준 에러에만 나온다.
