# 1단계: 토크나이저

## 목표

SQL 문자열을 의미 있는 조각(토큰)의 열로 자른다.

이 단계가 끝나면 `tokenize("SELECT * FROM students WHERE id = 1;")`가 아홉 개의 토큰과 끝 표시를 돌려준다. 각 토큰은 종류(키워드, 식별자, 숫자, 문자열, 기호, 연산자), 값, 그리고 원문에서의 줄과 열을 안다. 닫히지 않은 따옴표나 허용되지 않는 문자는 위치가 붙은 `ParseError`가 된다. 토큰 열이 문법에 맞는 문장인지는 아직 모른다. 그것은 2단계 파서의 일이다.

## 이 단계의 위치

0단계 문서의 여섯 순서 중 **2번**이다.

| 순서 | 하는 일 |
| --- | --- |
| 1 | CLI가 파일에서 문장을 꺼낸다 (5단계) |
| **2** | **토크나이저가 문자열을 토큰으로 자른다 (1단계)** |
| 3 | 파서가 토큰 열을 구조화된 객체로 만든다 (2단계) |
| 4 | 실행기가 무엇을 할지 정하고 저장소에 시킨다 (4단계) |
| 5 | 저장소가 파일을 읽고 쓴다 (3단계) |
| 6 | CLI가 결과를 화면에 찍는다 (5단계) |

입력은 SQL 파일 내용 전체(문장 여러 개)이고, 출력은 토큰 하나의 리스트다. 문장을 세미콜론 단위로 나누는 것은 파서가 한다. 토크나이저는 세미콜론도 그냥 기호 토큰 하나로 넘긴다.

## 1. 왜 공백으로 자르면 안 되는가

가장 단순한 방법은 `sql.split()`이다. 다음 문장들에서 바로 깨진다.

| 입력 | `split()` 결과 | 문제 |
| --- | --- | --- |
| `VALUES ('Kim Lee', 3)` | `'Kim`, `Lee'` | 문자열 안의 공백에서 잘린다 |
| `WHERE grade=3;` | `grade=3;` | 붙여 쓴 연산자와 세미콜론이 안 떨어진다 |
| `VALUES ('a;b')` | `('a;b')` | 문자열 안의 세미콜론을 문장 끝으로 오해할 수 있다 |
| `SELECT * -- 전체 조회` | `--`, `전체`, `조회` | 주석이 토큰이 된다 |
| `VALUES ('it''s')` | `('it''s')` | 따옴표 두 개가 따옴표 하나라는 규칙을 모른다 |

즉 "어디서 자를지"는 문자 하나하나를 보면서 **지금 문자열 안인가, 주석 안인가, 숫자 중간인가**를 알아야 정해진다. 이 상태를 추적하며 자르는 것이 토크나이저다. 파서가 이 일을 같이 하면 문법 규칙과 문자 처리 규칙이 뒤섞여 둘 다 읽기 어려워진다.

## 2. 토큰의 종류

| 종류 | 예 | 값으로 무엇을 담나 |
| --- | --- | --- |
| `KEYWORD` | `SELECT`, `from` | 대문자로 정규화한 문자열 (`"SELECT"`, `"FROM"`) |
| `IDENTIFIER` | `students`, `Name` | 소문자로 정규화한 문자열 (`"students"`, `"name"`) |
| `NUMBER` | `3`, `-7` | 정수 (`3`, `-7`) |
| `STRING` | `'Kim'`, `'it''s'` | 따옴표를 벗기고 `''`를 `'`로 바꾼 문자열 (`"Kim"`, `"it's"`) |
| `SYMBOL` | `(` `)` `,` `;` `*` | 그 문자 |
| `OPERATOR` | `=` `!=` `<` `<=` `>` `>=` | 그 문자열 |
| `EOF` | | 입력의 끝. 파서가 "더 없음"을 확인할 때 쓴다 |

키워드는 여섯 개다. `SELECT`, `FROM`, `WHERE`, `INSERT`, `INTO`, `VALUES`. 지원 문장이 두 개뿐이므로 이것으로 충분하다.

### 결정 1: 키워드와 식별자를 토크나이저에서 구분한다

`SELECT`와 `students`는 둘 다 "글자 덩어리"라서 자르는 규칙은 같다. 구분을 어디서 하느냐가 선택이다.

- 토크나이저에서 구분하면, 파서는 "다음 토큰이 `KEYWORD FROM`인가"만 보면 된다.
- 파서에서 구분하면, 파서가 매번 "이 식별자가 사실 키워드인가"를 검사해야 한다.

전자를 택했다. 부작용으로 `select`라는 이름의 컬럼은 만들 수 없다. 실제 DBMS들도 같은 제약(예약어)을 가진다.

### 결정 2: 모든 토큰이 줄과 열을 기억한다

토큰 열만 보면 원문의 어디서 왔는지 사라진다. 그러면 파서가 "FROM이 와야 하는데 `WHERE`가 왔다"는 것은 알아도 **원문 어디**인지 말할 수 없다. 토큰마다 줄과 열을 붙여 두면 1단계와 2단계의 모든 오류 메시지에 위치가 붙는다. SQL 파일이 길어질수록 이 차이가 크다. 줄과 열은 1부터 센다.

## 3. 자르는 규칙

토크나이저는 입력을 앞에서부터 한 글자씩 보며, 현재 글자가 무엇인지에 따라 아래 중 하나를 한다.

| 현재 글자 | 하는 일 |
| --- | --- |
| 공백, 탭, 줄바꿈 | 건너뛴다. 줄바꿈이면 줄 번호를 올리고 열을 1로 되돌린다 |
| `--` | 줄 끝까지 건너뛴다 (주석) |
| `'` | 닫는 `'`까지 읽는다. 도중에 `''`를 만나면 `'` 하나로 바꾸고 계속 읽는다. 입력이 끝나도 닫히지 않으면 오류 |
| 숫자, 또는 `-` 바로 뒤에 숫자 | 숫자가 이어지는 데까지 읽어 정수로 만든다 |
| 영문자 또는 `_` | 영문자, 숫자, `_`가 이어지는 데까지 읽는다. 대문자로 바꿔 키워드 목록에 있으면 `KEYWORD`, 아니면 소문자로 바꿔 `IDENTIFIER` |
| `(` `)` `,` `;` `*` | 한 글자 `SYMBOL` |
| `!=` `<=` `>=` | 두 글자 `OPERATOR`. 한 글자 `=` `<` `>`보다 **먼저** 확인한다 (최장 일치) |
| `=` `<` `>` | 한 글자 `OPERATOR` |
| 그 외 | 오류 |

몇 가지 주의할 점이 있다.

- `-`는 주석(`--`)인지 음수(`-3`)인지를 다음 글자를 보고 정한다. 둘 다 아니면 오류다. 뺄셈은 지원하지 않는다.
- `<=`를 `<`와 `=`로 자르면 파서가 "`<` 뒤에 값이 와야 하는데 `=`가 왔다"고 엉뚱한 오류를 낸다. 그래서 두 글자 연산자를 먼저 본다.
- `3.14`는 `3`까지 읽고 `.`에서 오류가 난다. INT만 지원하므로 의도된 동작이다.
- 식별자는 ASCII 영문자만 허용한다. 카탈로그의 식별자 규칙(0단계)과 맞춘다.
- 문자열 안에는 줄바꿈을 포함해 어떤 문자든 올 수 있다. 저장소에서 줄바꿈을 어떻게 다룰지는 3단계의 일이다.

## 4. 오류

모두 `ParseError`이며 줄과 열이 붙는다.

| 입력 | 메시지 |
| --- | --- |
| `VALUES ('Kim)` | `1:9: 닫히지 않은 문자열` |
| `SELECT # FROM t` | `1:8: 허용되지 않는 문자 '#'` |
| `WHERE id - 1` | `1:10: 허용되지 않는 문자 '-'` |

0단계의 `ParseError`에 `line`, `col` 속성을 추가했다. 메시지 문자열에 위치를 박아 넣는 대신 속성으로 두면, 서버(13단계)가 JSON 응답에 위치를 따로 실을 수 있다.

## 5. 코드 구조 (`minidb/lexer.py`)

- `Token(kind, value, line, col)`: 불변 데이터 클래스.
- `tokenize(sql) -> list[Token]`: 유일한 공개 함수. 마지막 원소는 항상 `EOF` 토큰이다.
- 내부는 `_Lexer` 클래스 하나다. 현재 위치(`pos`, `line`, `col`)를 들고 `_peek`, `_advance`로 한 글자씩 소비한다. 종류별 읽기는 `_read_string`, `_read_number`, `_read_word` 메서드다.

토크나이저는 카탈로그를 모른다. `students`가 실제로 있는 테이블인지는 상관없이 `IDENTIFIER`로 넘긴다.

- INSERT와 SELECT 예시 문장이 기대한 토큰 열로 잘린다.

- 닫히지 않은 문자열과 허용되지 않는 문자는 정확한 줄과 열이 붙은 `ParseError`다.
- 여러 줄 입력에서 각 토큰의 줄과 열이 맞다.
