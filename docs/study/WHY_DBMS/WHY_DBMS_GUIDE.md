# 왜 DBMS인가

> **한 줄 요약**: 파일로 데이터를 다루면, 데이터를 다루는 방법(파일 형식, 찾는 방법, 동시에 쓸 때의 보호)이 **프로그램마다 따로** 코드에 들어갑니다. DBMS는 그 일을 **프로그램 밖의 전담 프로그램 하나**로 빼냅니다.

## 1. 출발점: 파일은 좋은 도구다

막 문을 연 쇼핑몰 "정글마켓"에는 주문 프로그램 하나만 있습니다. 주문이 들어오면 `orders.csv` 파일 끝에 한 줄을 추가하고, 주문 목록이 필요하면 파일을 처음부터 읽으며 조건에 맞는 줄을 고릅니다.

```python
def add_order(order_id, user, product, price):
    with open("orders.csv", "a") as f:               # "a": 파일 끝에 덧붙이기
        f.write(f"{order_id},{user},{product},{price}\n")

def find_orders(user):
    for line in open("orders.csv"):                   # 처음부터 한 줄씩
        order_id, user_, product, price = line.strip().split(",")   # 쉼표로 4칸으로 나눔
        if user_ == user:
            yield product, int(price)
```

`orders.csv`는 이렇게 생겼습니다.

```
1,kim,키보드,200000
2,lee,마우스,30000
```

설치할 것도 배울 것도 없고, 메모장으로 열어 볼 수 있고, 주문이 하루 수십 건이면 처음부터 읽어도 금방입니다. **프로그램 하나가 작은 파일 하나를 쓴다면 여기서 끝이고, DBMS는 필요 없습니다.**

## 2. 상황이 바뀐다: 프로그램이 늘고, 데이터가 커진다

정글마켓이 커지면서 회원, 배송, 정산, 마케팅 프로그램이 생기고, 각 팀이 따로 만듭니다. 주문은 쌓여서 100만 건이 되고, 세일 날에는 수백 명이 같은 순간에 주문합니다.

각 팀은 **자기 프로그램에 필요한 파일을 직접 만들고, 다른 팀의 파일은 그 형식에 맞춰 읽습니다.** 코드는 1절과 같은 방식 그대로입니다.

> 이건 문제가 터지는 **상황**이지, 문제의 원인이 아닙니다. 같은 코드도 프로그램 하나, 작은 데이터에서는 멀쩡합니다. 원인은 4절에서 봅니다.

## 3. 생기는 문제: 여섯 장면

### ① 주소를 바꿨는데 택배는 옛날 집으로 간다

kim의 주소는 회원팀의 `members.csv`에도 있고, 배송팀이 편하게 쓰려고 따로 복사해 둔 `shipping.csv`에도 있습니다.

kim이 이사해서 주소를 바꾸면, 회원 프로그램은 **자기 파일(`members.csv`)만** 고칩니다. 배송 프로그램은 `shipping.csv`에 남은 옛 주소로 택배를 보냅니다.

**왜**: 같은 데이터가 파일 여러 개에 복사돼 있고, 회원 프로그램은 `shipping.csv`가 있다는 것조차 모르기 때문입니다.

### ② 칸 하나 추가했더니 다른 프로그램이 깨진다

주문팀이 `orders.csv`에 쿠폰 칸을 추가합니다. 한 줄이 `id,user,product,price`(4칸)에서 `id,user,product,coupon,price`(5칸)로 바뀝니다.

- 1년 전에 만든 정산 프로그램은 `order_id, user, product, price = line.split(",")`처럼 "칸이 4개"라고 정해 두고 읽습니다. 칸이 5개가 되자 오류를 내고 멈춥니다.
- 마케팅 스크립트는 "4번째 칸이 가격"이라고 알고 있어서, 이제 4번째가 된 쿠폰 값을 매출로 더합니다. 오류 없이 틀린 숫자가 나와서 더 위험합니다.
- 상품 이름에 쉼표가 들어가도(`"키보드, 무선"`) 칸 수가 달라져 똑같이 깨집니다.

**왜**: "몇 번째 칸이 가격인지" 같은 **파일 형식에 대한 지식이 프로그램마다 코드에 박혀** 있기 때문입니다. 형식을 바꾼 팀은 다른 팀의 코드에 그런 가정이 있는지 알 수 없습니다.

### ③ 질문 하나에 프로그램 하나

마케팅팀이 "지난달 서울에 사는 30대가 가장 많이 산 상품 10개"를 묻습니다. 개발자가 회원 파일과 주문 파일을 반복문으로 엮어 답을 내는 코드를 이틀 걸려 짭니다. 다음 주에 "부산 20대는?"이라고 물으면 또 새 코드를 짜야 합니다.

**왜**: 데이터는 있는데, **어떻게 찾을지**를 질문마다 사람이 코드로 직접 짜야 하기 때문입니다.

### ④ 주문이 100만 건이 되자 찾기가 느려진다

주문번호 하나를 찾으려면 첫 줄부터 읽어 나가며 비교해야 합니다. 뒤쪽 주문이면 거의 100만 줄을 읽습니다. 조회 한 번에 수백 ms가 걸리고, 1초에 수백 명이 조회하면 서버가 버티지 못합니다.

**왜**: 파일은 처음부터 순서대로 읽는 방법밖에 모릅니다. 주문번호 순으로 정렬해 두면 가운데부터 반씩 버리며 찾을 수 있지만(이진 탐색), 주문이 들어올 때마다 100만 줄을 다시 정렬할 수는 없습니다.

### ⑤ 세일 날, 남은 1개를 두 명에게 판다

재고 파일에 `1`이 적혀 있을 때, kim과 lee의 주문이 거의 동시에 들어옵니다.

```
주문 프로그램 A (kim): 재고 파일을 읽음 → 1
주문 프로그램 B (lee): 재고 파일을 읽음 → 1       ← A가 0을 쓰기 전에 읽음
주문 프로그램 A (kim): "살 수 있음" → 재고 파일에 0을 씀
주문 프로그램 B (lee): "살 수 있음" → 재고 파일에 0을 씀
→ 1개를 2명에게 팔았음
```

같은 파일에 두 프로그램이 동시에 줄을 추가하다가, 두 줄이 뒤섞인 깨진 줄이 생기기도 합니다.

**왜**: "읽기 → 판단 → 쓰기" 사이에 다른 프로그램이 끼어들 수 있고, 순서를 정해 줄 곳이 없기 때문입니다.

### ⑥ 저장하다 꺼지면 돈만 빠진다

주문 하나를 처리하려면 결제 파일, 재고 파일, 주문 파일 세 개를 차례로 고쳐야 합니다. 결제 기록을 쓴 직후 전원이 나가면 이렇게 됩니다.

| 파일 | 상태 |
| --- | --- |
| 결제 파일 | 결제 기록이 남음 (고객 돈은 나감) |
| 재고 파일 | 쓰던 도중이라 반만 남아 읽을 수 없음 |
| 주문 파일 | 아무것도 안 써짐 (주문은 없음) |

**왜**: 여러 파일의 변경을 **"전부 되거나, 전부 안 되거나"**로 묶어 주는 장치가 없기 때문입니다.

### 정리: 누가 겪고, 어떻게 드러나나

| 장면 | 누가 겪나 | 어떻게 드러나나 |
| --- | --- | --- |
| ① 주소가 어긋남 | 고객 | 엉뚱한 곳으로 배송 |
| ② 형식이 바뀜 | 개발자 | 칸 하나 바꿀 때마다 다른 프로그램이 깨짐 |
| ③ 질문마다 코드 | 회사 | 데이터가 있어도 답을 얻는 데 며칠 |
| ④ 느린 찾기 | 고객, 운영자 | 데이터가 늘수록 느려지고 서버가 버티지 못함 |
| ⑤ 동시에 쓰기 | 고객, 회사 | 초과 판매, 깨진 줄 |
| ⑥ 중간에 꺼짐 | 고객, 회사 | 돈과 주문이 안 맞음, 파일 손상 |

묶어 보면 세 종류입니다.

- ①②: 데이터가 서로 어긋나거나 프로그램이 깨지는 문제
- ③④: 데이터를 꺼내기 어렵고 느린 문제
- ⑤⑥: 데이터 자체가 망가지는 문제

## 4. 원인은 하나다

> **데이터를 다루는 방법(형식, 찾기, 보호)이 프로그램마다 따로 코드 안에 들어 있다.**

1절의 정산 코드 몇 줄을 다시 보면, 이 안에 데이터의 위치, 형식, 찾는 방법이 모두 들어 있습니다. 그리고 동시에 쓸 때와 중간에 꺼질 때의 대비는 없습니다.

```python
for line in open("orders.csv"):                              # 위치: orders.csv라는 파일
    order_id, user, product, price = line.strip().split(",") # 형식: 쉼표로 나눈 4칸, 4번째가 가격
    ...                                                      # 찾는 방법: 처음부터 한 줄씩
                                                             # 보호: 없음
```

회원, 주문, 배송, 정산, 마케팅 다섯 프로그램이 이런 코드를 **각자 따로** 들고 있습니다. 여섯 장면은 이 한 가지 원인이 다르게 드러난 것입니다.

| 장면 | 원인이 드러난 모습 |
| --- | --- |
| ① 주소 | 프로그램마다 자기 파일을 가져서, 같은 데이터가 여러 벌 생김 |
| ② 형식 | 파일 형식에 대한 지식이 각 프로그램 코드에 있음 |
| ③ 질문 | 찾는 방법이 각 프로그램 코드에 있음 |
| ④ 찾기 | 빨리 찾는 색인(인덱스)을 만들어도, 모든 프로그램이 함께 쓸 곳이 없음 |
| ⑤ 동시성 | 순서를 정하는 규칙을 각자 알아서 해야 함. 결국 아무도 안 함 |
| ⑥ 장애 | 여러 변경을 하나로 묶는 장치를 각자 알아서 해야 함. 결국 아무도 안 함 |

### 문제를 하나씩 막으면 어떻게 되나

| 시도 | 막는 것 | 남는 문제 |
| --- | --- | --- |
| 파일 읽는 코드를 공용 라이브러리로 만듦 | ② 형식 지식이 한 곳에 모임 | 형식이 바뀔 때마다 모든 프로그램을 다시 배포해야 함. ④⑤⑥은 그대로 |
| 파일 잠금 (`flock`: 운영체제에 "이 파일은 지금 내가 쓴다"고 알리는 기능) | ⑤ 동시에 쓰기 | 파일 전체를 잠가서 모두가 줄을 섬. 한 프로그램이라도 잠금을 빼먹으면 무너짐 |
| 주문번호 순으로 정렬해서 저장 | ④ 이진 탐색으로 빨리 찾음 | 추가할 때마다 전체를 다시 정렬. 다른 칸(user)으로 찾으면 여전히 느림 |
| 매일 밤 백업 | ⑥ 일부 복구 | 백업 이후 데이터는 잃음. 반만 써진 상태는 그대로 |

이렇게 하나씩 막다 보면, 모든 프로그램이 지켜야 할 공용 코드와 규칙이 점점 커집니다. 그 공용 코드와 규칙을 **아예 독립된 프로그램 하나로 떼어 낸 것**이 DBMS입니다.

## 5. 해결: 데이터를 다루는 일을 프로그램 밖으로 뺀다

다른 프로그램은 무엇이 필요한지만 SQL로 말하고, 데이터를 다루는 일은 DBMS 한 곳이 맡습니다.

```
회원 · 주문 · 배송 · 정산 · 마케팅
              ↓  SQL로 "무엇이 필요한지"만 말함
            DBMS  (테이블 모양, SQL 처리, 인덱스, 동시성 제어, 복구를 혼자 맡음)
              ↓
         디스크의 파일
```

정산 프로그램은 이렇게 바뀝니다.

```python
# 전: 파일 위치, 형식, 찾는 방법을 직접 앎
for line in open("orders.csv"):
    order_id, user, product, price = line.strip().split(",")
    total += int(price)

# 후: "price 칸의 합"만 말함
total = db.execute("SELECT SUM(price) FROM orders")
```

| 장면 | DBMS에서 풀리는 방식 |
| --- | --- |
| ① | 주소는 `members` 테이블에 한 번만 저장. 배송은 주문과 회원 정보를 함께 조회(JOIN: 두 테이블을 공통 칸으로 이어 붙여 조회하는 것) → 주소를 고치면 모두가 새 주소를 봄 |
| ② | 칸을 번호가 아니라 이름(`price`)으로 요청 → 칸을 추가해도 기존 SQL은 그대로 동작 |
| ③ | SQL 한 문장으로 직접 질문. 질문이 바뀌면 문장만 바꿈 |
| ④ | DBMS가 인덱스(B+ 트리)를 관리 → 100만 건도 몇 번의 비교로 찾음 |
| ⑤ | 모든 요청이 DBMS 한 곳을 거침 → lock으로 순서를 정해, 재고가 1개면 한 명만 삼 |
| ⑥ | 여러 변경을 트랜잭션 하나로 묶음 → 중간에 꺼지면 시작 전 상태로 되돌림 |

**DBMS도 결국 파일에 저장합니다.** 달라진 것은 **그 파일을 DBMS만 직접 만지고**, 다른 프로그램은 모두 DBMS에게 부탁한다는 점입니다.

데이터를 맡길 곳의 후보는 셋이었습니다.

| 후보 | 결과 |
| --- | --- |
| 각 프로그램 안에 넣는 공용 라이브러리 | 프로그램마다 라이브러리 버전이 갈리고, 동시성과 복구는 여전히 각자 해야 함 → 탈락 |
| 공유 폴더와 "이렇게 쓰자"는 규칙 문서 | 사람이 규칙을 지켜야 해서, 한 명만 어겨도 무너짐 → 탈락 |
| **데이터만 전담하는 별도 프로그램** | 형식, 색인, 순서, 복구를 한 곳에서 책임짐 → 이것이 DBMS |

핵심은 프로그램이 **"어떻게" 찾을지가 아니라 "무엇이" 필요한지만 말하게 된 것**입니다. 그래서 DBMS 안에서 저장 방식이나 인덱스가 바뀌어도, SQL을 보내는 프로그램은 고치지 않아도 됩니다. 이 성질을 **데이터 독립성**이라고 부릅니다.

## 6. DBMS의 역사: 어떻게 지금 모습이 됐나

**1960년대: 데이터를 프로그램 밖으로 빼다**

GE의 IDS(나중에 CODASYL이 1969~1971년 표준으로 정리한 **네트워크형 DB**)와, 아폴로 계획의 로켓 부품 관리에서 출발한 IBM의 IMS(**계층형 DB**, 1968년 설치)가 처음으로 데이터를 프로그램 밖으로 빼서 공유, 동시성, 복구를 맡았습니다.

하지만 데이터를 꺼내려면 프로그램이 데이터 사이에 미리 연결해 둔 길을 직접 따라가야 했습니다.

```
"kim의 주문 목록" 꺼내기:
  kim을 찾음 → kim의 첫 주문으로 가는 연결을 따라감 → 다음 주문으로 가는 연결을 따라감 → ...
```

데이터 구조가 바뀌면 이 길이 바뀌어서 프로그램을 고쳐야 했고, 미리 연결해 두지 않은 질문은 여전히 어려웠습니다. 데이터는 밖으로 뺐지만, **찾아가는 길은 여전히 프로그램이 들고 있던 셈**입니다.

**1970년: 표로 저장하고, 조건만 말하기**

IBM 연구소의 코드(Codd)가 1970년 논문 "A Relational Model of Data for Large Shared Data Banks"에서 **관계형 모델**을 제안했습니다. 데이터를 표(테이블)로만 표현하고, 프로그램은 원하는 결과의 **조건만** 말하게 했습니다. 어떻게 찾을지는 DBMS가 정합니다. 이 아이디어가 SQL과 Oracle, DB2, MySQL, PostgreSQL로 이어집니다.

| 할 수 있나 | 파일 | 계층형·네트워크형 | 관계형 DBMS |
| --- | --- | --- | --- |
| 모든 프로그램이 같은 데이터 한 벌을 씀 | ✗ | ✓ | ✓ |
| 형식이 바뀌어도 프로그램은 그대로 | ✗ | △ 따라갈 길이 바뀜 | ✓ 이름으로 요청 |
| 새 질문을 코드 없이 | ✗ | ✗ 길을 따라가는 코드가 필요 | ✓ SQL |
| 큰 데이터에서 빨리 찾기 | ✗ | ✓ 미리 연결해 둔 길 | ✓ 인덱스. 어떤 방법으로 찾을지 DBMS가 고름 |
| 동시에 써도 안전 | ✗ | ✓ | ✓ lock, MVCC |
| 중간에 꺼져도 반만 남지 않음 | ✗ | ✓ | ✓ 트랜잭션, 로그 |
| 잘못된 값 막기 | ✗ 프로그램마다 따로 | △ | ✓ 타입, 제약 조건 |

표에 나온 말 몇 가지:

- **MVCC**: 데이터를 고칠 때 옛 버전을 지우지 않고 잠시 남겨 두는 방식입니다. 읽는 쪽은 옛 버전을 읽으면 되니까, 쓰는 중이어도 기다리지 않고 읽을 수 있습니다. PostgreSQL이 이렇게 합니다.
- **제약 조건**: "재고는 0 이상"처럼 테이블에 걸어 두는 규칙입니다. 이 규칙을 어기는 변경은 DBMS가 거부합니다.

### 인덱스를 추가해도 SQL은 그대로다

같은 `SELECT * FROM orders WHERE id = 987654`라도, DBMS는 `id`에 인덱스가 있으면 인덱스로 찾고, 없으면 처음부터 읽습니다. 그래서 인덱스를 추가하면 SQL은 한 글자도 안 바꿨는데 빨라집니다.

이렇게 "어떤 방법으로 찾을지"를 고르는 DBMS의 부분을 **쿼리 플래너**라고 합니다. 우리 과제에서 실행기가 "조건이 `WHERE id = ?`이면 B+ 트리를 쓴다"고 정하는 한 줄이 쿼리 플래너의 가장 단순한 형태입니다.

### 여러 변경을 DBMS 안에서 한 번에: 트랜잭션

장면 ⑤⑥은 **트랜잭션**으로 풉니다. 재고 줄이기, 결제 기록, 주문 추가를 `BEGIN`과 `COMMIT` 사이에 묶습니다.

```sql
BEGIN;
UPDATE stock SET count = count - 1 WHERE product = '키보드' AND count > 0;
INSERT INTO payments ...;
INSERT INTO orders ...;
COMMIT;   -- 여기까지 와야 셋 다 반영됨. 그 전에 꺼지면 셋 다 없던 일
```

트랜잭션이 지키는 네 가지 성질을 앞 글자를 따서 **ACID**라고 부릅니다.

| 성질 | 뜻 | 막는 장면 |
| --- | --- | --- |
| 원자성 (Atomicity) | 전부 되거나, 전부 안 되거나 | ⑥ 돈만 빠짐 |
| 일관성 (Consistency) | "재고 ≥ 0" 같은 규칙이 항상 지켜짐 | ⑤ 초과 판매 |
| 격리성 (Isolation) | 동시에 실행해도, 하나씩 차례로 실행한 것과 같은 결과 | ⑤ 끼어들기 |
| 지속성 (Durability) | `COMMIT`된 것은 꺼져도 남음 | ⑥ 파일 손상 |

원칙은 **"여러 변경을 프로그램이 따로따로 하지 말고, 트랜잭션 하나로 DBMS에 맡긴다"**입니다.

## 7. 실제로 DBMS를 쓰는 코드

DBMS도 보통 **따로 떠 있는 서버 프로그램**입니다. (SQLite처럼 프로그램 안에 넣어 쓰는 것도 있습니다.) 다른 프로그램은 네트워크로 DBMS에 접속해 SQL을 보냅니다. 파일을 직접 열던 코드가 SQL을 보내는 코드로 바뀝니다.

아래는 PostgreSQL에 접속하는 파이썬 코드 예시입니다.

```python
conn = psycopg.connect("host=DB서버주소 dbname=jungle")    # DBMS 서버에 접속

def find_orders(user):                                     # 장면 ②③④
    return conn.execute(
        "SELECT product, price FROM orders WHERE user_name = %s", (user,)
    ).fetchall()

def place_order(user, product, price):                     # 장면 ⑤⑥
    with conn.transaction():                               # 이 블록 전체가 트랜잭션 하나
        row = conn.execute(
            "UPDATE stock SET count = count - 1 "
            "WHERE product = %s AND count > 0 RETURNING count", (product,)
        ).fetchone()
        if row is None:                                    # 재고가 0이라 아무 줄도 안 바뀜
            raise SoldOut()                                # 예외가 나면 블록 안의 변경이 모두 취소됨
        conn.execute("INSERT INTO orders VALUES (%s, %s, %s)", (user, product, price))
```

`%s` 자리의 값은 SQL 문자열에 직접 붙이지 않고 따로 넘깁니다. 이걸 **파라미터 바인딩**이라고 합니다. 값을 문자열에 직접 붙이면, 이름에 `'`가 들어간 사용자에서 SQL이 깨지고, 악의적인 사용자가 값 대신 SQL 명령을 끼워 넣을 수 있습니다(**SQL 인젝션**). 파라미터 바인딩은 이 두 가지를 막는 기본입니다.

정글마켓이 더 커지면 이런 구조가 됩니다.

```
앱 서버 → 레디스 (자주 쓰는 결과의 빠른 사본) → DBMS (원본) → 디스크
```

## 8. 우리 과제: 무엇을 왜 만드나

DBMS 안은 보통 이런 부분들로 나뉩니다.

| 부분 | 하는 일 |
| --- | --- |
| 연결 | 다른 프로그램의 요청을 받음 |
| SQL 처리 | SQL 문장을 해석하고 실행함 |
| 인덱스 | 빨리 찾게 해 줌 |
| 저장 | 파일에 읽고 씀 |
| 트랜잭션 | 동시성과 복구를 맡음 |

우리 과제의 Phase 1·2·3은 이 부분들을 가장 단순한 형태로 직접 만들어 보는 것이고, 여섯 장면 중 ②③④⑤를 직접 다시 풀어 봅니다.

**왜 인덱스로 B+ 트리를 쓰나**

데이터베이스에 오는 질문은 "이 키의 값을 줘"만 있지 않습니다. 범위(`id`가 100~200), 정렬(`ORDER BY`), 최댓값 같은 질문이 흔합니다.

| 자료구조 | `id = 5` 찾기 | `id`가 100~200인 것 찾기 | 문제 |
| --- | --- | --- | --- |
| 해시 테이블 (미니 레디스에서 만든 것) | 가장 빠름 | 못 함. 키를 계산해 흩어 놓아서 전부 확인해야 함 | 순서가 없음 |
| 이진 트리 | 빠름 | 가능 | 한 칸에 키가 하나라 나무가 깊어짐 (100만 건이면 약 20층) |
| **B+ 트리** | 빠름 | 시작점만 찾고 옆으로 이어 읽으면 됨 | 한 칸에 키를 수백 개 담아 3~4층이면 수억 건을 찾음 |

그래서 B+ 트리가 거의 모든 관계형 DB의 기본 인덱스입니다.

**우리가 만들 방식 (제안)**

아래 표는 DBMS의 각 기능을 우리 개발 단계와 연결하고, 그 방식을 고른 이유를 적은 것입니다. "개발 단계"의 숫자는 [설계](../../DESIGN.md) 3절의 단계 번호입니다(예: `1 → 3, 4`는 "1단계에서 임시로 만들고, 3·4단계에서 제대로 바꿈"). 모두 **아직 제안**이고, 자세한 결정은 [설계](../../DESIGN.md) 4절에 있습니다.

| DBMS의 기능 | 푸는 장면 | 개발 단계 | 제안하는 방식 | 이유 |
| --- | --- | --- | --- | --- |
| SQL 해석 | ②③ | 1 → 3, 4 | 처음엔 예제 SQL만 읽는 임시 파서로 끝까지 이어 본 뒤, 토크나이저 + 재귀 하강 파서로 교체 | 재귀 하강 파서는 문법 규칙 하나가 함수 하나라, 만들기도 설명하기도 쉬움 |
| 파일 저장 | | 1 → 5 | 한 줄에 데이터 하나를 JSON 배열로, 파일 끝에 추가만 함 | 쉼표나 한글이 든 값도 안전. 이미 쓴 줄의 위치가 안 바뀌어 인덱스가 계속 맞음 |
| 테이블 모양, 잘못된 값 막기 | ② | 0, 6 | `schema.json`에 칸과 타입을 적어 두고, 칸 수와 타입을 검사 | 과제가 `CREATE TABLE`을 요구하지 않아서 미리 적어 둠 |
| 인덱스 | ④ | 2 → 7, 8 | 처음엔 파이썬 `dict`, 다음에 메모리 B+ 트리로 교체 (id → 파일 위치) | 과제가 메모리 기반을 요구함. 데이터 전체 대신 위치만 담아 메모리를 아낌 |
| 쿼리 플래너 | ④ | 2, 8 | `WHERE id = ?`면 인덱스, 아니면 처음부터 읽기 | 과제의 비교 조건과 같음. 어떤 방법을 골랐는지 보여 주는 `EXPLAIN`은 17단계(선택) |
| 성능 증명 | ④ | 9, 10 | 100만 건을 만들고, 1만·10만·100만 건에서 각각 비교 | 숫자 하나보다 "데이터가 늘 때 시간이 늘어나는 모양"이 차이를 잘 보여 줌 |
| 외부 연결 | | 2 → 11 | HTTP `POST /query`로 받고, 직접 만든 Thread Pool로 처리 | 요청마다 스레드를 새로 만들면, 요청이 몰릴 때 스레드가 끝없이 늘어 서버가 버티지 못함 |
| 동시성 제어 | ⑤ | 12 | 처리기 전체에 lock 하나 | 단순하고 확실함. 미니 레디스와 같은 방식. 읽기와 쓰기를 나눈 lock은 16단계(선택) |
| 조회 결과 캐시 | | 18 | 미니 레디스에 `SELECT` 결과를 저장하고, `INSERT`가 오면 지움 | 두 과제를 "DBMS 앞의 레디스" 구조로 연결 (선택) |
| 트랜잭션, 복구, JOIN | ①⑥ | 하지 않음 | | 과제 범위 밖 ([설계](../../DESIGN.md)의 "하지 않을 것"). 발표에서 실제 DB의 방식으로 설명 |

## 9. 언제 파일, 언제 DBMS?

| 데이터 성격 | 파일 | DBMS |
| --- | --- | --- |
| 한 프로그램만 쓰는 설정 | 적합 | 과함 |
| 쌓기만 하고 나중에 분석하는 기록 (로그) | 적합 | 분석용 DB를 따로 쓰기도 함 |
| 이미지, 동영상 같은 큰 파일 | 적합 | 파일 경로만 DB에 저장 |
| 한 프로그램만 쓰지만 조건으로 찾아야 함 | 직접 만들면 고생 | SQLite |
| 여럿이 함께 쓰고, 동시에 바뀌고, 틀리면 안 됨 (주문, 결제, 재고) | 부적합 | 필요 |

기준은 세 가지입니다: **여럿이 함께 쓰는 데이터인가, 깨지면 안 되는 데이터인가, 여러 방식으로 물어볼 데이터인가.**

## 10. DBMS도 공짜는 아니다

| 비용 | 무엇이 문제인가 | 보완하는 방법 |
| --- | --- | --- |
| 운영 | 별도 서버를 띄우고, 백업하고, 업그레이드해야 함 | 클라우드가 관리해 주는 DB를 씀. 작은 서비스는 SQLite |
| 테이블 모양 바꾸기 | 데이터가 많은 테이블에 칸을 바꾸면 오래 걸리고 위험함 | 마이그레이션 도구(테이블 변경을 기록하고 차례로 적용하는 도구), 조금씩 나눠 바꾸기 |
| 서버 늘리기 | 원본이 한 곳이고 트랜잭션이 있어서 서버를 여러 대로 늘리기 어려움 | 읽기 전용 복제본, **레디스 캐시로 DB 부담 줄이기**, 샤딩(데이터를 나눠 여러 DB에 저장). 이 한계 때문에 NoSQL이 등장함 |
| 인덱스 | 저장 공간을 쓰고, `INSERT`할 때마다 인덱스도 고쳐야 해서 쓰기가 느려짐 | 자주 찾는 칸에만 만듦. `EXPLAIN`으로 실제로 쓰이는지 확인 |
| 요청마다 드는 비용 | 네트워크 왕복, SQL 해석 | 커넥션 풀(DB 접속을 미리 여러 개 열어 두고 재사용), prepared statement(SQL을 미리 해석해 두고 값만 바꿔 실행) |

### 헷갈리기 쉬운 것

- **DBMS도 파일에 저장합니다.** 파일 방식과의 차이는 저장 장소가 아니라 **파일을 누가 직접 만지느냐**입니다.
- **lock과 트랜잭션은 다릅니다.** lock은 동시에 끼어들지 못하게 막는 도구(격리성)입니다. 트랜잭션은 거기에 더해 "중간에 꺼져도 반만 남지 않게"(원자성, 지속성)까지 묶은 약속입니다. 우리 과제는 lock까지 만듭니다.

## 예상 질문

**Q. 파일에 잠금만 걸면 되지 않나요?**
동시에 쓰기(⑤)는 막힙니다. 하지만 모든 프로그램이 빠짐없이 잠금을 지켜야 하고, 파일 전체를 잠가서 모두가 줄을 섭니다. 형식(②), 질문(③), 찾기(④), 장애(⑥) 문제는 그대로 남습니다.

**Q. DBMS도 파일에 저장하는데 뭐가 다른가요?**
파일을 DBMS만 직접 만지고, 형식, 색인, 순서, 복구를 한 곳에서 책임진다는 점이 다릅니다.

**Q. 해시 테이블이 더 빠른데 왜 B+ 트리를 쓰나요?**
해시 테이블은 `=`(딱 맞는 값)만 빠르고, 범위와 정렬을 못 합니다. 데이터베이스에는 범위와 정렬 질문이 흔해서 순서를 유지하는 B+ 트리를 씁니다. 레디스는 질문이 항상 "이 키의 값"이라 해시 테이블이 맞습니다.

**Q. 레디스가 있으면 DBMS는 필요 없나요?**
레디스는 자주 쓰는 결과의 빠른 사본을 들고 있을 뿐이고, 원본과 트랜잭션은 DBMS가 책임집니다. 레디스는 DBMS를 대신하는 게 아니라, DBMS 앞에서 요청을 덜어 줍니다.

**Q. 우리 미니 DBMS는 장면 ⑥(중간에 꺼짐)을 막나요?**
아니요. 트랜잭션과 로그는 과제 범위 밖입니다. 다만 파일 끝에 추가만 하는 방식(제안)이라, 이미 저장된 데이터는 망가지지 않고 마지막 한 줄만 깨질 수 있습니다. 실제 DB는 변경 내용을 로그 파일에 먼저 쓰고 나서 실제 데이터를 고치는 방식(WAL, Write-Ahead Log)으로 이 문제를 풉니다. 꺼졌다 켜지면 로그를 보고 마무리하거나 되돌립니다.

**Q. lock이 하나뿐이면 Thread Pool이 의미가 있나요?**
처리기 실행은 한 번에 하나씩이지만, 요청 받기, 본문 읽기, JSON 해석, 응답 보내기는 lock 바깥에서 여러 스레드가 동시에 합니다. 먼저 lock 하나로 정확하게 동작하게 만들고, 그다음 읽기와 쓰기를 나눈 lock으로 개선하는 순서입니다.
