## 0. 큰 그림: DBMS는 SQL 한 줄을 어떻게 처리하나

실제 DB(PostgreSQL, MySQL)도 큰 흐름은 같습니다.

```
SQL 문자열
  → 토크나이저(lexer)   : 글자를 단어로 자름
  → 파서(parser)        : 단어를 문법 구조(트리)로 만듦
  → 플래너(planner)     : 어떻게 실행할지 고름 (인덱스를 쓸까, 전체를 훑을까)
  → 실행기(executor)    : 계획대로 저장소에 요청
  → 저장 엔진(storage)  : 디스크의 파일을 읽고 씀
```

우리 프로젝트에서 각각에 해당하는 것:

| 실제 DB | 우리 구현 | 단순화한 점 |
| --- | --- | --- |
| 토크나이저 | 4단계 | 지원 토큰 종류가 적음 |
| 파서 | 5단계 | `INSERT`, `SELECT`, `WHERE 컬럼 = 값`만 |
| 플래너/옵티마이저 | 실행기 안의 `if where.column == "id"` 한 줄 | 비용 계산 없이 규칙 하나 |
| 실행기 | 1, 6, 9단계 | |
| 저장 엔진 + 버퍼 풀 | 테이블 파일 (JSON Lines) | 페이지, 캐시 없음 |
| 인덱스 | 메모리 B+ 트리 | 디스크에 저장하지 않음 |
| 연결 관리 + 동시성 제어 | Thread Pool + lock 하나 | MVCC, 행 단위 lock 없음 |

> 핵심 문장: "우리 미니 DBMS는 실제 DB의 처리 단계를 모두 갖추고, 각 단계를 가장 단순한 형태로 구현했다."

## 1. SQL 처리기 (1~9단계)

### 1-1. 토크나이저: 글자를 단어로

`SELECT name FROM users WHERE age = 25;` 는 컴퓨터에게 그냥 글자들입니다. 먼저 의미 있는 조각(토큰)으로 자릅니다.

```
SELECT | name | FROM | users | WHERE | age | = | 25 | ;
키워드   이름    키워드  이름    키워드   이름  기호  숫자  기호
```

토큰은 보통 `(종류, 값)` 쌍으로 표현합니다. 구현 방법은 두 가지입니다.

- **정규식으로 한 번에**: 토큰 종류별 패턴을 `|`로 묶고 `re.finditer`로 앞에서부터 매칭.
- **한 글자씩 읽는 상태 기계**: 지금 문자열 안인지, 숫자 안인지 상태를 들고 진행.

```python
import re
TOKEN_RE = re.compile(r"""
    \s+                      |   # 공백 (버림)
    --[^\n]*                 |   # 주석 (버림)
    (?P<STRING>'(?:[^']|'')*') |
    (?P<NUMBER>-?\d+)          |
    (?P<IDENT>[A-Za-z_]\w*)    |
    (?P<SYMBOL>[(),;=*<>])
""", re.VERBOSE)
```

주의할 점:
- 문자열 `'It''s'` 안의 `''`는 작은따옴표 하나입니다.
- 문자열 안의 `;`는 문장 구분자가 아닙니다. 그래서 **`;`로 문장을 나누는 일은 토크나이저 이후에** 해야 정확합니다. (`split(";")`은 `'a;b'`를 깨뜨림 → 엣지 케이스 단골)
- 패턴에 안 맞는 글자(`@` 등)가 나오면 "몇 번째 글자에서 알 수 없는 문자"라고 오류를 내야 합니다.

### 1-2. 파서: 단어를 구조로 (재귀 하강)

파서는 토큰 목록이 문법에 맞는지 확인하면서 구조(AST, 추상 구문 트리)를 만듭니다.
문법을 먼저 적어 두면 코드가 거의 그대로 따라 나옵니다.

```
문장      := insert문 | select문
insert문  := INSERT INTO 이름 [ "(" 이름목록 ")" ] VALUES "(" 값목록 ")"
select문  := SELECT ( "*" | 이름목록 ) FROM 이름 [ WHERE 이름 "=" 값 ]
이름목록  := 이름 { "," 이름 }
값목록    := 값 { "," 값 }
```

**재귀 하강**: 문법 규칙 하나 = 함수 하나. 현재 토큰을 보고(peek), 기대한 것이면 소비(expect)하고, 아니면 오류.

```python
def parse_select(self):
    self.expect("SELECT")
    columns = ["*"] if self.accept("*") else self.parse_name_list()
    self.expect("FROM")
    table = self.expect_ident()
    where = None
    if self.accept("WHERE"):
        col = self.expect_ident(); self.expect("="); val = self.parse_value()
        where = Where(col, "=", val)
    return Select(table, columns, where)
```

왜 "재귀"인가: 규칙이 다른 규칙을 부르기 때문입니다(`select문` → `이름목록`). 나중에 `WHERE a = 1 AND (b = 2 OR c = 3)`처럼 괄호가 중첩되면 함수가 자기 자신을 부르게 됩니다.

> 파서는 "문법"만 검사합니다. `users` 테이블이 실제로 있는지, `age`가 INT인지는 **실행기(또는 검증 단계)**가 스키마를 보고 확인합니다. 이 구분을 물어보면 답할 수 있어야 합니다.

### 1-3. 실행기

AST를 받아서 실제 동작으로 바꿉니다.

- `Insert` → 스키마로 컬럼 수·타입 확인 → ID 부여 → 저장소 `append`
- `Select` → `where`가 없으면 전체 `scan`, 있으면 조건에 맞는 줄만 → 요청한 컬럼만 골라 반환(projection)

용어 정리:
- **Selection(선택)**: 조건에 맞는 *행*을 고름 (`WHERE`)
- **Projection(투영)**: 필요한 *열*만 고름 (`SELECT name, age`)

### 1-4. 파일 기반 저장: 왜 JSON Lines인가

후보 비교:

| 포맷 | 장점 | 단점 |
| --- | --- | --- |
| CSV | 엑셀로 열림, 익숙함 | 쉼표·따옴표·줄바꿈이 든 값 처리가 까다롭고, 타입 정보가 없음 (전부 문자열) |
| JSON Lines (`[1,"현지",25]`) | 이스케이프와 타입(숫자/문자열)을 `json`이 처리, 한 줄 = 한 레코드 | CSV보다 조금 큼 |
| 고정 길이 바이너리 | N번째 레코드 위치 = N × 크기, 매우 빠름 | 문자열 길이 제한, 구현·디버깅 어려움 |

JSON Lines를 고른 핵심 이유는 **줄 단위 + 위치(offset)로 바로 찾아가기**입니다.

```python
with open(path, "ab") as f:
    offset = f.tell()                 # 이 줄이 시작하는 바이트 위치
    f.write((json.dumps(row, ensure_ascii=False) + "\n").encode())
# 나중에
with open(path, "rb") as f:
    f.seek(offset)
    row = json.loads(f.readline())
```

- **바이너리 모드인 이유**: 텍스트 모드의 `tell()`은 바이트 위치가 아닌 내부 값을 줄 수 있고, 한글(UTF-8에서 3바이트)이 섞이면 "글자 수 ≠ 바이트 수"가 됩니다.
- **append-only인 이유**: 이미 쓴 줄은 절대 움직이지 않으니, 인덱스에 저장한 offset이 영원히 유효합니다. (실제 DB의 로그 구조 저장소, LSM 트리도 같은 아이디어)

실제 DB와의 차이: 실제 DB는 파일을 **페이지(보통 4~16KB)** 단위로 나누고, 페이지 안에 슬롯으로 레코드를 배치합니다. 디스크는 1바이트가 아니라 블록 단위로 읽기 때문입니다. 이 개념이 B+ 트리가 "넓적한" 이유로 이어집니다.

### 1-5. flush와 fsync (알아두면 좋은 것)

`f.write()` 해도 바로 디스크에 가지 않습니다.

```
파이썬 버퍼 → (flush) → OS 페이지 캐시 → (fsync) → 실제 디스크
```

- 프로그램이 죽어도 OS가 살아 있으면 flush까지 된 데이터는 남습니다.
- 전원이 나가도 남기려면 fsync가 필요하지만 매우 느립니다.
- 100만 건 삽입 시 매번 flush/fsync하면 엄청 느려집니다 → 그래서 "파일을 열어 둔 채 쓰고 끝에 한 번 flush"(설계 13단계, 100만 건 넣기).

## 2. B+ 트리 인덱스 (10~14단계)

### 2-1. 인덱스가 없으면: 선형 탐색

`SELECT * FROM users WHERE id = 777777;`
인덱스가 없으면 파일의 첫 줄부터 끝까지 읽으며 `id == 777777`인지 확인해야 합니다. → **O(n)**
100만 건이면 최악 100만 줄을 읽고 JSON 파싱을 100만 번 합니다.

책의 "찾아보기(색인)"처럼, 키 → 위치를 미리 정리해 두는 것이 인덱스입니다.

### 2-2. 왜 하필 B+ 트리인가 (후보 비교)

| 자료구조 | 점 조회 `id = 5` | 범위 조회 `id > 5` | 순서대로 읽기 | 비고 |
| --- | --- | --- | --- | --- |
| 정렬 안 된 배열 | O(n) | O(n) | 불가 | 선형 탐색 |
| 해시 테이블 (미니 레디스!) | **O(1)** | 불가 (전부 훑어야) | 불가 | 순서가 없음 |
| 이진 탐색 트리 | O(log n), 최악 O(n) | 가능 | 가능 | 한쪽으로 치우치면 연결 리스트가 됨 |
| 균형 이진 트리 (AVL, 레드블랙) | O(log₂ n) | 가능 | 가능 | 노드 하나에 키 하나 → 트리가 깊음 |
| **B+ 트리** | O(log_m n) | **매우 좋음** | **매우 좋음** | 노드 하나에 키 여러 개 → 트리가 얕음 |

**해시 테이블과 비교하는 질문이 반드시 나옵니다.** 지난 과제에서 해시 테이블을 만들었으니 이렇게 연결하면 좋습니다.
> "해시는 `=` 조회는 더 빠르지만 순서를 잃습니다. DB는 범위 조회, 정렬(`ORDER BY`), 최솟값·최댓값이 흔해서 순서를 유지하는 B+ 트리를 기본 인덱스로 씁니다."

### 2-3. B+ 트리의 모양

```
                    [ 30 | 60 ]                 ← 내부 노드: 길 안내용 키만
                  /      |      \
        [10 | 20]    [30 | 45]    [60 | 75 | 90]  ← 리프 노드: 실제 키 + 값(파일 위치)
           ↔             ↔              ↔          ← 리프끼리 옆으로 연결
```

규칙:
1. **모든 값은 리프에만** 있습니다. 내부 노드의 키는 "이 키 이상은 오른쪽으로" 같은 길 안내용 복사본입니다.
2. **모든 리프는 같은 깊이**입니다. (항상 균형)
3. 노드는 최대 m-1개의 키를 가집니다 (m = 차수). 넘치면 **분할(split)**합니다.
4. **리프끼리 연결 리스트**로 이어져 있어, 범위 조회 시 시작 리프만 찾고 옆으로 쭉 읽으면 됩니다.

**B 트리와 B+ 트리의 차이** (자주 묻는 질문):

| | B 트리 | B+ 트리 |
| --- | --- | --- |
| 값의 위치 | 모든 노드 | 리프에만 |
| 리프 연결 | 없음 | 있음 |
| 범위 조회 | 트리를 위아래로 오가야 함 | 리프를 옆으로 읽으면 끝 |
| 내부 노드 | 값까지 들어서 키가 적게 들어감 | 키만 있어서 더 많이 들어감 → 더 얕음 |

### 2-4. 검색

루트부터 시작해서, 노드 안의 키들과 비교해 내려갈 자식을 고르고, 리프에 도착하면 그 안에서 찾습니다.

```python
def search(self, key):
    node = self.root
    while not node.is_leaf:
        i = bisect.bisect_right(node.keys, key)   # key 이하인 키 개수 = 내려갈 자식 번호
        node = node.children[i]
    i = bisect.bisect_left(node.keys, key)
    if i < len(node.keys) and node.keys[i] == key:
        return node.values[i]
    return None
```

`bisect_right`를 쓰는 이유: 내부 노드 키 `30`은 "30 이상은 오른쪽"이라는 뜻이라, 30을 찾을 때 오른쪽 자식으로 가야 합니다.

### 2-5. 삽입과 분할 (손으로 그려보기)

차수 4 (노드당 최대 키 3개)로 1, 2, 3, 4, 5, 6을 넣어봅니다.

```
1,2,3 삽입:     [1 2 3]

4 삽입 → 넘침:  [1 2 3 4]  → 반으로 나눔
                    [3]                ← 오른쪽 리프의 첫 키를 부모로 "복사"
                  /     \
              [1 2]  ↔  [3 4]

5 삽입:             [3]
                  /     \
              [1 2]  ↔  [3 4 5]

6 삽입 → 넘침:  [3 4 5 6] → [3 4] [5 6], 5를 부모로 복사
                   [3 | 5]
                 /    |    \
             [1 2] ↔ [3 4] ↔ [5 6]
```

**리프 분할 vs 내부 노드 분할 차이** (구현에서 제일 헷갈리는 부분):
- **리프 분할**: 가운데 키를 부모로 **복사**합니다 (리프에도 남음). 값은 리프에 있어야 하니까.
- **내부 노드 분할**: 가운데 키를 부모로 **올려 보냅니다** (내부 노드에서 빠짐). 길 안내용이니 중복될 필요가 없음.
- 루트가 분할되면 새 루트가 생기고 **트리 높이가 1 늘어납니다**. B+ 트리는 아래가 아니라 **위로 자랍니다**. 그래서 항상 균형이 유지됩니다.

> 연습: 차수 4로 10, 20, 5, 6, 12, 30, 7, 17을 직접 그려보고, 코드 출력과 비교하기.

### 2-6. 왜 이렇게 넓적한가: 높이 계산

디스크는 한 번 읽을 때 블록(예: 8KB)을 통째로 읽습니다. 디스크 읽기 한 번이 메모리 비교 수만 번보다 느리므로, **한 번 읽을 때 최대한 많은 키를 가져와 트리를 얕게** 만드는 것이 목표입니다.

높이 ≈ log_m(n)

| 레코드 수 n | 이진 트리 (m=2) | B+ 트리 m=100 | B+ 트리 m=500 |
| --- | --- | --- | --- |
| 1만 | 약 14 | 2 | 2 |
| 100만 | 약 20 | 3 | 3 |
| 1억 | 약 27 | 4 | 3 |

→ 1억 건이어도 디스크를 3~4번만 읽으면 찾습니다.

**우리는 메모리 기반이라** 디스크 읽기 비용이 없습니다. 그래서 차수를 바꿔도 체감 차이가 디스크 DB만큼 크지 않습니다. 이 점을 성능 결과와 함께 설명하면 이해도가 드러납니다.
(차수가 너무 크면 노드 안에서 리스트 삽입 `list.insert`가 O(m)이라 느려지고, 너무 작으면 트리가 깊어집니다 → 실험해서 적당한 값 찾기)

### 2-7. 우리 인덱스가 저장하는 것: ID → 파일 위치

```
B+ 트리: 777777 → 41,203,550 (바이트 위치)
          ↓
파일:    f.seek(41203550); f.readline()  → [777777, "user777777", 42]
```

- 레코드 전체가 아니라 위치만 저장하므로 메모리가 적게 듭니다.
- 실제 DB 용어로는 **보조 인덱스(secondary index)**에 가깝습니다. (MySQL InnoDB의 기본 키 인덱스는 리프에 행 전체를 담는 **클러스터드 인덱스**)
- 메모리 기반이라 서버를 껐다 켜면 인덱스가 사라집니다 → 시작할 때 파일을 한 번 훑어 재구성. 원본은 항상 파일이므로 둘이 어긋날 일이 없습니다.

### 2-8. 성능 비교를 제대로 하는 법

비교 대상:
- `SELECT * FROM users WHERE id = ?` → B+ 트리 → O(log n) + 한 줄 읽기
- `SELECT * FROM users WHERE name = ?` → 선형 탐색 → O(n)

측정할 때 주의:
1. **`time.perf_counter()`** 사용 (`time.time()`은 정밀도가 낮고 시계 조정에 영향받음).
2. **여러 번 측정**해 평균·최댓값. 한 번은 우연(OS 캐시, GC)에 좌우됨.
3. **무작위 ID**로. 앞쪽 ID만 찾으면 선형 탐색도 금방 끝나서 불공평.
4. **첫 실행은 따로**: 처음엔 파일이 OS 캐시에 없어 느림 (warm-up).
5. **데이터 크기를 바꿔가며**: 1만 → 10만 → 100만. 인덱스는 거의 그대로, 선형은 10배씩 느려지는 모양이 나와야 O(log n) vs O(n)이 보입니다. **숫자 하나보다 "늘어나는 모양"이 설득력 있습니다.**

선형 탐색 시간에는 "비교"보다 "파일 읽기 + JSON 파싱"이 대부분입니다. 이걸 짚을 수 있으면 좋습니다.

## 3. API 서버와 Thread Pool (3, 15~17단계)

### 3-1. 프로세스와 스레드

- **프로세스**: 실행 중인 프로그램. 메모리 공간이 각자 따로.
- **스레드**: 프로세스 안의 실행 흐름. **같은 메모리를 공유** → 빠르게 데이터를 나눠 쓰지만, 동시에 같은 데이터를 건드리면 문제가 생김.

우리 서버의 모든 스레드는 같은 B+ 트리, 같은 `next_id`, 같은 파일 핸들을 봅니다.

### 3-2. 요청마다 스레드 vs Thread Pool

**요청마다 새 스레드**
```
요청 → 스레드 생성 → 처리 → 스레드 종료
```
- 스레드 생성·종료 비용이 매번 듦.
- 요청이 1만 개 몰리면 스레드 1만 개 → 메모리 폭증, 문맥 전환(context switch)에 CPU 낭비, 최악엔 서버 다운.

**Thread Pool**
```
              ┌→ 작업 스레드 1 ─┐
요청 → 큐 ───┼→ 작업 스레드 2 ─┼→ 응답
              └→ 작업 스레드 N ─┘
```
- 스레드를 **미리 N개** 만들어 두고 재사용.
- 동시에 처리하는 개수가 **N개로 제한**되어 서버가 버팀.
- 넘치는 요청은 큐에서 대기. 큐도 가득 차면 503으로 거절(과부하 보호, back-pressure).

이 구조가 **생산자-소비자 패턴**입니다. 서버(생산자)는 요청을 큐에 넣고, 작업 스레드(소비자)는 꺼내서 처리합니다.

```python
import queue, threading

class ThreadPool:
    def __init__(self, n, max_queue=100):
        self.tasks = queue.Queue(maxsize=max_queue)
        for i in range(n):
            threading.Thread(target=self._worker, name=f"worker-{i}", daemon=True).start()

    def _worker(self):
        while True:
            func, args = self.tasks.get()      # 큐가 비면 여기서 잠듦 (CPU 안 씀)
            try:
                func(*args)
            finally:
                self.tasks.task_done()

    def submit(self, func, *args):
        self.tasks.put_nowait((func, args))    # 가득 차면 queue.Full → 503
```

`queue.Queue`는 내부에 lock이 있어서 여러 스레드가 동시에 `put`/`get`해도 안전합니다(thread-safe). 우리가 lock을 따로 걸 필요가 없는 부분입니다.

**`http.server`와 연결하기**: `ThreadingHTTPServer`는 요청마다 새 스레드를 만듭니다(요청마다 스레드 방식). 우리는 `HTTPServer`를 상속해서 `process_request`를 오버라이드하고, 그 안에서 `pool.submit(...)`으로 넘기면 "HTTP 해석은 표준 라이브러리, 병렬 처리는 직접 만든 풀" 구조가 됩니다.

### 3-3. 경쟁 상태(race condition): 실제로 깨지는 예

lock 없이 두 스레드가 동시에 `INSERT`하면:

**① ID 중복**
```
스레드 A: id = self.next_id      (100 읽음)
스레드 B: id = self.next_id      (100 읽음)   ← A가 증가시키기 전에 끼어듦
스레드 A: self.next_id = id + 1  (101)
스레드 B: self.next_id = id + 1  (101)
→ 두 레코드 모두 id 100. 하나는 인덱스에서 덮어써져 사라짐
```

**② 파일 위치 꼬임**
```
스레드 A: offset = f.tell()  → 500
스레드 B: offset = f.tell()  → 500
스레드 A: f.write(...)       → 500~530에 기록
스레드 B: f.write(...)       → 530~560에 기록
→ B의 인덱스는 500을 가리키지만 실제 B의 레코드는 530에 있음. 엉뚱한 레코드를 반환
```

**③ B+ 트리 분할 중 읽기**
노드를 반으로 나누는 도중(키는 옮겼는데 부모는 아직 갱신 안 됨)에 다른 스레드가 검색하면, 있는 키를 못 찾을 수 있습니다.

> 이 세 가지는 "읽기 → 계산 → 쓰기"가 **한 덩어리(원자적)로 실행되지 않아서** 생깁니다. lock은 이 덩어리를 한 번에 한 스레드만 실행하게 만듭니다(임계 구역, critical section).

### 3-4. lock 전략

```python
class Engine:
    def __init__(self):
        self._lock = threading.Lock()
    def execute(self, sql):
        with self._lock:          # 예외가 나도 with가 자동으로 풀어줌
            return self._execute(sql)
```

| 전략 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| **전역 lock 하나** (우리 기본) | 한 번에 한 쿼리만 | 단순, 확실, 교착 상태 불가능 | 읽기끼리도 기다림 |
| 읽기/쓰기 lock (RWLock) | 읽기는 여럿 동시, 쓰기는 혼자 | 읽기 많은 부하에서 빠름 | 구현 복잡, 쓰기 굶주림(starvation) 주의 |
| 테이블별 lock | 다른 테이블은 동시에 | 테이블 많으면 효과 | 여러 테이블 쓰면 교착 위험 |
| 실제 DB: 행 단위 lock, MVCC | 버전을 여러 개 두고 읽기는 lock 없이 | 동시성 최고 | 매우 복잡 |

**"전역 lock이면 Thread Pool이 의미가 있나?"** — 꼭 나오는 질문입니다. 답:
> "엔진 실행은 한 번에 하나지만, HTTP 요청 받기·본문 읽기·JSON 해석·응답 보내기는 lock 밖에서 병렬로 일어납니다. 그리고 lock 구조가 맞는지 먼저 확실히 한 뒤, 읽기/쓰기 lock으로 읽기 병렬화를 다음 단계로 둡니다."

**lock을 엔진 안에 두는 이유**: 서버 코드에 두면 CLI나 나중에 추가하는 진입점에서 빠뜨릴 수 있습니다. 데이터를 가진 쪽이 자기 데이터를 보호해야 합니다(캡슐화).

**교착 상태(deadlock)**: 스레드 A는 lock1을 쥐고 lock2를 기다리고, B는 lock2를 쥐고 lock1을 기다리면 둘 다 영원히 멈춤. lock이 하나뿐이면 원천적으로 안 생깁니다. lock을 여러 개 쓰게 되면 **항상 같은 순서로 잡기**가 해결책입니다.

### 3-5. 파이썬 GIL: 알아야 하는 만큼만

**GIL(Global Interpreter Lock)**: CPython은 한 순간에 한 스레드만 파이썬 바이트코드를 실행합니다.

자주 나오는 오해 두 가지:

1. **"GIL이 있으니 lock이 필요 없다"** → 틀림.
   GIL은 바이트코드 *한 개* 단위로만 보장합니다. `self.next_id += 1`은 읽기·더하기·쓰기 여러 바이트코드라 그 사이에 스레드가 바뀔 수 있습니다. 3-3의 문제는 GIL이 있어도 그대로 생깁니다.

2. **"GIL 때문에 스레드는 쓸모없다"** → 반만 맞음.
   CPU만 쓰는 작업(파싱, 트리 탐색)은 동시에 실행되지 않습니다. 하지만 **I/O를 기다리는 동안(네트워크 수신, 파일 읽기)에는 GIL을 놓습니다**. 그래서 웹 서버처럼 I/O가 많은 일에는 스레드가 효과가 있습니다.

> 발표 한 줄: "파이썬은 GIL 때문에 CPU 작업이 진짜 병렬로 돌지는 않지만, 네트워크 I/O를 겹쳐 처리하는 효과가 있고, GIL과 무관하게 공유 데이터에는 lock이 필요합니다."
> (참고: 파이썬 3.13부터 GIL 없는 실험 빌드가 있습니다. 그 환경에서도 우리 lock 설계는 그대로 맞습니다.)

### 3-6. API 설계에서 생각할 것

- **왜 `POST /query` 하나인가**: SQL 자체가 동작을 표현하므로, REST처럼 `/users/1`로 나눌 필요가 없습니다. 실제 DB의 HTTP 인터페이스(ClickHouse, BigQuery 등)도 이런 형태가 많습니다.
- **SQL을 GET 쿼리스트링에 안 넣는 이유**: 길이 제한, 로그에 남음, 인코딩 문제.
- **상태 코드**: 사용자 실수(문법 오류)는 400, 서버 과부하는 503, 우리 코드 버그는 500. 클라이언트가 "다시 시도할지"를 판단할 수 있게 구분합니다.
- **보안 주의(발표 때 언급하면 좋음)**: 이 API는 SQL을 그대로 받으므로 아무나 쓰면 안 됩니다. 실제 서비스라면 인증과 SQL 인젝션을 막는 **파라미터 바인딩**(`WHERE id = ?` + 값 따로 전달)이 필요합니다.

## 6. 더 알아보기 (시간 날 때)

- **실제 DB의 페이지와 버퍼 풀**: 왜 디스크 기반 B+ 트리는 노드 = 페이지인가
- **WAL(Write-Ahead Log)**: 장애 후 복구를 위해 변경을 로그에 먼저 쓰는 방식
- **MVCC**: PostgreSQL이 읽기에 lock을 안 거는 방법
- **LSM 트리**: 쓰기가 많은 DB(RocksDB, Cassandra)가 B+ 트리 대신 쓰는 구조
- **쿼리 옵티마이저**: 인덱스가 있어도 전체 스캔이 더 빠른 경우 (조건에 맞는 행이 대부분일 때)
