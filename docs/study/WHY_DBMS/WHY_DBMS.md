# 왜 DBMS인가

> **한 줄 요약**: 같은 파일을 여러 코드가 각자 직접 열면, 형식을 바꿀 때 깨지고, 많아지면 느려지고, 동시에 쓰면 망가진다. DBMS는 파일을 다루는 일을 한 곳으로 모아 이 셋을 푼다.

## 1. 출발점: 파일 하나를 여러 코드가 직접 연다

쇼핑몰 폴더 하나가 있습니다.

```
shop/
├── orders.csv      ← 주문 데이터
├── order.py        ← 주문 받는 코드
├── report.py       ← 매출 계산하는 코드
└── delivery.py     ← 택배 보내는 코드
```

`orders.csv`는 한 줄에 주문 하나이고, 쉼표로 항목을 나눕니다. 표로 그리면 이렇습니다.

| 주문번호 | 회원 | 상품 | 가격 |
| --- | --- | --- | --- |
| 1 | kim | 키보드 | 50000 |
| 2 | lee | 마우스 | 20000 |

- **열**(column): 항목 하나. 세로줄입니다. 이 파일은 열이 4개(주문번호, 회원, 상품, 가격)입니다.
- **행**(row): 데이터 하나. 가로줄, 즉 파일의 한 줄입니다. 주문이 들어올 때마다 행이 하나 늘어납니다.

```
1,kim,키보드,50000
2,lee,마우스,20000
```

세 `.py` 파일이 **모두 같은 `orders.csv`를 직접 엽니다.**

```python
# order.py: 주문이 오면 한 줄 추가
open("orders.csv", "a").write("3,park,모니터,300000\n")

# report.py: 매출 합계
for line in open("orders.csv"):
    id, user, product, price = line.strip().split(",")
    total += int(price)

# delivery.py: kim에게 보낼 주문 찾기
for line in open("orders.csv"):
    id, user, product, price = line.strip().split(",")
    if user == "kim": ...
```

데이터가 적고 코드가 하나둘일 때는 이걸로 충분합니다. 설치할 것도 없고, 파일을 메모장으로 열어 볼 수도 있습니다.

## 2. 생기는 문제 세 가지

| | 언제 생기나 | 무슨 일이 생기나 |
| --- | --- | --- |
| 문제 1 | 파일에 열을 하나 추가할 때 | 그 파일을 읽는 다른 코드가 멈춘다 |
| 문제 2 | 데이터가 많아졌을 때 | 하나를 찾는데 처음부터 다 읽어서 느리다 |
| 문제 3 | 두 사람이 동시에 쓸 때 | 재고 1개를 두 명에게 판다 |

### 문제 1. 열을 추가하면 다른 코드가 멈춘다

**언제**: 파일 형식을 바꿀 때. 예를 들어 주문에 쿠폰 열을 하나 추가할 때.

| 파일 | 만든 사람 | 하는 일 |
| --- | --- | --- |
| `order.py` | A | 주문을 파일에 씀 |
| `report.py` | B | 파일을 읽어 매출을 계산 |
| `delivery.py` | C | 파일을 읽어 택배를 보냄 |

B와 C의 코드는 "한 줄은 열 4개, 4번째가 가격"이라고 믿고 읽습니다.

```python
id, user, product, price = line.split(",")
```

A가 쿠폰 기능을 만들면서 **자기 코드 `order.py`**를 고칩니다. 이제 `order.py`가 파일에 쓰는 줄은 열이 5개가 됩니다.

```
1,kim,키보드,50000             ← 예전 주문 (열 4개)
2,lee,마우스,20000             ← 예전 주문 (열 4개)
3,park,모니터,WELCOME,300000   ← A가 고친 뒤 들어온 주문 (열 5개)
```

B와 C가 코드를 안 고치면, 3번째 줄에서 멈춥니다.

```
ValueError: too many values to unpack (expected 4)
```

그러니 B와 C도 코드를 고쳐야 합니다. **바로 그게 문제입니다.**

| 어려운 점 | 무슨 일 |
| --- | --- |
| 누가 읽는지 모름 | A는 이 파일을 읽는 코드가 B, C 말고 또 있는지 모릅니다. 1년 전에 누가 만든 스크립트가 있을 수도 있습니다 |
| 같은 날 고쳐야 함 | A가 오늘 배포하면 B, C도 오늘 같이 배포해야 합니다. 하나라도 늦으면 그 사이에 멈춥니다 |
| 읽는 코드가 늘수록 커짐 | 읽는 코드가 10개면, 열 하나 추가할 때마다 10곳을 고쳐야 합니다 |
| 결국 바꾸기를 피함 | 쿠폰 열 하나도 "다 같이 고쳐야 해서" 미루게 됩니다 |

원인은 "열 4개, 4번째가 가격"이라는 약속이 A, B, C의 코드에 **따로** 적혀 있다는 것입니다.

### 문제 2. 데이터가 많으면 느리다

**언제**: 주문이 100만 건쯤 쌓였을 때.

주문번호 987654를 찾는 코드입니다.

```python
for line in open("orders.csv"):              # 1번째 줄부터
    if line.split(",")[0] == "987654": ...   # 하나씩 비교
```

| 주문 수 | 읽어야 하는 줄 |
| --- | --- |
| 100건 | 최대 100줄 |
| 100만 건 | 최대 100만 줄 |

**왜 처음부터 읽어야 하나**: 줄마다 길이가 다릅니다. 회원 이름, 상품명, 가격 자릿수가 주문마다 다르기 때문입니다. 그래서 987654번째 주문이 파일의 몇 바이트째에 있는지 계산할 수 없고, 앞에서부터 한 줄씩 읽으며 확인하는 수밖에 없습니다.

```
orders.csv
1,kim,키보드,50000           ← 읽고 비교: 아님
2,lee,마우스,20000           ← 읽고 비교: 아님
3,park,모니터,300000         ← 읽고 비교: 아님
...                          ← 98만 줄 넘게 계속
987654,kim,의자,89000        ← 여기서 찾음
```

데이터가 10배가 되면 읽을 줄도 10배, 시간도 10배가 됩니다.

### 문제 3. 동시에 쓰면 망가진다

**언제**: 두 사람이 거의 같은 순간에 같은 데이터를 고칠 때.

재고가 1개 남았고(`stock.txt`에 `1`), kim과 lee가 거의 동시에 주문합니다. 주문 하나는 한 번에 끝나지 않고 세 걸음입니다.

```python
n = int(open("stock.txt").read())            # ① 재고 읽기
if n > 0:                                    # ② 살 수 있는지 판단
    open("stock.txt", "w").write(str(n - 1)) # ③ 하나 줄여서 쓰기
```

두 주문이 동시에 들어오면 컴퓨터는 둘을 번갈아 조금씩 실행합니다. 그래서 kim의 ①과 ③ **사이에** lee의 ①이 끼어들 수 있습니다.

| 순서 | kim | lee | `stock.txt` |
| --- | --- | --- | --- |
| 1 | ① 읽음 → 1 | | 1 |
| 2 | | ① 읽음 → **1** | 1 ← kim이 아직 ③을 안 해서 lee도 1을 봄 |
| 3 | ③ 0을 씀 | | 0 |
| 4 | | ③ 0을 씀 | 0 |

**kim도 lee도 샀습니다.** 키보드는 1개였습니다.

**왜 망가지나**: 읽기(①)와 쓰기(③)가 따로따로인 걸음이라, 그 사이에 다른 주문이 끼어들면 둘 다 "아직 1개 남음"을 보게 됩니다. 두 사람이 각자 파일을 직접 열기 때문에, "kim의 ①\~③이 끝날 때까지 lee는 기다려"라고 막아 줄 곳이 없습니다.

(결제·재고·주문 파일 세 개를 고치다가 중간에 꺼지는 문제도 있지만, 과제 필수가 아니라서 [차별화 후보 C](#시연과-발표-자료)로 따로 둡니다.)

### 누가 겪나

- **먼저 겪는 사람은 개발자**입니다. 열 하나 바뀔 때마다 모든 코드를 같이 고쳐야 하고(문제 1), 동시에 쓰는 경우까지 직접 막아야 합니다(문제 3).
- **결국 겪는 사람은 고객**입니다. 화면이 느리고(문제 2), 산 줄 알았던 상품이 취소되고, 돈만 빠집니다(문제 3).

### 공통 원인

> **파일 하나를 여러 코드가 각자 직접 만진다.**

## 3. DBMS 이전의 시도

### 문제마다 하나씩 막아 보면

**문제 1을 막으려고: 파일 읽는 함수를 하나만 만들어 모두 쓰게 한다**

```python
# orders_lib.py: 열 순서는 여기만 앎
def read_orders(): ...
```

열이 바뀌면 이 함수만 고치면 됩니다. 그런데 이 함수를 쓰는 코드를 전부 다시 배포해야 하고, 한 곳이라도 옛 버전을 쓰면 또 멈춥니다. 문제 2, 3은 그대로입니다.

**문제 2를 막으려고: 파일을 주문번호 순으로 정렬해 둔다**

정렬돼 있으면 가운데부터 보고 반씩 버리며 빨리 찾을 수 있습니다. 그런데 주문이 들어올 때마다 100만 줄을 다시 정렬해야 하고, 회원 이름으로 찾으면 다시 처음부터 읽어야 합니다.

**문제 3을 막으려고: 파일 잠금을 건다**

```python
lock("stock.txt")      # "지금 내가 쓴다". 다른 사람은 여기서 기다림
... 읽고, 판단하고, 쓰기 ...
unlock("stock.txt")
```

kim이 끝날 때까지 lee가 기다리니 한 명만 삽니다. 그런데 재고를 다루는 모든 코드가 이 두 줄을 빠짐없이 넣어야 합니다. 한 곳이라도 빼먹으면 다시 2명에게 팝니다.

**정리**: 하나씩 막을수록 "모든 코드가 꼭 지켜야 할 규칙"이 늘어납니다. 사람이 이 규칙을 전부 지키기는 어렵습니다. 그래서 이 규칙들을 **아예 한 곳에 모아, 파일은 그곳만 만지게 합니다.** 그 한 곳이 DBMS입니다.

### 1960년대: 데이터를 한 곳으로 모은 첫 DB

IBM의 IMS(1968년, 아폴로 계획의 로켓 부품 관리에서 출발)와 GE의 IDS 같은 초기 DB가 데이터를 코드 밖의 한 곳으로 모았습니다. 동시에 쓸 때의 순서와 복구도 그곳이 맡았습니다.

하지만 데이터를 꺼내려면 코드가 미리 연결된 길을 직접 따라가야 했습니다.

```
"kim의 주문" 꺼내기:  kim을 찾음 → kim의 첫 주문으로 감 → 다음 주문으로 감 → ...
```

데이터 구조가 바뀌면 길이 바뀌어서 코드를 또 고쳐야 했습니다. 문제 1이 다른 형태로 남은 것입니다.

## 4. DBMS는 어떻게 풀었나

1970년 IBM 연구소의 코드(Codd)가 새 방식을 제안합니다. 데이터는 표로 저장하고, 코드는 SQL로 "무엇이 필요한지"만 말합니다. 그러면 DBMS가 **직접** 파일을 열어 찾고, 쓰고, 결과를 돌려줍니다. 코드는 파일을 만지지 않습니다. 이 방식이 오늘날의 MySQL, PostgreSQL, SQLite로 이어집니다.

```
    order.py    report.py    delivery.py
          \         |         /
           "가격 합 줘", "주문 하나 넣어 줘"   ← SQL로 부탁만 함
                     |
                   DBMS          ← 파일을 여는 건 얘 하나뿐
                     |
                  shop.db
```

같은 폴더를 DBMS로 바꾸면 이렇게 됩니다.

```
shop/
├── shop.db         ← 이 파일은 DBMS만 엶
├── order.py        ← 이제 파일을 직접 열지 않고 DBMS에 SQL로 부탁
├── report.py
└── delivery.py
```

세 문제가 각각 어떻게 풀리는지 봅니다.

### 문제 1 → 열을 이름으로 꺼낸다

B의 `report.py`는 이제 "4번째 열"이 아니라 `price`라는 **이름**으로 달라고 합니다.

```python
# report.py (B)
total = db.execute("SELECT SUM(price) FROM orders")
```

A가 쿠폰 열을 추가합니다. 이것도 파일을 직접 고치지 않고 DBMS에 부탁합니다.

```python
# order.py (A)
db.execute("ALTER TABLE orders ADD COLUMN coupon")
```

DBMS는 "orders 표에는 id, user, product, price, coupon 열이 있다"는 목록을 혼자 들고 있다가, 열이 추가되면 그 목록을 고쳐 둡니다. B가 `price`를 달라고 하면 DBMS가 목록을 보고 가격 열을 찾아 줍니다. 그래서 **B와 C의 코드는 그대로 돌아갑니다.**

| | 쿠폰 열을 추가할 때 고치는 코드 |
| --- | --- |
| 파일 직접 | `order.py` + `report.py` + `delivery.py` + 그 파일을 읽는 모든 코드 (모두 같은 날 배포) |
| DBMS | `order.py`에서 `ALTER TABLE orders ADD COLUMN coupon` 한 줄. **나머지는 안 고침** |

### 문제 2 → 목차(인덱스)로 바로 찾는다

```python
# delivery.py
db.execute("SELECT * FROM orders WHERE id = 987654")
```

DBMS는 "id가 몇 번인 주문은 파일의 어디에 있다"는 목차를 따로 만들어 둡니다.

```
목차(인덱스)                 shop.db
id 1      → 0바이트          ...
id 2      → 31바이트         ...
...
id 987654 → 41,203,550바이트 → 그 위치로 바로 가서 한 줄만 읽음
```

| 주문 수 | 파일 직접 | DBMS (인덱스) |
| --- | --- | --- |
| 100만 건 | 최대 100만 줄 읽음 | 목차를 3\~4번 보고 1줄 읽음 |

### 문제 3 → 한 곳에서 한 명씩 처리한다

kim과 lee의 주문이 모두 DBMS로 갑니다. DBMS는 kim이 끝날 때까지 lee를 기다리게 합니다.

| 순서 | kim | lee | 재고 |
| --- | --- | --- | --- |
| 1 | 읽음 → 1 | 도착. **kim이 끝날 때까지 기다림** | 1 |
| 2 | 0을 씀. 끝 | | 0 |
| 3 | | 읽음 → 0 → 품절 | 0 |

이렇게 기다리게 하는 장치가 **lock**입니다. 파일을 여는 곳이 DBMS 하나뿐이라서, lock도 그 한 곳에만 두면 됩니다.

```python
# DBMS 안쪽 (우리 과제 16단계에서 만드는 모양)
def execute(self, sql):
    with self._lock:      # 먼저 온 kim이 잡음. lee는 여기서 기다림
        ...               # 재고 읽기 → 판단 → 쓰기
```

### 정리

| 문제 | 파일 직접 | DBMS |
| --- | --- | --- |
| 1. 열 하나 바꿀 때마다 모든 코드를 고침 | 열 순서를 A, B, C의 코드가 따로 앎 | 열 목록은 DBMS만 앎. 코드는 이름(`price`)으로 요청 |
| 2. 많아지면 느림 | 처음부터 읽음 | 목차(인덱스)로 바로 감 |
| 3. 동시에 쓰면 망가짐 | 각자 파일을 열어서 끼어듦 | 한 곳에서 lock으로 한 명씩 |

## 5. 우리 과제에서 만드는 것

미니 DBMS는 4절의 세 가지를 가장 작게 직접 만들어 보는 것입니다. 과제 원문의 Phase 1·2·3이 문제 1·2·3과 하나씩 짝이 됩니다. 단계 번호는 [설계](../../DESIGN.md) 3절입니다.

| 과제 원문 | 풀어 보는 문제 | 왜 그런가 | 연결 | 설계 단계 |
| --- | --- | --- | --- | --- |
| Phase 1. SQL 처리기 | 문제 1. 열(항목 하나, 예: 쿠폰)을 추가하면 다른 코드가 멈춤 | 다른 코드가 "4번째 열이 가격"처럼 **순서**로 읽기 때문에, 열이 하나 끼어들면 순서가 밀려서 엉뚱한 값을 읽거나 멈춤 | 코드가 순서로 읽지 않고, SQL로 열 이름을 말함 (예: `WHERE name = '현지'`). 열 목록은 처리기만 앎. 단, 열을 추가하는 기능(`ALTER TABLE`)은 과제 범위가 아니라 만들지 않음 | 1, 4\~9 |
| Phase 2. B+ 트리 인덱스 | 문제 2. 데이터(행. 예: 주문 100만 건)가 많으면 느림 | 파일 안에는 "id 987654는 몇 바이트째"라는 정보가 없고, 줄마다 길이도 달라서 위치를 계산할 수 없음. 그래서 1번째 줄부터 읽고 비교하기를 줄 수만큼 반복함 → 100건이면 100번, 100만 건이면 100만 번 | `INSERT`할 때 DBMS가 id를 1, 2, 3… 자동으로 붙이고, "id → 파일 위치"를 목차(B+ 트리)에 적어 둠. 찾을 때는 목차를 보고 그 한 줄만 읽음 (예: "id 987654 → 41,203,550바이트째") | 2, 10\~14 |
| Phase 3. API 서버 | 문제 3. 동시에(두 요청이 같은 순간에) 쓰면 망가짐 | `INSERT` 하나는 ① 다음 id 읽기 → ② 파일에 쓰기 → ③ 다음 id 올리기, 세 걸음임. 스레드 두 개가 동시에 돌면 컴퓨터가 번갈아 실행해서, A의 ①과 ③ 사이에 B가 끼어들 수 있음. 그러면 A와 B가 둘 다 id 4를 읽어서 id 4가 두 개 생김 | 서버는 요청 여러 개를 스레드 여러 개로 동시에 처리함 (Thread Pool). 그래서 세 걸음을 lock으로 묶어 한 스레드가 ①\~③을 끝낼 때까지 다른 스레드는 기다리게 함 → 먼저 온 쪽이 id 4, 다음 쪽이 id 5 | 3, 15\~17 |

### 문제 1 → SQL 처리기 (1, 4\~9단계)

```python
engine.execute("SELECT name FROM users WHERE id = 3")
```

SQL 문장을 읽어서(토크나이저, 파서), `schema.json`에 적힌 열 목록을 보고 파일에서 꺼냅니다(실행기). 열 순서는 처리기만 압니다.

### 문제 2 → B+ 트리 인덱스 (2, 10\~14단계)

```python
offset = index.search(3)                   # 목차에서 위치를 찾고
row = storage.read_at("users", offset)     # 그 줄만 읽음
```

처음엔 파이썬 `dict`로 목차를 만들고(2단계), 나중에 B+ 트리로 바꿉니다(10\~12단계). 마지막에 100만 건에서 목차로 찾기와 처음부터 찾기의 시간을 비교합니다(13\~14단계).

### 문제 3 → 서버 + lock (3, 15\~17단계)

```python
class Engine:
    def execute(self, sql):
        with self._lock:          # 한 번에 한 문장만
            ...
```

다른 코드가 HTTP로 SQL을 보내면 서버가 받아서 `engine.execute`를 부릅니다. 요청이 동시에 와도 lock 때문에 한 문장씩 처리됩니다.

트랜잭션(여러 변경을 한 묶음으로)은 과제 필수가 아니라서, 시간이 남으면 차별화로 해 볼 수 있습니다. SQL 한 줄이 처리되는 과정은 [전체 그림](../OVERVIEW.md)에 코드로 더 자세히 있습니다.
