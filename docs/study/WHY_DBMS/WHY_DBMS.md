# 왜 DBMS인가 (자세한 버전)

> **한 줄 요약**
> 파일로 데이터를 관리하면 **파일 형식, 찾는 방법, 동시에 쓸 때의 규칙이 프로그램마다 따로 코드 안에 들어갑니다.** 그래서 데이터를 쓰는 프로그램이 늘고 데이터가 커지면, 같은 데이터가 서로 어긋나고, 형식 하나를 바꾸면 다른 프로그램이 깨지고, 동시에 쓰거나 중간에 꺼지면 데이터가 망가집니다.
>
> DBMS는 데이터를 다루는 일을 **프로그램 밖의 전담 프로그램 하나로 빼냅니다.** 다른 프로그램은 "무엇이 필요한지"만 말하고, 저장, 찾기, 보호는 DBMS가 책임집니다.

이 문서는 "DBMS를 어떻게 쓰나"보다 **"DBMS가 무슨 문제를 풀려고 나왔나"**를 설명합니다. 짧은 버전은 [왜 DBMS인가](./WHY_DBMS_GUIDE.md)입니다.

## 한눈에 보는 흐름

```
1. 출발점   파일은 단순하고 좋은 도구다. 프로그램 하나, 데이터가 적으면 이걸로 충분하다.
               ↓
2. 상황     그런데 같은 데이터를 쓰는 프로그램이 늘고, 데이터가 커진다.
               ↓
3. 문제     그러자 여섯 가지 문제가 생긴다.
               ↓
4. 원인     여섯 가지의 원인은 하나다: 데이터를 다루는 방법이 프로그램마다 따로 코드에 들어 있다.
               ↓
5. 해결     데이터를 다루는 일을 프로그램 밖 전담 프로그램 하나로 뺀다 → DBMS
```

두 가지를 먼저 구분해 둡니다.

- **상황(2절)**: 문제가 **터지는 때**입니다. 원인은 아닙니다. 똑같은 코드라도 프로그램 하나가 작은 파일을 쓸 때는 아무 문제가 없습니다.
- **원인(4절)**: 겉으로 보이는 여섯 가지 문제를 **하나로 묶는 진짜 이유**입니다. 문제를 하나씩 막는 대신 원인을 고쳐야 여섯 개가 한 번에 풀립니다.

예시는 **"정글마켓"**이라는 쇼핑몰 하나로 끝까지 따라갑니다.

## 1. 출발점: 파일은 좋은 도구다

막 문을 연 정글마켓에는 개발자 한 명과 주문 프로그램 하나가 있습니다. 주문이 들어오면 **파일 끝에 한 줄을 추가**하고, 주문 목록이 필요하면 **파일을 처음부터 읽습니다.**

```python
def add_order(order_id, user, product, price):
    with open("orders.csv", "a") as f:                   # "a": 파일 끝에 덧붙이기
        f.write(f"{order_id},{user},{product},{price}\n")

def find_orders(user):
    result = []
    for line in open("orders.csv"):                      # 처음부터 끝까지 한 줄씩 읽으며
        order_id, user_, product, price = line.strip().split(",")   # 쉼표로 4칸으로 나누고
        if user_ == user:                                # 조건에 맞는 줄만 고름
            result.append((product, int(price)))
    return result
```

`orders.csv`는 이렇게 생겼습니다. 한 줄이 주문 하나이고, 쉼표로 `주문번호, 회원, 상품, 가격` 네 칸을 나눕니다.

```
1,kim,키보드,50000
2,lee,마우스,20000
3,kim,모니터,300000
```

- 설치할 것도 배울 것도 없어서 **가장 단순합니다.**
- 메모장으로 열어 **눈으로 확인할 수 있습니다.**
- 주문이 하루 수십 건이면 처음부터 읽어도 **충분히 빠릅니다.**

**프로그램 하나가 작은 파일을 쓴다면 여기서 끝입니다. DBMS는 필요 없습니다.**

---

## 2. 상황: 함께 쓰는 프로그램이 늘고, 데이터가 커진다

정글마켓이 커지면서 세 가지가 함께 바뀝니다.

| 변화 | 구체적으로 |
| --- | --- |
| 프로그램이 늘어남 | 주문 말고도 회원, 배송, 정산, 마케팅 프로그램이 생기고, 각 팀이 따로 만듦 |
| 데이터가 커짐 | 주문이 하루 수십 건에서 쌓이고 쌓여 100만 건이 됨 |
| 동시에 씀 | 세일 날에는 같은 순간에 수백 명이 주문하고, 관리자도 동시에 재고를 고침 |

그래서 프로그램과 파일이 이렇게 얽힙니다.

```
회원 프로그램  ──→ members.csv  (회원 이름, 주소)
주문 프로그램  ──→ orders.csv   (주문)  ←── 정산 프로그램이 읽음
               └→ stock.txt    (재고)  ←── 관리자 프로그램도 고침
배송 프로그램  ──→ shipping.csv (배송지 주소)  ←── 주문 파일도 읽음
마케팅 담당    ──→ orders.csv를 엑셀로 열어 직접 계산
```

각 팀은 **자기 프로그램에 필요한 파일을 직접 만들고, 다른 팀의 파일은 그 형식에 맞춰 읽습니다.** 코드는 1절과 같은 방식 그대로입니다. 쓰는 프로그램과 데이터만 늘었을 뿐인데, 이제부터 문제가 생깁니다.

## 3. 문제: 여섯 장면

### 장면 ① 주소를 바꿨는데 택배는 옛날 집으로 간다

```
[처음]   kim의 주소: 서울시 강남구
         members.csv  : kim,서울시 강남구
         shipping.csv : kim,서울시 강남구     ← 배송팀이 편하게 쓰려고 따로 복사해 둔 주소

[이사]   kim이 마이페이지에서 주소를 송파구로 바꿈
         → 회원 프로그램이 members.csv만 고침
         shipping.csv : 여전히 서울시 강남구

[주문]   kim이 키보드를 주문
         → 배송 프로그램은 shipping.csv를 봄 → 옛날 집(강남구)으로 발송
```

- **왜?** 같은 데이터(주소)가 파일 두 개에 **복사되어** 있습니다. 회원 프로그램은 배송팀 파일이 있다는 것조차 모릅니다.
- **고객이 겪는 일**: "주소 바꿨는데요?" → 다시 보내는 비용, 분실

### 장면 ② 칸 하나 추가했더니 다른 프로그램들이 깨진다

주문팀이 쿠폰 기능을 만들면서 `orders.csv`의 가격 앞에 **쿠폰 칸**을 끼워 넣습니다.

```
바꾸기 전:  1,kim,키보드,50000             (주문번호, 회원, 상품, 가격)
바꾼 뒤:    1,kim,키보드,WELCOME10,50000   (주문번호, 회원, 상품, 쿠폰, 가격)
```

이 파일을 읽던 다른 프로그램들은 이렇게 됩니다.

```python
# 정산 프로그램 (정산팀이 1년 전에 작성): "칸이 4개"라고 정해 두고 읽음
order_id, user, product, price = line.strip().split(",")
# → ValueError: too many values to unpack (expected 4)
#   칸이 5개가 돼서, 변수 4개에 나눠 담지 못하고 멈춤

# 마케팅 스크립트: "4번째 칸(번호 3)이 가격"이라고 알고 읽음
price = int(line.split(",")[3])
# → int("WELCOME10")에서 오류.
#   쿠폰 값이 숫자였다면 오류도 없이 쿠폰 값을 매출로 더함 (더 위험함)
```

상품 이름에 쉼표가 들어가도 마찬가지입니다. `키보드, 무선`이라는 상품이 생기면, 모든 프로그램이 칸을 하나 더 세게 됩니다.

- **왜?** "몇 번째 칸이 가격인지" 같은 **파일 형식에 대한 지식이 프로그램마다 코드에 박혀** 있습니다.
- **개발자가 겪는 일**: 칸 하나를 추가하려면 그 파일을 읽는 프로그램을 모두 찾아 동시에 고쳐야 합니다. 그런데 누가 그 파일을 읽는지 다 아는 사람이 없습니다.

### 장면 ③ 질문 하나에 프로그램 하나

마케팅팀이 묻습니다. **"지난달 서울에 사는 30대가 가장 많이 산 상품 10개는?"**

```python
# 개발자가 이틀 걸려 작성
members = {}
for line in open("members.csv"):           # 1. 회원 파일에서 서울에 사는 30대를 찾고
    ...
counts = {}
for line in open("orders.csv"):            # 2. 주문 파일에서 그 회원들의 주문을 상품별로 세고
    ...
top10 = sorted(counts.items(), ...)[:10]   # 3. 많은 순으로 정렬해서 10개
```

다음 주에 질문이 바뀝니다. "부산 20대는?", "카테고리별로는?" → **또 새 코드**를 짜야 합니다.

- **왜?** 데이터를 **어떻게 찾을지(반복문, 조건, 두 파일 합치기)**를 질문마다 사람이 직접 짜야 합니다.
- **회사가 겪는 일**: 질문할 때마다 개발자를 기다립니다. 데이터는 있는데 쓸 수가 없습니다.

### 장면 ④ 주문이 100만 건이 되자 찾기가 느려진다

```
[하루 수십 건일 때]  kim의 주문 찾기 → 파일 수백 줄 읽기 → 순식간

[100만 건일 때]     주문번호 987654 찾기 → 첫 줄부터 읽으며 비교
                    → 거의 100만 줄을 읽고, 100만 번 쉼표로 나누고, 100만 번 비교
                    → 조회 한 번에 수백 ms. 1초에 수백 명이 조회하면 서버가 버티지 못함
```

- **왜?** 파일은 **처음부터 순서대로 읽는 방법밖에 모릅니다.** 이렇게 하나씩 비교하며 찾는 것을 **선형 탐색**이라고 하고, 데이터가 N개면 최대 N번 비교합니다(**O(N)**: 데이터가 10배가 되면 시간도 10배).
- 파일을 주문번호 순으로 정렬해 두면 가운데부터 보고 절반씩 버리며 찾을 수 있습니다(**이진 탐색**). 하지만 주문이 들어올 때마다 100만 줄을 다시 정렬할 수는 없고, "회원 이름으로 찾기"에는 또 다른 순서의 정렬이 필요합니다.

### 장면 ⑤ 세일 날, 남은 1개를 두 명에게 판다

```
[한정판 키보드 재고 1개. stock.txt에 "1"이 적혀 있음]

kim의 주문 → 주문 프로그램 1: stock.txt를 읽음 → 1 → "살 수 있음"
lee의 주문 → 주문 프로그램 2: stock.txt를 읽음 → 1 → "살 수 있음"   ← 1이 0으로 바뀌기 전에 읽음
주문 프로그램 1: stock.txt에 0을 쓰고, 주문 기록
주문 프로그램 2: stock.txt에 0을 쓰고, 주문 기록

→ 1개를 2명에게 팔아 버림
```

같은 파일에 여러 프로그램이 동시에 한 줄씩 추가하면, 운이 나쁘면 **두 줄이 섞인 깨진 줄**이 생기기도 합니다.

```
kim,키보드,50lee,마우스,20000
000
```

- **왜?** "읽기 → 판단하기 → 쓰기" 사이에 다른 프로그램이 끼어들 수 있는데, **순서를 정해 줄 곳이 없습니다.**
- 이번에는 사본이 아니라 **원본 데이터 자체**가 틀어집니다. 나중에 고칠 근거가 남지 않습니다.

### 장면 ⑥ 저장하다 꺼지면 돈만 빠진다

주문 하나를 처리하려면 파일 세 개를 차례로 고쳐야 합니다.

```
주문 처리
  1. payments.csv에 결제 기록 추가     ✅ 완료
  2. stock.txt의 재고를 1 줄이기        ← 이 순간 서버 전원이 나감
  3. orders.csv에 주문 추가             ❌ 실행 안 됨

→ 고객 돈은 결제됐는데 주문은 없음
→ stock.txt는 쓰던 도중이라 내용이 반만 남아 읽을 수조차 없음
```

- **왜?** 여러 파일의 변경을 **"전부 되거나, 전부 안 되거나"로 묶어 주는 장치**가 없습니다.
- **고객이 겪는 일**: "돈은 나갔는데 주문 내역이 없어요" → 가장 심각한 종류의 문의

### 누가 겪고, 어떻게 드러나나

| 장면 | 누가 겪나 | 어떻게 드러나나 |
| --- | --- | --- |
| ① 주소가 어긋남 | 고객 | 엉뚱한 곳으로 배송 |
| ② 형식이 바뀜 | 개발자 | 칸 하나 바꿀 때마다 다른 프로그램이 깨져서, 바꾸기가 무서워짐 |
| ③ 질문마다 코드 | 회사 (기획, 마케팅) | 데이터가 있어도 답을 얻는 데 며칠 |
| ④ 느린 찾기 | 고객, 운영자 | 데이터가 늘수록 화면이 느려지고 서버가 버티지 못함 |
| ⑤ 동시에 쓰기 | 고객, 회사 | 초과 판매, 깨진 줄 |
| ⑥ 중간에 꺼짐 | 고객, 회사 | 돈과 주문이 안 맞음, 파일 손상 |

묶어 보면 세 종류입니다.

- ①②: 데이터가 서로 어긋나거나 프로그램이 깨지는 문제
- ③④: 데이터를 꺼내기 어렵고 느린 문제
- ⑤⑥: 데이터 자체가 망가지는 문제

## 4. 원인: 여섯 장면의 원인은 하나다

### 4-1. "데이터를 다루는 방법"이 어디에 있나

정산 프로그램의 코드를 다시 봅니다.

```python
for line in open("orders.csv"):                              # ← 위치: 데이터가 orders.csv에 있다
    order_id, user, product, price = line.strip().split(",") # ← 형식: 쉼표로 나눈 4칸, 4번째가 가격
    if user == "kim":                                        # ← 찾는 방법: 처음부터 하나씩 비교
        total += int(price)
# 동시에 누가 이 파일을 쓰고 있으면?   ← 아무 대비 없음
# 읽다가 꺼지면?                      ← 아무 대비 없음
```

이 몇 줄 안에 **데이터를 다루는 방법 전부**(위치, 형식, 찾는 방법, 보호)가 들어 있습니다. 그리고 회원, 주문, 배송, 정산, 마케팅 프로그램이 **각자 이것을 따로** 들고 있습니다.

```
회원 프로그램 안   : members.csv 형식 + 찾는 방법
주문 프로그램 안   : orders.csv 형식 + stock.txt 형식 + 찾는 방법
배송 프로그램 안   : shipping.csv 형식 + orders.csv 형식 + 찾는 방법
정산 프로그램 안   : orders.csv 형식 + 찾는 방법
마케팅 스크립트 안 : orders.csv 형식 + members.csv 형식 + 찾는 방법
```

`orders.csv`의 형식이 네 군데에 따로 적혀 있습니다. 주문팀이 형식을 바꾸면, 나머지 세 군데는 옛 형식을 그대로 믿고 읽습니다. 이게 장면 ②입니다.

### 4-2. 여섯 장면을 다시 보면

| 장면 | 실제로 일어난 일 |
| --- | --- |
| ① 주소가 어긋남 | 프로그램마다 **자기 파일**을 가져서 같은 데이터가 여러 벌 생김 |
| ② 형식이 바뀜 | **파일 형식에 대한 지식**이 각 프로그램 코드에 있음 |
| ③ 질문마다 코드 | **찾는 방법**이 각 프로그램 코드에 있음 |
| ④ 느린 찾기 | 빨리 찾는 구조(색인, 인덱스)를 누가 만들어도 **모든 프로그램이 함께 쓸 곳**이 없음 |
| ⑤ 동시에 쓰기 | **순서를 정하는 규칙**을 각 프로그램이 알아서 해야 함. 결국 아무도 안 함 |
| ⑥ 중간에 꺼짐 | **여러 변경을 하나로 묶는 장치**를 각 프로그램이 알아서 해야 함. 결국 아무도 안 함 |

전부 같은 이야기입니다.

> **원인: 데이터를 다루는 방법(형식, 찾기, 보호)이 프로그램마다 따로 코드 안에 들어 있다.**

### 4-3. "어떻게" 대신 "무엇을"

원인을 풀면, 프로그램이 데이터를 요청하는 방식이 바뀝니다.

| | 파일 방식: 어떻게 찾을지 직접 | DBMS 방식: 무엇이 필요한지만 |
| --- | --- | --- |
| 프로그램이 하는 말 | "이 파일을 열어서, 쉼표로 나누고, 2번째 칸이 kim인 줄의 4번째 칸을 더해" | "kim의 주문 금액 합계를 줘" |
| 코드 | 반복문, 조건문, 칸 번호 | `SELECT SUM(price) FROM orders WHERE user = 'kim'` |
| 파일 형식이 바뀌면 | 코드를 고쳐야 함 | 그대로 |
| 인덱스가 새로 생기면 | 코드를 고쳐야 빨라짐 | 코드는 그대로인데 빨라짐 |

어떻게 찾을지는 DBMS가 고릅니다. 이렇게 **데이터를 저장하는 방식이 바뀌어도 프로그램을 고치지 않아도 되는 성질**을 **데이터 독립성**이라고 합니다.

### 4-4. 문제를 하나씩 막으면 왜 안 되나

| 시도 | 막는 것 | 남는 문제 |
| --- | --- | --- |
| 파일 읽는 코드를 공용 라이브러리로 만들어 모두 쓰게 함 | ② 형식 지식이 한 곳에 모임 | 형식이 바뀌면 모든 프로그램을 다시 배포해야 함. 옛 버전을 쓰는 프로그램이 남음. ④⑤⑥은 그대로 |
| 파일 잠금 (`flock`: 운영체제에 "이 파일은 지금 내가 쓴다"고 알리는 기능) | ⑤ 동시에 쓰기 | 파일 전체를 잠가서 모두가 줄을 섬. **한 프로그램이라도 잠금을 빼먹으면** 무너짐. ⑥은 그대로 |
| 파일을 주문번호 순으로 정렬해 저장 | ④ 이진 탐색 가능 | 추가할 때마다 전체를 다시 정렬. 다른 칸(이름)으로 찾을 땐 여전히 느림 |
| 매일 밤 백업 | ⑥ 일부 복구 | 백업 이후 데이터는 잃음. "결제는 됐는데 주문이 없는" 반쪽 상태는 그대로 |
| "복사하지 말고 한 파일만 쓰자"는 규칙을 정함 | ① 중복 | 문서로 정한 규칙은 언젠가 누군가 어김. 한 파일에 모두 몰리면 ⑤가 더 심해짐 |

이렇게 하나씩 막다 보면, 결국 **"모든 프로그램이 지켜야 하는 공용 코드와 규칙"**이 점점 커집니다. 그걸 아예 **독립된 프로그램 하나로 떼어 낸 것**이 DBMS입니다.

## 5. 해결: 데이터를 다루는 일을 프로그램 밖으로 뺀다

**다른 프로그램은 무엇이 필요한지만 말하고, 데이터를 다루는 일은 전담 프로그램 한 곳이 맡습니다.**

```
회원 프로그램  ─┐
주문 프로그램  ─┤
배송 프로그램  ─┼─ SQL로 "무엇이 필요한지" ─→ [ DBMS ]
정산 프로그램  ─┤                             ├─ 스키마: 어떤 테이블에 어떤 칸이 어떤 타입으로 있는지
마케팅 담당    ─┘                             ├─ SQL 처리: 어떻게 찾을지 스스로 결정
                                              ├─ 인덱스: 빨리 찾는 색인
                                              ├─ 동시성 제어: 동시에 써도 순서대로
                                              └─ 복구: 꺼져도 전부 되거나 전부 안 되거나
                                                       ↓
                                                   디스크의 파일
```

**DBMS도 결국 파일에 저장합니다.** 달라진 것은 그 파일을 **DBMS만 직접 만지고**, 다른 프로그램은 모두 DBMS에게 부탁한다는 점입니다.

여섯 장면이 이렇게 바뀝니다.

| 장면 | DBMS를 두면 |
| --- | --- |
| ① 주소 | 주소는 `members` 테이블에 한 번만 저장. 배송은 주문과 회원을 함께 조회(`JOIN`: 두 테이블을 공통 칸, 여기서는 회원 이름으로 이어 붙여 한 번에 조회하는 것) → 주소를 고치면 모두가 새 주소를 봄 |
| ② 형식 | 칸을 번호가 아니라 이름(`price`)으로 요청. 칸을 추가해도 기존 SQL은 그대로 동작 |
| ③ 질문 | 마케팅이 SQL 한 문장으로 직접 질문. 질문이 바뀌면 문장만 바꿈 |
| ④ 찾기 | DBMS가 인덱스(B+ 트리)를 관리. 100만 건이어도 몇 번만 비교해서 찾음 |
| ⑤ 동시성 | 모든 요청이 DBMS 한 곳을 거치므로, DBMS가 lock으로 순서를 정함 → 재고가 1개면 한 명만 삼 |
| ⑥ 장애 | 여러 변경을 **트랜잭션** 하나로 묶음 → 중간에 꺼지면 시작 전 상태로 되돌림 |

### 전담하는 곳을 어디에 두나

| 후보 | 결과 |
| --- | --- |
| 각 프로그램 안 (공용 라이브러리) | 4-4의 첫 줄과 같음. 프로그램마다 라이브러리 버전이 달라지고, 동시성과 복구는 여전히 각자 |
| 공유 폴더의 파일 + 규칙 문서 | 규칙을 사람이 지켜야 함. 한 명이 어기면 끝 |
| **데이터만 전담하는 별도 프로그램** | 파일은 이 프로그램만 만짐 → 형식, 색인, 순서, 복구를 한 곳에서 책임짐 → **DBMS** |

## 6. DBMS 이전의 시도들

| 시기 | 시도 | 방식 | 한계 |
| --- | --- | --- | --- |
| 1950~60년대 | 파일 시스템 | 프로그램마다 자기 파일 (처음엔 자기 테이프, 나중엔 디스크) | 3절의 여섯 장면 그대로 |
| 1960년대 | 색인 순차 파일 (IBM의 ISAM 등) | 정렬된 파일에 색인을 붙여 키로 빨리 찾음 | ④를 일부 풀었음. 하지만 색인이 고정돼 있어서 새 데이터가 쌓이면 느려지고, 주기적으로 파일 전체를 다시 정리해야 함. 형식과 찾는 방법은 여전히 프로그램 안에 있음 |
| 1960년대 초~ | **네트워크형 DB** (GE의 IDS, 찰스 바크먼이 만듦) → 1969~1971년 CODASYL이라는 단체가 표준으로 정리 | 데이터끼리 포인터(다른 데이터의 위치)로 연결하고, 프로그램이 그 연결을 따라감 | 데이터는 프로그램 밖으로 뺐지만, **찾아가는 길**은 프로그램이 알아야 함 |
| 1966~1968년 | **계층형 DB** (IBM IMS. 아폴로 계획의 새턴 V 로켓 부품 목록을 관리하려고 1966년 개발 시작, 1968년 설치, 1969년 IMS로 이름을 바꿈) | 데이터를 부모-자식 나무 모양으로 DBMS가 관리 | 같은 한계. 미리 정한 나무 모양대로만 빨리 찾을 수 있고, 구조를 바꾸면 프로그램을 고쳐야 함 |

계층형, 네트워크형 DB 덕분에 **공유, 동시성, 복구**는 상당 부분 DBMS가 맡게 되었습니다. 하지만 데이터를 꺼내는 방식은 이랬습니다.

```
[네트워크형 DB에서 "kim의 주문 금액 합계" 구하기]
1. 고객 데이터 중에서 kim을 찾는다
2. kim에 연결된 "첫 번째 주문"으로 간다
3. 금액을 더하고, 연결된 "다음 주문"으로 간다
4. 마지막 주문까지 3을 반복한다
```

- 프로그램이 **데이터 사이의 연결을 직접 따라가는** 방식이라 "내비게이션 방식"이라고 부릅니다. 바크먼이 1973년 튜링상 강연 제목을 "내비게이터로서의 프로그래머(The Programmer as Navigator)"로 붙인 데서 퍼진 말입니다.
- 데이터 구조가 바뀌면(예: 주문을 고객 아래가 아니라 상품 아래에 연결) 따라갈 길이 바뀌어서 **프로그램을 고쳐야** 합니다. 장면 ②가 모양만 바꿔 남은 것입니다.
- 미리 연결해 두지 않은 질문(장면 ③)은 여전히 어렵습니다.

정리하면 이 시기는 **"데이터는 프로그램 밖으로 뺐지만, 찾아가는 길은 여전히 프로그램이 들고 있던"** 단계입니다.

## 7. 관계형 DBMS (1970년~): 원하는 것만 말하면 길은 DBMS가 찾는다

1970년 6월, IBM 샌호세 연구소의 에드거 F. 코드(Codd)가 논문 "A Relational Model of Data for Large Shared Data Banks"로 **관계형 모델**을 발표합니다. 논문은 "큰 데이터를 쓰는 사람은 데이터가 기계 안에서 어떻게 구성되어 있는지 몰라도 되어야 한다"는 취지로 시작합니다. 핵심은 두 가지입니다.

1. 데이터를 **표(테이블)**로만 표현합니다. 포인터나 따라갈 길이 없고, 행(가로줄)과 열(세로줄, 칸)만 있습니다.
2. 프로그램은 **원하는 결과의 조건만** 말하고, 어떻게 찾을지는 DBMS가 정합니다.

코드는 당시 시스템에 남아 있던 문제를 세 가지 "의존"으로 짚었습니다. 이 문서의 장면과 그대로 이어집니다.

| 코드가 짚은 의존 | 뜻 | 이 문서의 장면 |
| --- | --- | --- |
| 순서 의존 | 프로그램이 "데이터가 이 순서로 저장되어 있다"고 가정함 | ② 형식이 바뀌면 깨짐 |
| 인덱스 의존 | 프로그램이 특정 색인을 이름으로 직접 써서, 색인을 없애면 프로그램이 깨짐 | ④ 색인을 마음대로 넣고 뺄 수 없음 |
| 접근 경로 의존 | 프로그램이 나무 모양, 연결 구조의 길을 따라감 | 6절의 내비게이션 방식 |

이 아이디어가 IBM의 System R, 버클리의 Ingres 같은 연구를 거쳐 **SQL**과 Oracle, DB2, 이후 MySQL, PostgreSQL로 이어집니다.

### 7-1. 파일, 초기 DBMS, 관계형 DBMS 비교

| 구분 | 구체적인 요구 | 파일 | 계층형·네트워크형 DB | 관계형 DBMS |
| --- | --- | --- | --- | --- |
| 공유 | 모든 프로그램이 같은 데이터 한 벌을 봄 | ❌ 프로그램마다 파일 | ✅ | ✅ |
| 독립성 | 저장 형식이 바뀌어도 프로그램은 그대로 | ❌ | △ 구조가 바뀌면 길도 바뀜 | ✅ 이름으로 요청 |
| 질문 | 새 질문을 코드 없이 | ❌ 질문마다 프로그램 | ❌ 길을 따라가는 코드 | ✅ SQL 한 문장 |
| 성능 | 큰 데이터에서 빨리 찾기 | ❌ 처음부터 읽기 | ✅ 포인터로 | ✅ 인덱스. 어떤 방법으로 찾을지 DBMS가 고름 |
| 동시성 | 동시에 써도 깨지지 않음 | ❌ | ✅ | ✅ lock, MVCC |
| 복구 | 중간에 꺼져도 반쪽 상태가 없음 | ❌ | ✅ | ✅ 트랜잭션, 로그 |
| 무결성 | 잘못된 값 막기 (가격은 숫자, 주문에는 회원이 꼭 있어야 함) | ❌ 프로그램마다 검사 | △ | ✅ 타입, 제약 조건 |
| 권한 | 누가 무엇을 볼 수 있는지 | ❌ 파일 권한 정도 | ✅ | ✅ 테이블·칸 단위 |

- **파일**: 단순하지만, 모든 걸 프로그램이 알아서 해야 함
- **계층형·네트워크형**: 보호는 DBMS가 하지만, 길은 프로그램이 앎
- **관계형**: 보호도, 길 찾기도 DBMS가 함

### 7-2. SQL이 왜 중요한가

SQL은 "어떻게 찾을지"가 아니라 "무엇을 원하는지"를 적는 언어입니다. 이런 방식을 **선언형**이라고 합니다.

| 하고 싶은 일 | 파일로 하면 | SQL로 하면 |
| --- | --- | --- |
| kim의 주문 목록 | 파일 열기 → 줄마다 쉼표로 나누기 → 2번째 칸 비교 | `SELECT * FROM orders WHERE user = 'kim'` |
| 주문번호 987654 | 100만 줄을 처음부터 비교 | `SELECT * FROM orders WHERE id = 987654` |
| 서울 30대의 인기 상품 10개 | 반복문 세 개, 이틀 | `SELECT product, COUNT(*) FROM orders JOIN members ... GROUP BY product ORDER BY 2 DESC LIMIT 10` |
| 주소 바꾸기 | 주소가 들어 있는 모든 파일을 찾아 고치기 | `UPDATE members SET address = '...' WHERE name = 'kim'` |

두 가지 효과가 있습니다.

1. **프로그램이 형식을 몰라도 됩니다.** 칸 번호 대신 이름으로 말하니 장면 ②가 사라집니다.
2. **DBMS가 가장 빠른 방법을 고릅니다.** 같은 `WHERE id = 987654`라도 `id`에 인덱스가 있으면 인덱스로, 없으면 처음부터 읽습니다. **그래서 인덱스를 추가해도 SQL은 한 글자도 안 바뀌고 빨라집니다.** 이렇게 "어떤 방법으로 찾을지 고르는 일"을 하는 DBMS의 부분이 **쿼리 플래너**(또는 옵티마이저)입니다.

### 7-3. 트랜잭션: 동시성과 장애를 한 번에

장면 ⑤⑥은 **트랜잭션**으로 풉니다. 여러 작업을 하나로 묶어 "전부 되거나, 전부 안 되거나"로 만드는 것입니다.

```sql
BEGIN;                                                                  -- 여기서부터 한 묶음
UPDATE stock SET count = count - 1 WHERE product = '키보드' AND count > 0;
INSERT INTO payments ...;
INSERT INTO orders ...;
COMMIT;                                                                 -- 여기까지 와야 셋 다 반영. 그 전에 꺼지면 셋 다 없던 일
```

트랜잭션이 지키는 네 가지 성질을 앞 글자를 따서 **ACID**라고 합니다.

| 성질 | 뜻 | 막는 장면 | DBMS가 하는 일 (대표적인 방법) |
| --- | --- | --- | --- |
| **A**tomicity 원자성 | 전부 되거나, 전부 안 되거나 | ⑥ 돈만 빠짐 | 바꾸기 전 상태를 기록해 두고, 실패하면 되돌림 |
| **C**onsistency 일관성 | "재고 ≥ 0" 같은 규칙이 항상 지켜짐 | ⑤ 초과 판매 | 타입, 제약 조건 검사 |
| **I**solation 격리성 | 동시에 실행해도, 하나씩 차례로 실행한 것과 같은 결과 | ⑤ 끼어들기, 섞인 줄 | lock, MVCC |
| **D**urability 지속성 | `COMMIT`된 것은 꺼져도 남음 | ⑥ 파일 손상 | 변경을 로그에 먼저 쓰고(WAL) 디스크에 확실히 기록 |

표에 나온 말:

- **MVCC** (Multi-Version Concurrency Control): 데이터를 고칠 때 옛 버전을 바로 지우지 않고 잠시 남겨 둡니다. 읽는 쪽은 옛 버전을 읽으면 되니까, 누가 쓰는 중이어도 기다리지 않고 읽을 수 있습니다.
- **WAL** (Write-Ahead Log): 실제 데이터를 고치기 전에, "무엇을 바꿀지"를 로그 파일에 먼저 씁니다. 중간에 꺼지면 다시 켤 때 로그를 보고 마저 하거나 되돌립니다.

원칙은 **"여러 변경을 프로그램이 따로따로 하지 말고, 트랜잭션 하나로 DBMS에 맡긴다"**입니다.

## 8. 그럼 우리는 무엇을 만드나?

### 8-1. DBMS의 부분과 우리 Phase

DBMS 안은 대략 이런 부분으로 나뉩니다. 우리 과제의 세 Phase가 각 부분에 대응합니다.

```
[연결]       다른 프로그램의 요청을 받고, 여러 요청을 동시에 처리   ← Phase 3: API 서버, Thread Pool
[SQL 처리]   SQL 해석 → 어떻게 실행할지 정함 → 실행                ← Phase 1: 토크나이저, 파서, 실행기
[인덱스]     빨리 찾기                                             ← Phase 2: B+ 트리
[저장]       디스크의 파일에 읽고 쓰기                              ← Phase 1: 테이블 파일
[트랜잭션]   동시성 제어, 장애 복구                                 ← Phase 3: lock 하나 (복구는 과제 범위 밖)
```

여섯 장면 중 우리가 직접 다시 풀어 보는 것:

| 장면 | 우리 과제에서 | 어떻게 확인하나 |
| --- | --- | --- |
| ② 형식이 바뀜 / ③ 질문마다 코드 | **Phase 1** SQL 처리기. 사용하는 쪽은 SQL만 쓰고, 파일 형식은 처리기만 앎 | 터미널(CLI)에서 SQL 파일 실행 |
| ④ 느린 찾기 | **Phase 2** B+ 트리 인덱스 | 100만 건에서 인덱스로 찾기 vs 처음부터 찾기 시간 비교 |
| ⑤ 동시에 쓰기 | **Phase 3** 모든 요청이 처리기 하나를 거치고, lock으로 순서를 정함 | 동시에 `INSERT`해도 ID가 겹치지 않는지 테스트 |
| ① 중복 | 과제 범위 밖 (`JOIN`과 정규화: 같은 데이터를 한 곳에만 두도록 테이블을 나누는 설계) | |
| ⑥ 중간에 꺼짐 | 과제 범위 밖 (트랜잭션, WAL) | 발표에서 "실제 DB는 이렇게 푼다"로 설명 |

### 8-2. 왜 하필 B+ 트리인가

데이터베이스에 오는 질문은 "이 키의 값을 줘"만 있지 않습니다.

```
WHERE id = 5                     ← 정확히 일치
WHERE id BETWEEN 100 AND 200     ← 범위
ORDER BY id                      ← 정렬
WHERE created_at > '2026-11-01'  ← 범위
SELECT MAX(id)                   ← 최댓값
```

| 후보 | 키 하나 찾기 | 범위·정렬 | 맞나? |
| --- | --- | --- | --- |
| 파일 처음부터 | O(N): 데이터 수만큼 | O(N) | 장면 ④ 그 자체 |
| 해시 테이블 (미니 레디스에서 만든 것) | **O(1)**: 데이터 수와 상관없이 거의 한 번 | ❌ 키를 계산해서 흩어 놓아 순서가 없음. 범위를 찾으려면 전부 확인 | 범위·정렬이 흔한 DB에는 부족 |
| 균형 이진 트리 | O(log₂ N): 100만 건이면 약 20번 | ✅ | 한 칸(노드)에 키가 하나라 나무가 깊음. 디스크에서는 깊이만큼 읽어야 함 |
| **B+ 트리** | O(log_m N): m은 한 칸에 담는 키 수. 매우 얕음 | ✅ 맨 아래 칸끼리 옆으로 연결 | 순서를 유지하면서, 한 칸에 키를 수백 개 담아 3~4층이면 수억 건을 찾음 |

B 트리는 보잉 연구소의 Bayer와 McCreight가 **메모리에 다 들어가지 않는 큰 색인**을 디스크에서 다루려고 만들었습니다(1970년 논문을 돌려 보고, 1972년 출판). 데이터를 넣고 빼도 스스로 균형을 유지해서, 주기적으로 다시 정리해야 했던 ISAM의 약점을 풀었습니다. 1979년에는 이미 "DB 인덱스의 표준 구조"라는 평가를 받았고, 맨 아래 칸끼리 연결해 순서대로 읽기를 강화한 B+ 트리가 오늘날 거의 모든 관계형 DB의 기본 인덱스입니다.

우리 과제는 이를 **메모리 기반으로 단순화**해서 만듭니다. (과제가 그렇게 요구합니다)

### 8-3. 우리 개발 단계와의 관계 (제안)

아래 숫자는 [설계](../../DESIGN.md) 3절의 개발 단계 번호입니다. 방식은 모두 **아직 제안**입니다.

| DBMS의 기능 | 개발 단계 |
| --- | --- |
| SQL 해석 | **1** 임시 파서 → **3, 4** 토크나이저, 재귀 하강 파서 |
| 파일 저장 | **1** 한 줄 추가 → **5** 한 줄에 JSON 배열 하나, 파일 위치(몇 번째 바이트인지) |
| 스키마 | **0** `schema.json` (`CREATE TABLE` 대신 미리 적어 둠) |
| 무결성 (타입 검사) | **6** 오류 처리 |
| 인덱스 | **2** 임시 파이썬 `dict` → **7, 8** B+ 트리 |
| 쿼리 플래너 (인덱스를 쓸지 고르기) | **2, 8** `WHERE id = ?`면 인덱스, 아니면 처음부터 / **17** `EXPLAIN` (선택) |
| 범위 조회 | **15** 맨 아래 칸의 연결로 범위 검색 (선택) |
| 외부 연결 | **2** API 서버 → **11** Thread Pool |
| 동시성 제어 | **12** 처리기 전체에 lock 하나 → **16** 읽기와 쓰기를 나눈 lock (선택) |
| 성능 증명 | **9, 10** 100만 건 생성, 인덱스 vs 처음부터 찾기 |
| 캐시와 함께 쓰기 | **18** 미니 레디스로 조회 결과 캐시 (선택) |
| 트랜잭션, 장애 복구, `JOIN`, `UPDATE`/`DELETE` | 하지 않음 ([설계](../../DESIGN.md)의 "하지 않을 것") |

## 9. 실제로는 어떻게 쓰나

DBMS도 보통 **따로 떠 있는 서버 프로그램**입니다. 다른 프로그램은 네트워크로 접속해 SQL을 보냅니다. (SQLite처럼 프로그램 안에 라이브러리로 넣어 쓰는 DB도 있습니다.)

아래는 PostgreSQL에 접속하는 파이썬 코드 예시입니다.

```python
import psycopg                                    # PostgreSQL에 접속하는 파이썬 라이브러리
conn = psycopg.connect("host=DB서버주소 dbname=jungle")

def find_orders(user):
    return conn.execute(
        "SELECT product, price FROM orders WHERE user_name = %s",  # %s 자리에 값이 들어감
        (user,),                                                    # 값은 따로 넘김
    ).fetchall()

def place_order(user, product, price):
    with conn.transaction():                       # 장면 ⑤⑥: 이 블록 전체가 트랜잭션 하나
        row = conn.execute(
            "UPDATE stock SET count = count - 1 WHERE product = %s AND count > 0 RETURNING count",
            (product,),
        ).fetchone()
        if row is None:                            # 재고가 0이라 바뀐 줄이 없음
            raise SoldOut()                        # 예외가 나면 블록 안의 변경이 모두 취소됨
        conn.execute("INSERT INTO orders (user_name, product, price) VALUES (%s, %s, %s)",
                     (user, product, price))
```

- 값은 SQL 문자열에 직접 붙이지 않고 **따로 넘깁니다.** 이걸 **파라미터 바인딩**이라고 합니다. 값을 문자열에 직접 붙이면, 이름에 `'`가 들어간 사용자에서 SQL이 깨지고, 악의적인 사용자가 값 대신 SQL 명령을 끼워 넣을 수 있습니다(**SQL 인젝션**). 파라미터 바인딩은 이 두 가지를 막는 기본입니다.
- 정글마켓이 더 커지면 이런 구조가 됩니다.

```
앱 서버 A, B, C → 레디스 (자주 쓰는 결과의 빠른 사본, 서버끼리 공유하는 상태) → DBMS (원본, 트랜잭션) → 디스크
```

DBMS가 **원본과 정확성**을 책임지고, 레디스가 그 앞에서 **속도와 DB 부담 줄이기**를 맡습니다.

## 10. 언제 파일, 언제 DBMS?

| 데이터 성격 | 파일 | DBMS |
| --- | --- | --- |
| 한 프로그램만 쓰는 설정 (설정 파일, `schema.json`) | 적합 | 과함 |
| 쌓기만 하고 나중에 한꺼번에 분석하는 기록 (로그) | 적합 (추가만 하므로) | 분석용 DB를 따로 쓰기도 함 |
| 큰 덩어리 그 자체 (이미지, 동영상) | 적합 (파일 저장소) | 파일 경로만 DB에 저장 |
| 한 프로그램만 쓰지만 조건으로 찾아야 함 | 직접 만들면 고생 | SQLite 같은 내장 DB |
| 여러 프로그램과 사람이 함께 쓰고, 동시에 바뀌고, 틀리면 안 됨 (주문, 결제, 재고, 회원) | 부적합 | 필요 |

DBMS가 필요한 기준은 세 가지입니다: **여럿이 함께 쓰는 데이터인가, 틀리거나 깨지면 안 되는 데이터인가, 여러 방식으로 물어볼 데이터인가.**

## 11. DBMS도 공짜는 아니다

| 비용 | 무엇이 문제인가 | 보완하는 방법 |
| --- | --- | --- |
| 운영 | 별도 서버를 띄우고, 백업, 버전 업그레이드, 모니터링을 해야 함 | 클라우드가 관리해 주는 DB를 씀. 작은 서비스는 SQLite |
| 스키마 변경 | 데이터가 많은 테이블에 칸을 추가하거나 바꾸면 오래 걸리고 위험함 | 마이그레이션 도구(테이블 변경 이력을 기록하고 차례로 적용), 조금씩 나눠 바꾸기 |
| 서버 늘리기 | 원본이 한 곳이고 트랜잭션이 있어서, 서버를 여러 대로 늘리기 어려움 | 읽기 전용 복제본, 레디스 캐시로 DB 부담 줄이기, 샤딩(데이터를 나눠 여러 DB에 저장). 이 한계 때문에 NoSQL이 등장함 |
| 인덱스 | 인덱스마다 저장 공간을 쓰고, `INSERT`할 때마다 모든 인덱스를 고쳐야 해서 쓰기가 느려짐 | 자주 찾는 칸에만 인덱스를 만듦. `EXPLAIN`으로 실제로 쓰이는지 확인 |
| 요청마다 드는 비용 | 네트워크 왕복, SQL 해석 | 커넥션 풀(DB 접속을 미리 여러 개 열어 두고 재사용), prepared statement(SQL을 미리 해석해 두고 값만 바꿔 실행) |

### 헷갈리기 쉬운 것

- **DBMS도 파일에 저장합니다.** "파일 vs DBMS"는 저장 장소의 차이가 아니라, **파일을 누가 직접 만지느냐**의 차이입니다.
- **인덱스는 많을수록 좋은 게 아닙니다.** 읽기는 빨라지지만, 쓸 때마다 인덱스를 고치는 비용이 붙습니다. 우리 과제에서 `id`에만 인덱스를 거는 것도 이 균형의 가장 단순한 형태입니다.
- **lock과 트랜잭션은 같은 게 아닙니다.** lock은 "동시에 끼어들지 못하게" 막는 도구(격리성)입니다. 트랜잭션은 거기에 더해 "중간에 꺼져도 반쪽이 없게"(원자성, 지속성)까지 묶은 약속입니다. 우리 과제는 lock까지 만듭니다.

## 12. 용어 정리

| 용어 | 뜻 |
| --- | --- |
| DBMS | 데이터를 저장하고, 찾고, 보호하는 일을 전담하는 프로그램 (Database Management System) |
| 데이터베이스 | DBMS가 관리하는 데이터 자체 |
| 파일 시스템 방식 | 프로그램마다 자기 파일을 직접 읽고 쓰는 방식 |
| 데이터 독립성 | 데이터를 저장하는 방식이 바뀌어도 프로그램을 고치지 않아도 되는 성질 |
| 스키마 | 어떤 테이블에 어떤 칸이 어떤 타입으로 있는지에 대한 정의 |
| 선언형 질의 | 어떻게 찾을지가 아니라 무엇을 원하는지만 적는 방식 (SQL) |
| 쿼리 플래너 | 같은 SQL을 실행하는 여러 방법 중 가장 빠른 방법을 고르는 DBMS의 부분 |
| 인덱스 | "키 → 데이터 위치"를 정리해 둔 색인. 대표적인 구조가 B+ 트리 |
| 선형 탐색 | 처음부터 끝까지 하나씩 비교하며 찾기. 데이터가 N개면 최대 N번, O(N) |
| 트랜잭션 | 여러 변경을 "전부 되거나 전부 안 되거나"로 묶은 단위 |
| ACID | 트랜잭션의 네 성질: 원자성, 일관성, 격리성, 지속성 |
| lock | 한 번에 한 작업만 데이터에 들어가게 하는 잠금 |
| MVCC | 데이터의 여러 버전을 두어, 읽기가 쓰기를 기다리지 않게 하는 방식 |
| WAL | Write-Ahead Log. 변경을 로그에 먼저 기록해서, 장애가 난 뒤에 복구하는 방식 |
| 무결성 제약 | 타입, 꼭 있어야 하는 값, 범위처럼 데이터가 지켜야 할 규칙을 DBMS가 검사하는 것 |
| 내비게이션 방식 | 초기 DB에서 프로그램이 포인터를 따라 데이터 사이를 직접 찾아가던 방식 |
| O(N), O(log N), O(1) | 데이터가 N개일 때 걸리는 시간이 어떻게 늘어나는지. O(N)은 N에 비례, O(log N)은 N이 10배가 돼도 조금만 늘어남, O(1)은 N과 상관없이 거의 같음 |
