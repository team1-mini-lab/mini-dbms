# 왜 DBMS인가

> **한 줄 요약**
> 파일로 데이터를 관리하면 **파일 형식, 찾는 방법, 동시에 쓸 때의 규칙이 각 프로그램 코드 안에 흩어지기** 때문에, 데이터를 쓰는 프로그램과 사람이 많아지고 데이터가 커지는 순간 값이 서로 어긋나고, 형식 하나 바꾸면 프로그램이 줄줄이 깨지고, 동시에 쓰거나 중간에 꺼지면 데이터가 망가진다.
> DBMS는 데이터를 다루는 일을 **프로그램 밖의 전담 시스템 하나로 빼내서**, 프로그램은 "무엇이 필요한지"만 말하고 저장, 검색, 보호는 DBMS가 책임지게 한다.

이 문서는 "DBMS를 어떻게 쓰나(HOW)"보다 **"DBMS가 무슨 문제를 풀려고 나왔나(WHAT)"**를 설명합니다.
범위와 단계는 [DESIGN.md](../DESIGN.md), 구현 개념은 [DBMS_STUDY.md](./DBMS_STUDY.md)를 참고합니다. 레디스 편은 [WHY_REDIS.md](./WHY_REDIS.md)입니다.

## 한눈에 보는 흐름

레디스가 **로컬 캐시가 일으키는 고통**에서 출발했듯이, DBMS도 **파일로 데이터를 관리할 때의 고통**에서 출발합니다.

```
1. 출발점   파일은 단순하고 좋은 도구다. 프로그램 하나, 데이터가 적으면 이걸로 충분하다.
               ↓
2. 조건     그런데 같은 데이터를 쓰는 프로그램과 사람이 늘고, 데이터가 커진다.
               ↓
3. 문제     그 순간 파일 방식이 여섯 가지를 망가뜨린다.
               ↓
4. 뿌리     여섯 가지의 원인은 하나다: 데이터를 다루는 방법이 각 프로그램에 묶여 있다.
               ↓
5. 해결     데이터를 다루는 일을 프로그램 밖 전담 시스템 하나로 뺀다 → DBMS
```

두 단어만 먼저 짚고 갑니다.

- **조건**: 문제가 **터지는 상황**입니다. 원인은 아닙니다. 똑같은 코드라도 프로그램 하나가 작은 파일을 쓸 때는 아무 문제가 없고, 함께 쓰는 프로그램이 늘고 데이터가 커지는 순간 문제가 드러납니다.
- **뿌리**: 겉으로 보이는 여섯 가지 증상을 **하나로 묶는 진짜 원인**입니다. 증상을 하나씩 막는 대신 뿌리를 고쳐야 여섯 개가 한 번에 풀립니다.

레디스 편과 같은 **"정글마켓"** 쇼핑몰을 예로 끝까지 따라갑니다. 이번에는 레디스를 들이기 훨씬 전, 정글마켓이 처음 문을 연 시절입니다.

## 1. 출발점: 파일은 좋은 도구다

막 문을 연 정글마켓에는 개발자 한 명과 주문 프로그램 하나가 있습니다. 주문이 들어오면 **파일에 한 줄 추가**하고, 주문 목록이 필요하면 **파일을 처음부터 읽습니다.**

```python
def add_order(user, product, price):
    with open("orders.csv", "a") as f:               # 파일 끝에 한 줄 추가
        f.write(f"{user},{product},{price}\n")

def find_orders(user):
    result = []
    for line in open("orders.csv"):                  # 처음부터 끝까지 읽으며
        u, product, price = line.strip().split(",")
        if u == user:                                # 조건에 맞는 줄만
            result.append((product, int(price)))
    return result
```

```
orders.csv
kim,키보드,50000
lee,마우스,20000
kim,모니터,300000
```

- 설치할 것도, 배울 것도 없어서 **가장 단순합니다.**
- 메모장으로 열어 **눈으로 확인할 수 있습니다.**
- 주문이 하루 수십 건이면 처음부터 읽어도 **충분히 빠릅니다.**

**프로그램 하나가 작은 파일을 쓴다면 여기서 끝입니다. DBMS는 필요 없습니다.**

---

## 2. 조건: 함께 쓰는 프로그램이 늘고, 데이터가 커진다

정글마켓이 커지면서 세 가지가 동시에 바뀝니다.

| 변화 | 상황 |
| --- | --- |
| 프로그램이 늘어남 | 주문 외에 회원, 배송, 정산, 마케팅 프로그램이 생기고, 각 팀이 따로 만듦 |
| 데이터가 커짐 | 주문이 하루 수십 건에서 누적 100만 건으로 |
| 동시에 씀 | 세일 날 같은 순간에 수백 명이 주문, 관리자도 동시에 재고를 고침 |

그래서 이런 모양이 됩니다.

```
회원 프로그램  ──→ members.csv  (회원 이름, 주소)
주문 프로그램  ──→ orders.csv   (주문)  ←── 정산 프로그램이 읽음
               └→ stock.txt    (재고)  ←── 관리자 프로그램도 고침
배송 프로그램  ──→ shipping.csv (배송지 주소)  ←── 주문 파일도 읽음
마케팅 담당    ──→ orders.csv를 엑셀로 열어 직접 계산
```

각 팀은 **자기 프로그램에 필요한 파일을 만들고, 남의 파일은 형식을 맞춰 읽습니다.** 코드는 1번과 같은 방식 그대로입니다. 쓰는 사람과 데이터만 늘었을 뿐인데, 이제부터 문제가 터집니다.

## 3. 문제: 파일 방식이 망가뜨리는 여섯 장면

### 장면 ① 주소를 바꿨는데 택배는 옛날 집으로 간다

```
[처음]   kim의 주소: 서울시 강남구
         members.csv  : kim, 서울시 강남구
         shipping.csv : kim, 서울시 강남구     ← 배송팀이 따로 복사해 둔 주소

[kim]    이사해서 마이페이지에서 주소 변경 → 회원 프로그램이 members.csv만 고침
         shipping.csv : 여전히 서울시 강남구

[주문]   kim이 키보드 주문 → 배송 프로그램은 shipping.csv를 봄 → 옛날 집으로 발송
```

- **왜?** 같은 데이터가 여러 파일에 **복사되어** 있고, 회원 프로그램은 배송팀 파일이 있는지조차 모릅니다.
- **고객 입장**: "주소 바꿨는데요?" → 재발송 비용, 분실

### 장면 ② 칸 하나 추가했더니 프로그램 네 개가 깨진다

주문팀이 쿠폰 기능을 만들면서 `orders.csv`에 **쿠폰 칸**을 추가합니다.

```
변경 전:  kim,키보드,50000
변경 후:  kim,키보드,WELCOME10,50000
```

```python
# 정산 프로그램 (정산팀이 1년 전에 작성)
u, product, price = line.strip().split(",")
# → ValueError: too many values to unpack   ← 정산 멈춤

# 마케팅 스크립트
price = int(line.split(",")[2])
# → int("WELCOME10")  오류. 운 나쁘면 쿠폰 코드가 숫자라 엉뚱한 값을 매출로 더함
```

상품 이름에 쉼표가 들어가도 마찬가지입니다. `키보드, 무선`이라는 상품이 생기면 모든 프로그램이 칸을 하나 더 셉니다.

- **왜?** "몇 번째 칸이 가격인지"라는 **파일 형식 지식이 프로그램마다 코드에 박혀** 있습니다.
- **개발자 입장**: 칸 하나 추가하려면 그 파일을 읽는 모든 프로그램을 찾아서 동시에 고쳐야 함. 누가 읽는지 다 아는 사람도 없음

### 장면 ③ 질문 하나에 프로그램 하나

마케팅팀이 묻습니다. **"지난달 서울에 사는 30대가 가장 많이 산 상품 10개는?"**

```python
# 개발자가 이틀 걸려 작성
members = {}
for line in open("members.csv"):           # 1. 회원 파일에서 서울 30대 찾기
    ...
counts = {}
for line in open("orders.csv"):            # 2. 주문 파일에서 그 회원들 주문 세기
    ...
top10 = sorted(counts.items(), ...)[:10]   # 3. 정렬해서 10개
```

다음 주에 질문이 바뀝니다. "부산 20대는?", "카테고리별로는?" → **또 새 코드**.

- **왜?** 데이터를 **어떻게 찾을지(반복문, 조건, 합치기)**를 질문마다 사람이 직접 짜야 합니다.
- **회사 입장**: 질문할 때마다 개발자를 기다림. 데이터는 있는데 쓸 수가 없음

### 장면 ④ 주문이 100만 건이 되자 주문 조회가 느려진다

```
[하루 수십 건 시절]  kim의 주문 찾기 → 파일 수백 줄 읽기 → 순식간

[100만 건]          주문번호 987654 찾기 → 첫 줄부터 읽으며 비교
                    → 최악 100만 줄을 읽고 100만 번 쪼개고 비교
                    → 조회 한 번에 1초 안팎, 1초에 수백 명이 조회하면 서버가 버티지 못함
```

- **왜?** 파일은 **순서대로 읽는 것밖에 모릅니다.** 책에 찾아보기(색인)가 없어서 첫 장부터 넘기는 것과 같습니다.
- 파일을 주문번호 순으로 정렬해 두면 이진 탐색이 되지만, 주문이 들어올 때마다 100만 줄을 다시 정렬할 수는 없고, "회원 이름으로 찾기"에는 또 다른 정렬이 필요합니다.

### 장면 ⑤ 세일 날, 남은 1개를 두 명에게 판다

```
[한정판 키보드 재고 1개, stock.txt 에 "1"]

kim의 주문 → 주문 프로그램(1): stock.txt 읽기 → 1 → "구매 가능"
lee의 주문 → 주문 프로그램(2): stock.txt 읽기 → 1 → "구매 가능"
주문 프로그램(1): stock.txt에 0 쓰기, 주문 기록
주문 프로그램(2): stock.txt에 0 쓰기, 주문 기록

→ 1개를 2명에게 팔아버림
```

같은 파일에 여러 프로그램이 동시에 한 줄씩 추가하면, 운 나쁘면 **두 줄이 섞여 깨진 한 줄**이 생기기도 합니다.

```
kim,키보드,50lee,마우스,20000
000
```

- **왜?** "읽고 → 판단하고 → 쓰기" 사이에 다른 프로그램이 끼어들 수 있고, **순서를 정해 줄 누군가가 없습니다.**
- 레디스 편 장면 ⑤와 같은 모양이지만, 이번에는 사본(캐시)이 아니라 **원본 자체**가 틀어진다는 점이 더 심각합니다.

### 장면 ⑥ 저장하다 꺼지면 돈만 빠진다

주문 하나를 처리하려면 파일 세 개를 고쳐야 합니다.

```
주문 처리
  1. payments.csv 에 결제 기록 추가     ✅ 완료
  2. stock.txt 의 재고 1 줄이기          ← 이 순간 서버 전원이 나감
  3. orders.csv 에 주문 추가             ❌ 실행 안 됨

→ 고객 돈은 결제됐는데 주문은 없음
→ stock.txt는 쓰던 도중이라 내용이 반만 남아 읽을 수조차 없음
```

- **왜?** 여러 파일의 변경을 **"전부 되거나, 전부 안 되거나"로 묶는 장치**가 없습니다.
- **고객 입장**: "돈은 나갔는데 주문 내역이 없어요" → 가장 심각한 종류의 문의

### 누가 겪고, 어떻게 드러나나

| 장면 | 누가 겪나 | 어떻게 드러나나 |
| --- | --- | --- |
| ① 주소 불일치 | 고객 | 엉뚱한 곳으로 배송 |
| ② 형식 변경 | 개발자 | 칸 하나 바꿀 때마다 여러 프로그램이 깨짐, 변경이 무서워짐 |
| ③ 질문마다 코드 | 회사 (기획, 마케팅) | 데이터가 있어도 답을 얻는 데 며칠 |
| ④ 느린 검색 | 고객, 운영자 | 데이터가 늘수록 화면이 느려지고 서버가 버티지 못함 |
| ⑤ 동시에 쓰기 | 고객, 회사 | 초과 판매, 깨진 줄 |
| ⑥ 중간에 꺼짐 | 고객, 회사 | 돈과 주문이 안 맞음, 파일 손상 |

정리하면 **①②는 데이터가 서로 어긋나거나 프로그램이 깨지는 문제, ③④는 데이터를 꺼내기 어렵고 느린 문제, ⑤⑥은 데이터 자체가 망가지는 문제**입니다.

## 4. 뿌리: 여섯 장면의 원인은 하나다

### 4-1. "데이터를 다루는 방법"이 어디에 있나 (눈으로 보기)

정산 프로그램의 코드를 다시 봅니다.

```python
for line in open("orders.csv"):                 # ← 데이터가 어느 파일에 있는지
    u, product, price = line.strip().split(",") # ← 쉼표로 나뉘고, 셋째 칸이 가격이라는 형식
    if u == user:                               # ← 어떻게 찾을지 (처음부터 하나씩)
        total += int(price)
# 동시에 누가 쓰고 있으면?   ← 아무 대비 없음
# 읽다가 꺼지면?             ← 아무 대비 없음
```

이 몇 줄 안에 **데이터를 다루는 방법 전부**(위치, 형식, 찾는 법, 보호)가 들어 있습니다. 그리고 회원, 주문, 배송, 정산, 마케팅 프로그램이 **각자 이것을 따로** 들고 있습니다.

```
회원 프로그램 안   : members.csv 형식 + 찾는 법
주문 프로그램 안   : orders.csv 형식 + stock.txt 형식 + 찾는 법
배송 프로그램 안   : shipping.csv 형식 + orders.csv 형식 + 찾는 법
정산 프로그램 안   : orders.csv 형식 + 찾는 법
마케팅 스크립트 안 : orders.csv 형식 + members.csv 형식 + 찾는 법
```

### 4-2. 여섯 장면을 다시 보면

| 장면 | 실제로 일어난 일 |
| --- | --- |
| ① 주소 불일치 | 프로그램마다 **자기 파일**을 가져서 같은 데이터가 여러 벌 |
| ② 형식 변경 | **파일 형식 지식**이 각 프로그램 코드에 |
| ③ 질문마다 코드 | **찾는 방법**이 각 프로그램 코드에 |
| ④ 느린 검색 | 빨리 찾는 구조(색인)를 만들어도 **모두가 함께 쓸 곳**이 없음 |
| ⑤ 동시에 쓰기 | **순서를 정하는 규칙**을 각 프로그램이 알아서 (= 아무도 안 함) |
| ⑥ 중간에 꺼짐 | **여러 변경을 하나로 묶는 장치**를 각 프로그램이 알아서 (= 아무도 안 함) |

전부 같은 말입니다.

> **뿌리: 데이터를 다루는 방법(형식, 찾기, 보호)이 각 프로그램 안에 묶여 흩어져 있다.**

레디스 편의 뿌리는 "상태가 각 **서버**에 묶여 있다"였습니다. 이번에는 "데이터 다루는 법이 각 **프로그램**에 묶여 있다"입니다. 둘 다 **"묶여 있다"**가 핵심입니다.

### 4-3. 도서관으로 비유하면

- **파일 방식**: 사람마다 **자기 책장**에 책을 둡니다. 같은 책이 여러 책장에 있고(①), 책장마다 꽂는 방식이 달라서 남의 책장에서 찾으려면 그 사람의 방식을 알아야 하고(②), 원하는 책을 찾으려면 책장을 처음부터 훑어야 합니다(③④). 두 사람이 같은 책을 동시에 빌려 갈 수도 있습니다(⑤).
- **DBMS 방식**: 책은 **도서관 한 곳**에 두고 **사서**가 관리합니다. 이용자는 "2020년 이후에 나온 DB 책 주세요"라고 **원하는 것만** 말하면, 사서가 **카탈로그(색인)**로 찾아 줍니다. 도서관이 책 배치를 바꿔도 이용자는 몰라도 되고, 대출 규칙이 있어서 한 권을 두 명에게 빌려주지 않습니다.

### 4-4. "어떻게" 대신 "무엇을"

뿌리를 풀면 프로그램이 데이터에 말을 거는 방식이 바뀝니다.

| | 파일 방식: 어떻게(HOW) | DBMS 방식: 무엇을(WHAT) |
| --- | --- | --- |
| 말하는 것 | 이 파일을 열어서, 쉼표로 나누고, 첫 칸이 kim인 줄의 셋째 칸을 더해 | kim의 주문 금액 합계를 줘 |
| 코드 | 반복문, 조건문, 칸 번호 | `SELECT SUM(price) FROM orders WHERE user = 'kim'` |
| 형식이 바뀌면 | 코드를 고쳐야 함 | 그대로 |
| 색인이 생기면 | 코드를 고쳐야 빨라짐 | 그대로인데 빨라짐 |

택시에 비유하면, 파일 방식은 기사에게 "직진, 두 번째 골목에서 우회전..."을 하나하나 지시하는 것이고, DBMS 방식은 **목적지만 말하는 것**입니다. 길은 기사(DBMS)가 고릅니다. 이렇게 프로그램이 데이터의 저장 방식과 상관없이 동작하는 성질을 **데이터 독립성**이라고 합니다.

### 4-5. 증상만 막으면 왜 안 되나

| 시도 | 막는 것 | 남는 것 |
| --- | --- | --- |
| 파일 읽기 공용 코드(라이브러리)를 만들어 모두 쓰게 함 | ② 형식 지식이 한 곳에 | 형식이 바뀌면 모든 프로그램을 다시 배포해야 함. 옛 버전을 쓰는 프로그램이 남음. ④⑤⑥ 그대로 |
| 파일 잠금(flock)으로 한 번에 한 프로그램만 | ⑤ 동시에 쓰기 | 파일 전체를 잠가 모두가 줄을 섬. **한 프로그램이라도 잠금을 빼먹으면** 무너짐. ⑥ 그대로 |
| 파일을 주문번호 순으로 정렬해 저장 | ④ 이진 탐색 가능 | 추가할 때마다 전체 재정렬. 다른 칸(이름)으로 찾을 땐 여전히 느림 |
| 매일 밤 백업 | ⑥ 일부 복구 | 백업 이후 데이터는 잃음. "결제는 됐는데 주문이 없는" 반쪽 상태는 그대로 |
| 복사본 없이 한 파일만 쓰기로 규칙을 정함 | ① 중복 | 규칙을 문서로만 지키면 언젠가 누군가 어김. 한 파일에 모두 몰리면 ⑤가 심해짐 |

증상마다 막다 보면 결국 **"모든 프로그램이 지켜야 하는 공용 코드와 규칙"**이 점점 커집니다. 그걸 아예 **프로그램 하나로 떼어 낸 것**이 DBMS입니다.

## 5. 해결 방향: 데이터를 다루는 일을 프로그램 밖으로 뺀다

**프로그램은 무엇이 필요한지만 말하고, 데이터를 다루는 일은 전담 시스템 한 곳이 맡습니다.**

```
회원 프로그램  ─┐
주문 프로그램  ─┤
배송 프로그램  ─┼─ "무엇이 필요한지" (SQL) ─→ [ DBMS ]
정산 프로그램  ─┤                              ├─ 스키마: 어떤 데이터가 어떤 모양인지
마케팅 담당    ─┘                              ├─ 질의 처리: 어떻게 찾을지 스스로 결정
                                               ├─ 인덱스: 빨리 찾는 색인
                                               ├─ 동시성 제어: 동시에 써도 순서대로
                                               └─ 복구: 꺼져도 전부 되거나 전부 안 되거나
                                                        ↓
                                                    디스크의 파일
```

DBMS도 결국 **파일에 저장합니다.** 달라진 것은 그 파일을 **DBMS만 직접 만지고**, 나머지는 모두 DBMS에게 부탁한다는 점입니다.

여섯 장면이 이렇게 바뀝니다.

| 장면 | DBMS를 두면 |
| --- | --- |
| ① 주소 | 주소는 회원 테이블에 한 번만 저장. 배송은 그 테이블을 함께 조회(`JOIN`) → 고치면 모두 새 주소 |
| ② 형식 | 프로그램은 칸 번호가 아니라 이름(`price`)으로 요청. 칸을 추가해도 기존 SQL은 그대로 |
| ③ 질문 | 마케팅이 SQL 한 문장으로 직접 질문. 질문이 바뀌면 문장만 바꿈 |
| ④ 검색 | DBMS가 인덱스(B+ 트리)를 관리. 100만 건이어도 몇 번만 비교해서 찾음 |
| ⑤ 동시성 | 모든 요청이 DBMS 한 곳을 거치므로, DBMS가 lock으로 순서를 정함 → 1개면 한 명만 |
| ⑥ 장애 | 여러 변경을 **트랜잭션** 하나로 묶음 → 중간에 꺼지면 시작 전 상태로 되돌림 |

### 그런데 "전담하는 곳"을 어디에 두나?

| 후보 | 결과 |
| --- | --- |
| 각 프로그램 안 (공용 라이브러리) | 4-5의 첫 줄. 프로그램마다 버전이 달라지고, 동시성과 복구는 여전히 각자 |
| 공유 폴더의 파일 + 규칙 문서 | 규칙을 사람이 지켜야 함. 한 명이 어기면 끝 |
| **데이터를 전담하는 별도 프로그램** | 파일은 이 프로그램만 만짐 → 형식, 색인, 순서, 복구를 한 곳에서 책임 → **DBMS** |

### 레디스와 나란히 보면

| | 레디스 | DBMS |
| --- | --- | --- |
| 출발한 고통 | 서버 메모리에 캐시·세션을 두니 서버끼리 어긋남 | 프로그램마다 파일을 다루니 데이터가 어긋나고 깨짐 |
| 조건 | 서버가 여러 대가 됨 | 함께 쓰는 프로그램이 늘고, 데이터가 커짐 |
| 뿌리 | 상태가 각 서버에 묶여 있음 | 데이터 다루는 법이 각 프로그램에 묶여 있음 |
| 해결 | 상태를 서버 밖 한 곳(공용 메모리 저장소)으로 | 데이터 관리를 프로그램 밖 한 곳(전담 시스템)으로 |
| 결과 | 상태와 **서버** 분리 | 데이터와 **프로그램** 분리 |

## 6. DBMS 이전의 시도들

| 시기 | 시도 | 방식 | 한계 |
| --- | --- | --- | --- |
| 1950~60년대 | 파일 시스템 | 프로그램마다 자기 파일 (자기 테이프, 이후 디스크) | 3장의 여섯 장면 그대로 |
| 1960년대 | 색인 순차 파일 (IBM ISAM 등) | 정렬된 파일에 색인을 붙여 키로 빨리 찾기 | ④를 일부 풀었지만 색인이 고정이라 추가가 쌓이면 느려져 주기적으로 재정리해야 함. 형식과 찾는 법은 여전히 프로그램 안 |
| 1960년대 초~ | **네트워크형 DB** (GE의 IDS, 찰스 바크먼) → 1969~1971년 CODASYL이 표준화 | 데이터끼리 포인터로 연결, 프로그램이 따라감 | 데이터는 프로그램 밖으로 뺐지만, **찾아가는 길**은 프로그램이 알아야 함 |
| 1966~1968년 | **계층형 DB** (IBM IMS. 아폴로 계획의 새턴 V 로켓 부품 목록 관리용으로 1966년 개발 시작, 1968년 설치, 1969년 IMS로 이름 변경) | 데이터를 부모-자식 나무 구조로 DBMS가 관리 | 같은 한계. 미리 정한 나무 모양대로만 빨리 찾을 수 있고, 구조를 바꾸면 프로그램을 고쳐야 함 |

계층형, 네트워크형 DB로 **공유, 동시성, 복구**는 상당 부분 DBMS가 맡게 되었습니다. 하지만 데이터를 꺼내는 방식은 이랬습니다.

```
[네트워크형 DB에서 "kim의 주문 금액 합계"]
1. 고객 레코드 중 kim을 찾는다
2. kim에서 "첫 번째 주문" 포인터를 따라간다
3. 금액을 더하고, "다음 주문" 포인터를 따라간다
4. 마지막 주문까지 3을 반복
```

- 프로그램이 **데이터 사이의 길을 직접 따라가는** 방식이라 "내비게이션" 방식이라고 부릅니다. 바크먼이 1973년 튜링상 강연 제목을 "내비게이터로서의 프로그래머(The Programmer as Navigator)"로 붙인 데서 퍼진 말입니다.
- 데이터 구조가 바뀌면(예: 주문을 고객 밑이 아니라 상품 밑으로) 길이 바뀌어 **프로그램을 고쳐야** 합니다. 장면 ②가 모양만 바꿔 남은 것입니다.
- 미리 연결해 두지 않은 질문(장면 ③)은 여전히 어렵습니다.

레디스 편에서 Memcached가 "공유는 얻었지만 자료구조를 잃은" 단계였다면, 이 시기는 **"데이터는 프로그램 밖으로 뺐지만, 찾아가는 길은 여전히 프로그램이 들고 있던"** 단계입니다.

## 7. 관계형 DBMS (1970~): 무엇을 원하는지만 말하면 길은 DBMS가 찾는다

1970년 6월, IBM 샌호세 연구소의 에드거 F. 코드(Codd)가 논문 "A Relational Model of Data for Large Shared Data Banks"로 **관계형 모델**을 발표합니다. 논문의 첫 문장부터 "앞으로 큰 데이터 뱅크를 쓰는 사람은 데이터가 기계 안에서 어떻게 구성되는지 몰라도 되게 보호받아야 한다"는 취지로 시작합니다. 핵심은 두 가지입니다.

1. 데이터를 **표(테이블)**로만 표현합니다. 포인터나 길이 없고, 행과 열만 있습니다.
2. 프로그램은 **원하는 결과의 조건만** 말하고, 어떻게 찾을지는 DBMS가 정합니다.

코드는 당시 시스템에 남아 있던 문제를 세 가지 "의존"으로 짚었는데, 이 문서의 장면과 그대로 이어집니다.

| 코드가 짚은 의존 | 뜻 | 이 문서의 장면 |
| --- | --- | --- |
| 순서 의존 | 프로그램이 "파일이 이 순서로 저장되어 있다"고 가정 | ② 형식이 바뀌면 깨짐 |
| 인덱스 의존 | 프로그램이 특정 색인을 이름으로 직접 사용해서, 색인을 없애면 깨짐 | ④ 색인을 마음대로 넣고 뺄 수 없음 |
| 접근 경로 의존 | 프로그램이 나무·네트워크 구조의 길을 따라감 | 6장의 내비게이션 방식 |

이 아이디어가 IBM System R, 버클리 Ingres 같은 연구를 거쳐 **SQL**과 Oracle, DB2, 이후 MySQL, PostgreSQL로 이어집니다.

### 7-1. 파일, 초기 DBMS, 관계형 DBMS 비교

| 구분 | 구체적인 요구 | 파일 | 계층형·네트워크형 DB | 관계형 DBMS |
| --- | --- | --- | --- | --- |
| 공유 | 모든 프로그램이 같은 데이터 한 벌 보기 | ❌ 프로그램마다 파일 | ✅ | ✅ |
| 독립성 | 저장 형식이 바뀌어도 프로그램 그대로 | ❌ | △ 구조가 바뀌면 길도 바뀜 | ✅ 이름으로 요청 |
| 질의 | 새 질문을 코드 없이 | ❌ 질문마다 프로그램 | ❌ 길을 따라가는 코드 | ✅ SQL 한 문장 |
| 성능 | 큰 데이터에서 빨리 찾기 | ❌ 처음부터 읽기 | ✅ 포인터로 | ✅ 인덱스, DBMS가 길을 고름 |
| 동시성 | 동시에 써도 깨지지 않기 | ❌ | ✅ | ✅ lock, MVCC |
| 복구 | 중간에 꺼져도 반쪽 상태 없음 | ❌ | ✅ | ✅ 트랜잭션, 로그 |
| 무결성 | 잘못된 값 막기 (가격은 숫자, 주문엔 회원 필요) | ❌ 프로그램마다 검사 | △ | ✅ 타입, 제약 조건 |
| 권한 | 누가 무엇을 볼 수 있는지 | ❌ 파일 권한 정도 | ✅ | ✅ 테이블·열 단위 |

- **파일**: 단순하지만 모든 걸 프로그램이 알아서
- **계층형·네트워크형**: 보호는 DBMS가 하지만, 길은 프로그램이
- **관계형**: 보호도, 길 찾기도 DBMS가

### 7-2. SQL(선언형 질의)이 왜 중요한가

| 하고 싶은 일 | 파일로 하면 | SQL |
| --- | --- | --- |
| kim의 주문 목록 | 파일 열기 → 줄마다 나누기 → 첫 칸 비교 | `SELECT * FROM orders WHERE user = 'kim'` |
| 주문번호 987654 | 100만 줄 처음부터 비교 | `SELECT * FROM orders WHERE id = 987654` |
| 서울 30대의 인기 상품 10개 | 반복문 세 개, 이틀 | `SELECT product, COUNT(*) FROM orders JOIN members ... GROUP BY product ORDER BY 2 DESC LIMIT 10` |
| 주소 바꾸기 | 주소가 있는 모든 파일을 찾아 고치기 | `UPDATE members SET address = '...' WHERE name = 'kim'` |

두 가지 효과가 있습니다.

1. **프로그램이 형식을 몰라도 됩니다.** 칸 번호 대신 이름으로 말하니 장면 ②가 사라집니다.
2. **DBMS가 가장 빠른 길을 고릅니다.** 같은 `WHERE id = 987654`라도 인덱스가 있으면 인덱스로, 없으면 처음부터 읽습니다. **인덱스를 추가해도 SQL은 한 글자도 안 바뀌고 빨라집니다.** 이 "길을 고르는 일"을 하는 부분이 **쿼리 플래너(옵티마이저)**입니다.

### 7-3. 트랜잭션: 동시성과 장애를 한 번에

장면 ⑤⑥은 **트랜잭션**으로 풉니다. 여러 작업을 하나로 묶어 "전부 되거나, 전부 안 되거나"로 만듭니다.

```sql
BEGIN;
UPDATE stock SET count = count - 1 WHERE product = '키보드' AND count > 0;
INSERT INTO payments ...;
INSERT INTO orders ...;
COMMIT;            -- 여기까지 와야 셋 다 반영. 중간에 꺼지면 셋 다 없던 일
```

트랜잭션이 지키는 네 가지 성질을 **ACID**라고 합니다.

| 성질 | 뜻 | 막는 장면 | DBMS가 하는 일 (대표적인 방법) |
| --- | --- | --- | --- |
| **A**tomicity 원자성 | 전부 되거나 전부 안 되거나 | ⑥ 돈만 빠짐 | 변경 전 상태를 기록해 두고 실패하면 되돌림 |
| **C**onsistency 일관성 | 규칙(재고 ≥ 0 등)이 항상 지켜짐 | ⑤ 초과 판매 | 타입, 제약 조건 검사 |
| **I**solation 격리성 | 동시에 실행해도 하나씩 실행한 것과 같은 결과 | ⑤ 끼어들기, 섞인 줄 | lock, MVCC(여러 버전 유지) |
| **D**urability 지속성 | COMMIT된 것은 꺼져도 남음 | ⑥ 파일 손상 | 변경을 로그에 먼저 쓰고(WAL) 디스크에 확실히 기록 |

- 레디스 편 7-3의 원칙이 "읽고 쓰기를 앱에서 나눠 하지 말고 레디스 안에서 한 번에"였다면, DBMS의 원칙은 **"여러 변경을 프로그램이 따로 하지 말고 트랜잭션 하나로 DBMS에 맡긴다"**입니다.

## 8. 그럼 우리는 무엇을 만드나?

### 8-1. DBMS의 층과 우리 Phase

DBMS는 대략 이런 층으로 나뉩니다. 우리 과제의 세 Phase가 각 층에 대응합니다.

```
[연결 층]     외부 요청 받기, 여러 요청 동시에 처리         ← Phase 3: API 서버, Thread Pool
[질의 처리 층] SQL 해석 → 실행 계획 → 실행                  ← Phase 1: 토크나이저, 파서, 실행기
[접근 방법 층] 인덱스로 빨리 찾기                            ← Phase 2: B+ 트리
[저장 층]     디스크의 파일에 읽고 쓰기                      ← Phase 1: 테이블 파일
[트랜잭션 층]  동시성 제어, 장애 복구                        ← Phase 3: lock 하나 (복구는 범위 밖)
```

여섯 장면 중 우리가 직접 다시 풀어 보는 것:

| 장면 | 우리 과제에서 | 어떻게 확인하나 |
| --- | --- | --- |
| ② 형식 변경 / ③ 질문마다 코드 | **Phase 1** SQL 처리기. 사용자는 SQL만 쓰고 파일 형식은 엔진만 앎 | CLI로 SQL 파일 실행 |
| ④ 느린 검색 | **Phase 2** B+ 트리 인덱스 | 100만 건에서 인덱스 vs 선형 탐색 시간 비교 |
| ⑤ 동시에 쓰기 | **Phase 3** 모든 요청이 엔진 하나를 거치고, lock으로 순서를 정함 | 동시 `INSERT` 테스트에서 ID 중복 없음 |
| ① 중복 | 범위 밖 (`JOIN`, 정규화) | |
| ⑥ 중간에 꺼짐 | 범위 밖 (트랜잭션, WAL) | 발표에서 "실제 DB는 이렇게 푼다"로 설명 |

### 8-2. 왜 하필 B+ 트리인가

레디스 편에서는 "캐시에 오는 질문은 항상 '이 키의 값 줘'라서 해시 테이블"이었습니다. DB에 오는 질문은 다릅니다.

```
WHERE id = 5                 ← 정확히 일치
WHERE id BETWEEN 100 AND 200 ← 범위
ORDER BY id                  ← 정렬
WHERE created_at > '2026-11-01' ← 범위
SELECT MAX(id)               ← 최댓값
```

| 후보 | 키 하나 찾기 | 범위·정렬 | 맞나? |
| --- | --- | --- | --- |
| 파일 처음부터 | O(N) | O(N) | 장면 ④ 그 자체 |
| 해시 테이블 | **O(1)** | ❌ 키를 뒤섞어 배치해서 전부 확인 | 범위·정렬이 흔한 DB엔 부족 |
| 균형 이진 트리 | O(log₂ N) | ✅ | 노드 하나에 키 하나라 트리가 깊음. 디스크에서는 깊이 = 읽는 횟수 |
| **B+ 트리** | O(log_m N), 매우 얕음 | ✅ 리프가 옆으로 연결 | 정렬을 유지하면서, 노드 하나에 키를 수백 개 담아 3~4층이면 수억 건 |

B 트리는 보잉 연구소의 Bayer와 McCreight가 **메모리에 다 들어가지 않는 큰 색인**을 디스크에서 다루려고 만들었습니다(1970년 논문 회람, 1972년 출판). 추가와 삭제에도 스스로 균형을 유지해서, 주기적 재정리가 필요했던 ISAM의 약점을 풀었습니다. 1979년에는 이미 "DB 인덱스의 표준 구조"라는 평가를 받았고, 리프를 연결해 순서대로 읽기를 강화한 B+ 트리가 오늘날 거의 모든 관계형 DB의 기본 인덱스입니다.
우리 과제는 이를 **메모리 기반으로 단순화**해서 만듭니다.

### 8-3. 우리 범위와의 관계

| DBMS의 기능 | 우리 단계 (DESIGN.md) |
| --- | --- |
| SQL 해석 (질의 처리의 입구) | **1** 임시 파서 → **3, 4** 토크나이저, 재귀 하강 파서 |
| 파일 저장 | **1** 한 줄 추가 → **5** JSON Lines, 파일 위치(offset) |
| 스키마 | **0** `schema.json` (`CREATE TABLE` 대신) |
| 무결성 (타입 검사) | **6** 오류 처리 |
| 인덱스 | **2** 임시 `dict` → **7, 8** B+ 트리 |
| 플래너 (인덱스를 쓸지 고르기) | **2, 8** `WHERE id = ?`면 인덱스, 아니면 선형 탐색 / **17** `EXPLAIN` (선택) |
| 범위 조회 | **15** 리프 연결로 범위 검색 (선택) |
| 외부 연결 | **2** API 서버 → **11** Thread Pool |
| 동시성 제어 | **12** 엔진 전체 lock 하나 → **16** 읽기/쓰기 lock (선택) |
| 성능 증명 | **9, 10** 100만 건 생성, 인덱스 vs 선형 탐색 |
| 캐시와 함께 쓰기 | **18** 미니 레디스로 쿼리 결과 캐시 (선택) |
| 트랜잭션, 장애 복구, `JOIN`, `UPDATE`/`DELETE` | 하지 않음 (DESIGN.md "하지 않을 것") |

## 9. 실제로는 어떻게 쓰나

DBMS도 레디스처럼 **따로 돌아가는 서버 프로그램**입니다. 앱은 네트워크로 접속해 SQL을 보냅니다. (SQLite처럼 프로그램 안에 라이브러리로 들어가는 DB도 있습니다.)

```python
import psycopg                                    # PostgreSQL 드라이버
conn = psycopg.connect("host=DB서버주소 dbname=jungle")

def find_orders(user):
    return conn.execute(
        "SELECT product, price FROM orders WHERE user_name = %s",  # 값은 따로 전달
        (user,),
    ).fetchall()

def place_order(user, product, price):
    with conn.transaction():                       # 장면 ⑤⑥: 전부 되거나 전부 안 되거나
        row = conn.execute(
            "UPDATE stock SET count = count - 1 WHERE product = %s AND count > 0 RETURNING count",
            (product,),
        ).fetchone()
        if row is None:
            raise SoldOut()                        # 재고 없으면 아무것도 반영 안 됨
        conn.execute("INSERT INTO orders (user_name, product, price) VALUES (%s, %s, %s)",
                     (user, product, price))
```

- 값은 SQL 문자열에 붙이지 않고 **따로 전달**합니다(파라미터 바인딩). 이름에 `'`가 들어간 사용자, 그리고 SQL 인젝션 공격을 막는 기본입니다.
- 정글마켓이 더 커지면 레디스 편의 구조가 됩니다.

```
앱 서버 A, B, C → 레디스 (빠른 사본, 공유 상태) → DBMS (원본, 트랜잭션) → 디스크
```

DBMS가 **원본과 정확성**을 책임지고, 레디스가 그 앞에서 **속도와 DB 보호**를 맡습니다.

## 10. 언제 파일, 언제 DBMS?

| 데이터 성격 | 파일 | DBMS |
| --- | --- | --- |
| 한 프로그램만 쓰는 설정 (설정 파일, `schema.json`) | 적합 | 과함 |
| 쌓기만 하고 나중에 한꺼번에 분석 (로그) | 적합 (추가만 하므로) | 분석용 DB를 따로 쓰기도 함 |
| 큰 덩어리 그 자체 (이미지, 동영상) | 적합 (파일·객체 저장소) | 위치(경로)만 DB에 저장 |
| 한 프로그램이 쓰지만 조건 검색이 필요 | 직접 구현하면 고생 | SQLite 같은 내장 DB |
| 여러 프로그램·사람이 함께 쓰고, 동시에 바뀌고, 틀리면 안 됨 (주문, 결제, 재고, 회원) | 부적합 | 필요 |

- DBMS가 필요한 기준은 **"함께 쓰는 데이터"**, **"틀리거나 깨지면 안 되는 데이터"**, **"여러 방식으로 물어볼 데이터"** 세 가지입니다.

## 11. DBMS도 공짜는 아니다

| 비용 | 무엇이 문제인가 | 보완 |
| --- | --- | --- |
| 운영 비용 | 별도 서버, 백업, 버전 업그레이드, 모니터링 | 클라우드 관리형 DB. 작은 서비스는 SQLite |
| 스키마 변경 | 큰 테이블에 칸 추가·변경이 오래 걸리고 위험 | 마이그레이션 도구로 변경 이력 관리, 단계적 변경 |
| 늘리기 어려움 | 원본이 한 곳이라 서버를 늘리기 어려움 (트랜잭션 때문) | 읽기 복제본, 레디스 캐시로 DB 보호, 샤딩. 이 한계에서 NoSQL이 등장 |
| 인덱스 비용 | 인덱스마다 공간을 쓰고, `INSERT`마다 모든 인덱스를 갱신해 쓰기가 느려짐 | 자주 찾는 칸에만 인덱스. `EXPLAIN`으로 실제로 쓰이는지 확인 |
| 요청마다 드는 비용 | 네트워크 왕복, SQL 해석 | 커넥션 풀, 미리 해석해 두는 문장(prepared statement) |

### 헷갈리기 쉬운 짝

- **DBMS도 파일에 저장합니다.** "파일 vs DBMS"는 저장 장소의 차이가 아니라, **파일을 누가 직접 만지느냐**의 차이입니다.
- **인덱스는 많을수록 좋은 게 아닙니다.** 읽기는 빨라지지만 쓰기마다 갱신 비용이 붙습니다. 우리 과제에서 `id`에만 인덱스를 거는 것도 이 균형의 가장 단순한 형태입니다.
- **lock과 트랜잭션은 같은 게 아닙니다.** lock은 "동시에 끼어들지 못하게"(격리성의 도구)이고, 트랜잭션은 거기에 "중간에 꺼져도 반쪽이 없게"(원자성, 지속성)까지 묶은 약속입니다. 우리 과제는 lock까지 구현합니다.

## 12. 용어 정리

| 용어 | 뜻 |
| --- | --- |
| DBMS | 데이터를 저장, 검색, 보호하는 일을 전담하는 시스템 (Database Management System) |
| 데이터베이스 | DBMS가 관리하는 데이터 자체 |
| 파일 시스템 방식 | 프로그램마다 자기 파일을 직접 읽고 쓰는 방식 |
| 데이터 독립성 | 저장 방식이 바뀌어도 프로그램을 고치지 않아도 되는 성질 |
| 스키마 | 어떤 테이블에 어떤 칸이 어떤 타입으로 있는지에 대한 정의 |
| 선언형 질의 | 어떻게 찾을지가 아니라 무엇을 원하는지만 적는 방식 (SQL) |
| 쿼리 플래너 | 같은 SQL을 실행할 여러 방법 중 가장 빠른 길을 고르는 부분 |
| 인덱스 | 키 → 데이터 위치를 정리해 둔 색인. 대표 구조가 B+ 트리 |
| 선형 탐색 | 처음부터 끝까지 하나씩 비교하며 찾기, O(N) |
| 트랜잭션 | 여러 변경을 "전부 되거나 전부 안 되거나"로 묶은 단위 |
| ACID | 트랜잭션의 네 성질: 원자성, 일관성, 격리성, 지속성 |
| lock | 한 번에 한 작업만 데이터에 들어가게 하는 잠금 |
| MVCC | 데이터의 여러 버전을 두어 읽기가 쓰기를 기다리지 않게 하는 방식 |
| WAL | Write-Ahead Log. 변경을 로그에 먼저 기록해 장애 후 복구하는 방식 |
| 무결성 제약 | 타입, 필수 값, 범위처럼 데이터가 지켜야 할 규칙을 DBMS가 검사하는 것 |
| 내비게이션 방식 | 초기 DB에서 프로그램이 포인터를 따라 데이터 사이를 직접 찾아가던 방식 |
