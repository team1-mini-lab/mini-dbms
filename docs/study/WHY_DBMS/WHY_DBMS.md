# 왜 DBMS인가

> **한 줄 요약**: 같은 파일을 여러 코드가 각자 직접 열면, 모양을 바꿀 때 깨지고, 많아지면 느려지고, 동시에 쓰면 망가진다. DBMS는 파일을 다루는 일을 한 곳으로 모아 이 셋을 푼다.

## 1. 출발점: 파일 하나를 여러 코드가 직접 연다

쇼핑몰 폴더 하나가 있습니다.

```
shop/
├── orders.csv      ← 주문 데이터
├── order.py        ← 주문 받는 코드
├── report.py       ← 매출 계산하는 코드
└── delivery.py     ← 택배 보내는 코드
```

`orders.csv`는 한 줄에 주문 하나이고, 쉼표로 `주문번호, 회원, 상품, 가격` 네 칸을 나눕니다.

```
1,kim,키보드,50000
2,lee,마우스,20000
```

세 `.py` 파일이 **모두 같은 `orders.csv`를 직접 엽니다.**

```python
# order.py: 주문이 오면 한 줄 추가
open("orders.csv", "a").write("3,park,모니터,300000\n")

# report.py: 매출 합계
for line in open("orders.csv"):
    id, user, product, price = line.strip().split(",")
    total += int(price)

# delivery.py: kim에게 보낼 주문 찾기
for line in open("orders.csv"):
    id, user, product, price = line.strip().split(",")
    if user == "kim": ...
```

데이터가 적고 코드가 하나둘일 때는 이걸로 충분합니다. 설치할 것도 없고, 파일을 메모장으로 열어 볼 수도 있습니다.

## 2. 생기는 문제 세 가지

### 문제 1: 모양을 바꾸면 다른 코드가 깨진다

`order.py`를 고쳐서 가격 앞에 쿠폰 칸을 하나 넣습니다. 이제 새 주문은 이렇게 저장됩니다.

```
orders.csv
1,kim,키보드,50000
2,lee,마우스,20000
3,park,모니터,WELCOME,300000      ← 새 줄은 5칸
```

`report.py`는 그대로입니다. 3번째 줄을 읽는 순간 이렇게 됩니다.

```python
id, user, product, price = "3,park,모니터,WELCOME,300000".split(",")
# 쉼표로 나누면 5개인데, 받을 변수는 4개
# ValueError: too many values to unpack (expected 4)
```

`report.py`와 `delivery.py`는 한 글자도 안 고쳤는데 멈췄습니다.

**왜**: "한 줄은 4칸, 4번째가 가격"이라는 파일 모양이 `order.py`, `report.py`, `delivery.py` 세 곳에 **따로** 적혀 있기 때문입니다. `order.py`만 5칸으로 바꾸면, 나머지 두 곳은 여전히 4칸이라고 믿고 읽습니다.

### 문제 2: 데이터가 많아지면 느려진다

주문이 100만 건이 됐습니다. `delivery.py`가 주문번호 987654를 찾으려면 첫 줄부터 987654번째 줄까지 다 읽어야 합니다. 데이터가 10배 늘면 시간도 10배 걸립니다.

**왜**: 파일은 처음부터 순서대로 읽는 방법밖에 없기 때문입니다.

### 문제 3: 동시에 쓰면 망가진다

재고 파일 `stock.txt`에 `1`이 적혀 있습니다. kim과 lee가 거의 동시에 `order.py`로 주문합니다.

```
order.py (kim): stock.txt 읽음 → 1 → "살 수 있다"
order.py (lee): stock.txt 읽음 → 1 → "살 수 있다"     ← kim이 0을 쓰기 전에 읽음
order.py (kim): stock.txt에 0을 씀
order.py (lee): stock.txt에 0을 씀
→ 1개를 2명에게 팖
```

주문 하나에 결제, 재고, 주문 기록 파일 세 개를 차례로 고치다가 중간에 꺼지면, 결제만 되고 주문은 없는 일도 생깁니다.

**왜**: 실행마다 각자 파일을 열기 때문에, 끼어드는 걸 막거나 여러 변경을 하나로 묶어 주는 곳이 없습니다.

### 누가 겪나

| 먼저 겪는 사람 | 결국 겪는 사람 |
| --- | --- |
| 개발자: 내가 안 고친 코드가 깨지고(문제 1), 찾기 코드를 매번 새로 짜고, 동시에 쓰는 경우까지 직접 막아야 함 | 고객: 화면이 느리고(문제 2), 1개 남은 상품이 둘에게 팔려 취소되고, 돈만 빠짐(문제 3) |

### 공통 원인

> **파일을 여러 코드가 각자 직접 다룬다.**

## 3. DBMS 이전의 시도

### 문제마다 하나씩 막기

| 시도 | 막는 것 | 남는 문제 |
| --- | --- | --- |
| 파일 읽는 코드를 공용 함수로 만들어 모두 쓰게 함 | 문제 1 | 함수를 고칠 때마다 모든 코드에 다시 배포해야 함. 문제 2, 3은 그대로 |
| 파일을 주문번호 순으로 정렬해 둠 | 문제 2 | 주문이 올 때마다 전체를 다시 정렬해야 함. 회원 이름으로 찾으면 여전히 느림 |
| 파일 잠금 (운영체제에 "지금 내가 쓴다"고 알림) | 문제 3 | 모든 코드가 빠짐없이 잠금을 써야 함. 하나라도 빼먹으면 무너짐 |

막을수록 "모든 코드가 지켜야 할 규칙"이 늘어납니다.

### 1960년대: 데이터를 한 곳으로 모은 첫 DB

IBM의 IMS(1968년, 아폴로 계획의 로켓 부품 관리에서 출발)와 GE의 IDS 같은 초기 DB가 데이터를 코드 밖의 한 곳으로 모았습니다. 동시에 쓸 때의 순서와 복구도 그곳이 맡았습니다.

하지만 데이터를 꺼내려면 코드가 미리 연결된 길을 직접 따라가야 했습니다.

```
"kim의 주문" 꺼내기:  kim을 찾음 → kim의 첫 주문으로 감 → 다음 주문으로 감 → ...
```

데이터 구조가 바뀌면 길이 바뀌어서 코드를 또 고쳐야 했습니다. 문제 1이 모양만 바꿔 남은 것입니다.

## 4. DBMS는 어떻게 풀었나

1970년 IBM 연구소의 코드(Codd)가 **관계형 모델**을 제안합니다. 데이터는 표로만 저장하고, 코드는 "무엇이 필요한지"만 말하고, 어떻게 찾을지는 DBMS가 정합니다. 이것이 SQL과 오늘날의 MySQL, PostgreSQL로 이어집니다.

같은 폴더를 DBMS로 바꾸면 이렇게 됩니다.

```
shop/
├── shop.db         ← 이 파일은 DBMS만 엶
├── order.py
├── report.py
└── delivery.py
```

```python
# order.py
db.execute("INSERT INTO orders (user, product, price) VALUES ('park', '모니터', 300000)")

# report.py
total = db.execute("SELECT SUM(price) FROM orders")

# delivery.py
db.execute("SELECT * FROM orders WHERE user = 'kim'")
```

| 문제 | 파일 직접 | DBMS가 하는 일 |
| --- | --- | --- |
| 1. 모양을 바꾸면 깨짐 | 모양을 아는 곳이 세 군데 | 모양은 DBMS만 앎. 코드는 `price`처럼 **이름**으로 요청. 쿠폰 칸(`ALTER TABLE orders ADD COLUMN coupon`)을 넣어도 `report.py`는 그대로 |
| 2. 많으면 느림 | 처음부터 읽음 | "id가 몇 번이면 파일 어디"라는 목록(**인덱스**)으로 바로 감 |
| 3. 동시에 쓰면 망가짐 | 각자 열어서 끼어듦 | 모든 요청이 DBMS 한 곳을 거치고, DBMS가 **한 명씩** 순서를 정함. 여러 변경은 "전부 되거나 전부 안 되거나"(**트랜잭션**)로 묶음 |

## 5. 우리 과제에서

| 문제 | 우리가 만드는 것 | 설계 단계 |
| --- | --- | --- |
| 1. 모양을 바꾸면 깨짐 | SQL 처리기: SQL을 읽고, 파일 모양은 처리기만 앎 | 1, 4~9 |
| 2. 많으면 느림 | B+ 트리 인덱스: `WHERE id = ?`를 바로 찾음 | 2, 10~14 |
| 3. 동시에 쓰면 망가짐 | 서버 + lock: 모든 요청을 한 곳에서 한 문장씩 처리 | 3, 15~16 |

트랜잭션(여러 변경을 하나로 묶기)은 과제 범위 밖입니다. 단계별 내용은 [설계](../../DESIGN.md), SQL 문장 하나가 처리되는 과정은 [전체 그림](../OVERVIEW.md)에 있습니다.
