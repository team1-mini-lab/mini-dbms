## 0. 큰 그림: DBMS는 SQL 한 줄을 어떻게 처리하나

실제 DB(PostgreSQL, MySQL)도 큰 흐름은 같습니다.

```
SQL 문자열
  → 토크나이저 : 글자를 단어로 자름            "SELECT name FROM users" → SELECT | name | FROM | users
  → 파서       : 단어를 명령 구조로 만듦         → Select(table="users", columns=["name"])
  → 플래너     : 어떻게 찾을지 고름              → "id로 찾으니 목차를 쓰자" 또는 "처음부터 읽자"
  → 실행기     : 고른 방법대로 실제로 실행함
  → 저장 엔진  : 파일을 읽고 씀
```

우리 프로젝트에서 각각에 해당하는 것:

| 실제 DB의 부분 | 우리 구현 | 우리는 얼마나 단순하게 하나 |
| --- | --- | --- |
| 토크나이저 | 4단계 | 알아보는 단어 종류가 적음 |
| 파서 | 5단계 | `INSERT`, `SELECT`, `WHERE 열 = 값`만 |
| 플래너 (어떻게 찾을지 고르기) | 실행기 안의 `if where.column == "id"` 한 줄 | 실제 DB는 여러 방법의 비용을 계산해서 고르지만, 우리는 "id면 목차, 아니면 처음부터" 규칙 하나 |
| 실행기 | 1, 6, 9단계 | |
| 저장 엔진 | 테이블 파일 (한 줄에 JSON 배열 하나) | 실제 DB는 파일을 일정 크기 덩어리(페이지)로 나누고 자주 쓰는 덩어리를 메모리에 올려 두지만(버퍼 풀), 우리는 줄 단위로 바로 읽고 씀 |
| 인덱스 (목차) | 메모리에 둔 B+ 트리 | 실제 DB는 목차도 파일에 저장하지만, 우리는 메모리에만 둠 |
| 동시 요청 처리 | Thread Pool + lock 하나 | 실제 DB는 행 하나씩 따로 잠그거나, 데이터 버전을 여러 개 두고 읽기는 잠그지 않음(MVCC). 우리는 엔진 전체를 lock 하나로 잠금 |

> 핵심 문장: "우리 미니 DBMS는 실제 DB의 처리 단계를 모두 갖추고, 각 단계를 가장 단순한 형태로 구현했다."

### 이 노트에 자주 나오는 말

| 말 | 뜻 |
| --- | --- |
| O(n) | 데이터가 n개일 때, 걸리는 일의 양이 n에 비례함. 10배 많아지면 10배 오래 걸림 |
| O(log n) | 데이터가 10배 많아져도 일의 양은 조금만 늘어남. 100만 건이어도 20번 안쪽 |
| O(1) | 데이터 수와 상관없이 일의 양이 거의 같음 |
| 레코드 | 데이터 하나. 테이블의 행 하나, 파일의 한 줄 |
| offset | 파일 맨 앞에서 몇 바이트째인지. "id 3 → 36"이면 36바이트째에서 그 줄이 시작함 |
| 스키마 | 테이블마다 어떤 열이 있고 각 열이 숫자인지 글자인지 적어 둔 것. 우리는 `schema.json` |

## 1. SQL 처리기 (1\~9단계)

### 1-1. 토크나이저: 글자를 단어로

`SELECT name FROM users WHERE age = 25;` 는 컴퓨터에게 그냥 글자들입니다. 먼저 의미 있는 조각(토큰)으로 자릅니다.

```
SELECT | name | FROM | users | WHERE | age | = | 25 | ;
키워드   이름    키워드  이름    키워드   이름  기호  숫자  기호
```

토큰은 보통 `(종류, 값)` 쌍으로 표현합니다. 예: `("키워드", "SELECT")`, `("숫자", 25)`. 구현 방법은 두 가지입니다.

- **정규식으로 한 번에**: 정규식은 "숫자가 하나 이상 이어진 것"처럼 글자 모양을 적는 규칙입니다. 토큰 종류마다 모양을 적어 `|`(또는)로 묶고, `re.finditer`로 앞에서부터 맞는 조각을 차례로 꺼냅니다.
- **한 글자씩 읽기**: 글자를 하나씩 보면서 "지금 따옴표 안인가, 숫자 안인가"를 변수에 들고 진행합니다. 이런 방식을 상태 기계라고 부릅니다.

```python
import re
TOKEN_RE = re.compile(r"""
    \s+                      |   # 공백 (버림)
    --[^\n]*                 |   # 주석 (버림)
    (?P<STRING>'(?:[^']|'')*') |
    (?P<NUMBER>-?\d+)          |
    (?P<IDENT>[A-Za-z_]\w*)    |
    (?P<SYMBOL>[(),;=*<>])
""", re.VERBOSE)
```

주의할 점:
- 문자열 `'It''s'` 안의 `''`는 작은따옴표 하나입니다.
- 문자열 안의 `;`는 문장 구분자가 아닙니다. 그래서 **`;`로 문장을 나누는 일은 토크나이저 이후에** 해야 정확합니다. (`split(";")`은 `'a;b'`를 깨뜨림 → 엣지 케이스 단골)
- 패턴에 안 맞는 글자(`@` 등)가 나오면 "몇 번째 글자에서 알 수 없는 문자"라고 오류를 내야 합니다.

### 1-2. 파서: 단어를 구조로 (재귀 하강)

파서는 토큰 목록이 문법에 맞는지 확인하면서 명령 구조를 만듭니다. 이 구조를 AST(추상 구문 트리)라고 부릅니다. `Select(table="users", columns=["name"], where=...)` 같은 것입니다.
문법을 먼저 적어 두면 코드가 거의 그대로 따라 나옵니다.

```
문장      := insert문 | select문
insert문  := INSERT INTO 이름 [ "(" 이름목록 ")" ] VALUES "(" 값목록 ")"
select문  := SELECT ( "*" | 이름목록 ) FROM 이름 [ WHERE 이름 "=" 값 ]
이름목록  := 이름 { "," 이름 }
값목록    := 값 { "," 값 }
```

**재귀 하강**: 문법 규칙 하나를 함수 하나로 만듭니다. 함수는 지금 토큰을 들여다보고(`peek`), 기대한 단어면 받아서 다음으로 넘어가고(`expect`), 아니면 "FROM이 와야 하는데 WHERE가 왔습니다" 같은 오류를 냅니다. `accept`는 "있으면 받고, 없으면 그냥 넘어감"입니다.

```python
def parse_select(self):
    self.expect("SELECT")
    columns = ["*"] if self.accept("*") else self.parse_name_list()
    self.expect("FROM")
    table = self.expect_ident()
    where = None
    if self.accept("WHERE"):
        col = self.expect_ident(); self.expect("="); val = self.parse_value()
        where = Where(col, "=", val)
    return Select(table, columns, where)
```

왜 "재귀"인가: 규칙이 다른 규칙을 부르기 때문입니다(`select문` → `이름목록`). 나중에 `WHERE a = 1 AND (b = 2 OR c = 3)`처럼 괄호가 중첩되면 함수가 자기 자신을 부르게 됩니다.

> 파서는 "문법"만 검사합니다. `users` 테이블이 실제로 있는지, `age`가 INT인지는 **실행기(또는 검증 단계)**가 스키마를 보고 확인합니다. 이 구분을 물어보면 답할 수 있어야 합니다.

### 1-3. 실행기

파서가 만든 구조(AST)를 받아서 실제로 실행합니다.

- `Insert` → 스키마로 열 수와 타입(숫자/글자) 확인 → id를 자동으로 붙임 → 파일 끝에 한 줄 추가(`append`)
- `Select` → `where`가 없으면 파일 전체를 처음부터 읽고(`scan`), 있으면 조건에 맞는 줄만 → 그중 요청한 열만 골라 돌려줌

용어 정리:
- **Selection(선택)**: 조건에 맞는 *행*을 고름 (`WHERE`)
- **Projection(투영)**: 필요한 *열*만 고름 (`SELECT name, age`)

### 1-4. 파일 기반 저장: 왜 JSON Lines인가

후보 비교:

| 포맷 | 장점 | 단점 |
| --- | --- | --- |
| CSV | 엑셀로 열림, 익숙함 | 쉼표·따옴표·줄바꿈이 든 값 처리가 까다롭고, 타입 정보가 없음 (전부 문자열) |
| JSON Lines (`[1,"현지",25]`) | 값 안의 쉼표나 따옴표를 `json`이 알아서 처리하고, 숫자와 글자가 구분되어 저장됨. 한 줄 = 레코드 하나 | CSV보다 조금 큼 |
| 고정 길이 바이너리 (모든 줄을 같은 바이트 수로) | N번째 레코드 위치 = N × 한 줄 크기로 바로 계산, 매우 빠름 | 긴 글자는 잘림, 메모장으로 못 열어서 만들기·고치기 어려움 |

JSON Lines를 고른 핵심 이유는 **값이 안전하게 저장되고, 위치(offset)를 알면 그 줄로 바로 가서 읽을 수 있기** 때문입니다.

```python
with open(path, "ab") as f:
    offset = f.tell()                 # tell = 지금 파일의 몇 바이트째인지. 곧 쓸 줄이 시작하는 위치
    f.write((json.dumps(row, ensure_ascii=False) + "\n").encode())
# 나중에
with open(path, "rb") as f:
    f.seek(offset)                    # seek = 그 바이트 위치로 바로 이동
    row = json.loads(f.readline())
```

- **바이너리 모드(`"ab"`, `"rb"`의 `b`)로 여는 이유**: 텍스트 모드에서는 `tell()`이 정확한 바이트 위치를 주지 않을 수 있습니다. 또 한글은 한 글자가 3바이트라서 "글자 수 ≠ 바이트 수"가 됩니다. 바이너리 모드는 바이트 그대로 다뤄서 위치가 정확합니다.
- **파일 끝에 덧붙이기만 하는(append-only) 이유**: 이미 쓴 줄은 절대 움직이지 않으니, 목차에 적은 offset이 계속 맞습니다. (쓰기가 많은 실제 DB 중에도 이렇게 덧붙이기만 하는 방식이 있습니다)

실제 DB와의 차이: 실제 DB는 파일을 **페이지**라는 일정 크기 덩어리(보통 4\~16KB)로 나누고, 레코드를 그 안에 나눠 담습니다. 디스크는 1바이트씩이 아니라 덩어리 단위로 읽기 때문입니다. 이것이 B+ 트리 노드 하나에 키를 많이 담는 이유로 이어집니다(2-6).

### 1-5. flush와 fsync (알아두면 좋은 것)

`f.write()`를 해도 바로 디스크에 써지지 않고, 중간에 잠시 모아 두는 곳(버퍼)을 거칩니다.

```
파이썬 버퍼 → (flush) → OS 페이지 캐시 → (fsync) → 실제 디스크
```

- `flush`는 파이썬이 모아 둔 것을 운영체제(OS)에 넘기는 것, `fsync`는 운영체제가 실제 디스크에 쓰게 하는 것입니다.
- 우리 프로그램이 죽어도 운영체제가 살아 있으면 flush까지 된 데이터는 남습니다.
- 전원이 나가도 남기려면 fsync가 필요하지만 매우 느립니다.
- 100만 건 삽입 시 매번 flush/fsync하면 엄청 느려집니다 → 그래서 "파일을 열어 둔 채 쓰고 끝에 한 번 flush"(설계 13단계, 100만 건 넣기).

## 2. B+ 트리 인덱스 (10\~14단계)

### 2-1. 인덱스가 없으면: 선형 탐색

`SELECT * FROM users WHERE id = 777777;`
인덱스가 없으면 파일의 첫 줄부터 끝까지 읽으며 `id == 777777`인지 확인해야 합니다. → **O(n)** (데이터가 10배면 시간도 10배)
100만 건이면 최악 100만 줄을 읽고, 각 줄을 `json.loads`로 풀어 보는 일을 100만 번 합니다.

그래서 "id 777777 → 파일의 41,203,550바이트째"처럼 키와 위치를 미리 정리해 둡니다. 이것이 인덱스(목차)입니다.

### 2-2. 왜 하필 B+ 트리인가 (후보 비교)

| 자료구조 | 하나 찾기 `id = 5` | 범위 찾기 `id > 5` | 순서대로 읽기 | 비고 |
| --- | --- | --- | --- | --- |
| 정렬 안 된 배열 | O(n) | O(n) | 불가 | 선형 탐색 |
| 해시 테이블 (미니 레디스!) | **O(1)** | 불가 (전부 훑어야) | 불가 | 순서가 없음 |
| 이진 탐색 트리 (노드마다 키 1개, 자식 2개) | O(log n), 최악 O(n) | 가능 | 가능 | 1, 2, 3…처럼 순서대로 넣으면 한쪽으로만 길게 늘어져 처음부터 읽는 것과 같아짐 |
| 균형 이진 트리 (AVL, 레드블랙: 한쪽으로 안 늘어지게 스스로 맞추는 이진 트리) | O(log₂ n) | 가능 | 가능 | 노드 하나에 키 하나 → 트리가 깊음 |
| **B+ 트리** | O(log_m n) (m = 노드 하나의 자식 수) | **매우 좋음** | **매우 좋음** | 노드 하나에 키 여러 개 → 트리가 얕음 |

**해시 테이블과 비교하는 질문이 반드시 나옵니다.** 지난 과제에서 해시 테이블을 만들었으니 이렇게 연결하면 좋습니다.
> "해시는 `=` 조회는 더 빠르지만 순서를 잃습니다. DB는 범위 조회, 정렬(`ORDER BY`), 최솟값·최댓값이 흔해서 순서를 유지하는 B+ 트리를 기본 인덱스로 씁니다."

### 2-3. B+ 트리의 모양

```
                    [ 30 | 60 ]                 ← 내부 노드(위쪽): 길 안내용 키만
                  /      |      \
        [10 | 20]    [30 | 45]    [60 | 75 | 90]  ← 리프 노드(맨 아래): 실제 키 + 값(파일 위치)
           ↔             ↔              ↔          ← 리프끼리 옆으로 연결
```

규칙:
1. **모든 값(파일 위치)은 리프(맨 아래 노드)에만** 있습니다. 내부 노드의 키는 "이 키 이상은 오른쪽으로" 같은 길 안내용 복사본입니다.
2. **모든 리프는 같은 깊이**입니다. (항상 균형)
3. 노드는 최대 m-1개의 키를 가집니다 (m = 차수 = 노드 하나가 가질 수 있는 자식 수). 넘치면 반으로 **나눕니다(split)**.
4. **리프끼리 옆으로 이어져 있어서**(각 리프가 "다음 리프"를 가리킴), 범위 찾기는 시작 리프만 찾고 옆으로 쭉 읽으면 됩니다.

**B 트리와 B+ 트리의 차이** (자주 묻는 질문):

| | B 트리 | B+ 트리 |
| --- | --- | --- |
| 값의 위치 | 모든 노드 | 리프에만 |
| 리프 연결 | 없음 | 있음 |
| 범위 조회 | 트리를 위아래로 오가야 함 | 리프를 옆으로 읽으면 끝 |
| 내부 노드 | 값까지 들어서 키가 적게 들어감 | 키만 있어서 더 많이 들어감 → 더 얕음 |

### 2-4. 검색

루트(맨 위 노드)부터 시작해서, 노드 안의 키들과 비교해 내려갈 자식을 고르고, 리프에 도착하면 그 안에서 찾습니다. `bisect`는 정렬된 리스트에서 "이 값이 몇 번째 자리에 들어가야 하나"를 빠르게 찾는 파이썬 표준 함수입니다.

```python
def search(self, key):
    node = self.root
    while not node.is_leaf:
        i = bisect.bisect_right(node.keys, key)   # key 이하인 키 개수 = 내려갈 자식 번호
        node = node.children[i]
    i = bisect.bisect_left(node.keys, key)
    if i < len(node.keys) and node.keys[i] == key:
        return node.values[i]
    return None
```

`bisect_right`를 쓰는 이유: 내부 노드 키 `30`은 "30 이상은 오른쪽"이라는 뜻이라, 30을 찾을 때 오른쪽 자식으로 가야 합니다.

### 2-5. 삽입과 분할 (손으로 그려보기)

차수 4 (노드당 최대 키 3개)로 1, 2, 3, 4, 5, 6을 넣어봅니다.

```
1,2,3 삽입:     [1 2 3]

4 삽입 → 넘침:  [1 2 3 4]  → 반으로 나눔
                    [3]                ← 오른쪽 리프의 첫 키를 부모로 "복사"
                  /     \
              [1 2]  ↔  [3 4]

5 삽입:             [3]
                  /     \
              [1 2]  ↔  [3 4 5]

6 삽입 → 넘침:  [3 4 5 6] → [3 4] [5 6], 5를 부모로 복사
                   [3 | 5]
                 /    |    \
             [1 2] ↔ [3 4] ↔ [5 6]
```

**리프 분할 vs 내부 노드 분할 차이** (구현에서 제일 헷갈리는 부분):
- **리프 분할**: 가운데 키를 부모로 **복사**합니다 (리프에도 남음). 값은 리프에 있어야 하니까.
- **내부 노드 분할**: 가운데 키를 부모로 **올려 보냅니다** (내부 노드에서 빠짐). 길 안내용이니 중복될 필요가 없음.
- 루트가 분할되면 새 루트가 생기고 **트리 높이가 1 늘어납니다**. B+ 트리는 아래가 아니라 **위로 자랍니다**. 그래서 항상 균형이 유지됩니다.

> 연습: 차수 4로 10, 20, 5, 6, 12, 30, 7, 17을 직접 그려보고, 코드 출력과 비교하기.

### 2-6. 왜 이렇게 넓적한가: 높이 계산

디스크는 한 번 읽을 때 일정 크기 덩어리(예: 8KB)를 통째로 읽습니다. 디스크 읽기 한 번이 메모리에서 값 비교 수만 번보다 느리므로, **한 번 읽을 때 최대한 많은 키를 가져와 트리를 얕게**(층 수를 적게) 만드는 것이 목표입니다.

높이(층 수) ≈ log_m(n). m이 클수록 층이 적습니다.

| 레코드 수 n | 이진 트리 (m=2) | B+ 트리 m=100 | B+ 트리 m=500 |
| --- | --- | --- | --- |
| 1만 | 약 14 | 2 | 2 |
| 100만 | 약 20 | 3 | 3 |
| 1억 | 약 27 | 4 | 3 |

→ 1억 건이어도 디스크를 3\~4번만 읽으면 찾습니다.

**우리는 메모리 기반이라** 디스크 읽기 비용이 없습니다. 그래서 차수를 바꿔도 체감 차이가 디스크 DB만큼 크지 않습니다. 이 점을 성능 결과와 함께 설명하면 이해도가 드러납니다.
(차수가 너무 크면 노드 안의 리스트 중간에 키를 끼워 넣을 때(`list.insert`) 뒤의 키를 다 밀어야 해서 느려지고, 너무 작으면 트리가 깊어집니다 → 실험해서 적당한 값 찾기)

### 2-7. 우리 인덱스가 저장하는 것: ID → 파일 위치

```
B+ 트리: 777777 → 41,203,550 (바이트 위치)
          ↓
파일:    f.seek(41203550); f.readline()  → [777777, "user777777", 42]
```

- 레코드 전체가 아니라 위치만 저장하므로 메모리가 적게 듭니다.
- 실제 DB 용어로는 **보조 인덱스**(목차에 위치만 담는 방식)에 가깝습니다. MySQL의 기본 키 인덱스는 리프에 행 전체를 담는 **클러스터드 인덱스**라서 다릅니다.
- 메모리 기반이라 서버를 껐다 켜면 인덱스가 사라집니다 → 시작할 때 파일을 한 번 훑어 재구성. 원본은 항상 파일이므로 둘이 어긋날 일이 없습니다.

### 2-8. 성능 비교를 제대로 하는 법

비교 대상:
- `SELECT * FROM users WHERE id = ?` → B+ 트리 → O(log n) + 한 줄 읽기
- `SELECT * FROM users WHERE name = ?` → 선형 탐색 → O(n)

측정할 때 주의:
1. **`time.perf_counter()`** 사용. 짧은 시간을 정밀하게 재는 함수입니다. `time.time()`은 덜 정밀하고, 컴퓨터 시계를 맞추면 값이 튈 수 있습니다.
2. **여러 번 측정**해 평균·최댓값. 한 번만 재면 우연에 좌우됩니다(운영체제가 파일을 메모리에 올려 뒀는지, 파이썬이 마침 안 쓰는 메모리를 정리했는지 등).
3. **무작위 ID**로. 앞쪽 ID만 찾으면 선형 탐색도 금방 끝나서 불공평.
4. **첫 실행은 따로**: 처음엔 운영체제가 파일을 아직 메모리에 올려 두지 않아서 느립니다. 한 번 돌려 두고(warm-up) 잽니다.
5. **데이터 크기를 바꿔가며**: 1만 → 10만 → 100만. 인덱스는 거의 그대로, 선형은 10배씩 느려지는 모양이 나와야 O(log n) vs O(n)이 보입니다. **숫자 하나보다 "늘어나는 모양"이 설득력 있습니다.**

선형 탐색(처음부터 읽기) 시간에는 "비교"보다 "파일 읽기 + 각 줄을 `json.loads`로 풀기"가 대부분입니다. 이걸 짚을 수 있으면 좋습니다.

## 3. API 서버와 Thread Pool (3, 15\~17단계)

### 3-1. 프로세스와 스레드

- **프로세스**: 실행 중인 프로그램 하나. `python3 server.py`를 실행하면 프로세스 하나가 생깁니다. 프로세스끼리는 메모리(변수)를 따로 씁니다.
- **스레드**: 프로세스 안에서 동시에 돌아가는 실행 흐름. 한 프로세스 안의 스레드들은 **같은 변수를 함께 씁니다** → 데이터를 쉽게 나눠 쓰지만, 동시에 같은 변수를 고치면 문제가 생깁니다.

우리 서버의 모든 스레드는 같은 B+ 트리, 같은 `next_id`, 같은 열린 파일을 함께 씁니다.

### 3-2. 요청마다 스레드 vs Thread Pool

**요청마다 새 스레드**
```
요청 → 스레드 생성 → 처리 → 스레드 종료
```
- 스레드 생성·종료 비용이 매번 듦.
- 요청이 1만 개 몰리면 스레드 1만 개 → 메모리가 크게 늘고, CPU가 스레드를 바꿔 가며 실행하는 일(문맥 전환)에 시간을 낭비하고, 최악엔 서버가 죽습니다.

**Thread Pool**
```
              ┌→ 작업 스레드 1 ─┐
요청 → 큐 ───┼→ 작업 스레드 2 ─┼→ 응답
              └→ 작업 스레드 N ─┘
```
- 스레드를 **미리 N개** 만들어 두고 재사용.
- 동시에 처리하는 개수가 **N개로 제한**되어 서버가 버팀.
- 넘치는 요청은 큐(줄)에서 대기. 큐도 가득 차면 503(서버가 바쁨)으로 거절해서 서버가 쓰러지지 않게 합니다.

이 구조를 **생산자-소비자 패턴**이라고 부릅니다. 일을 만드는 쪽(서버)은 요청을 큐에 넣고, 일을 하는 쪽(작업 스레드)은 꺼내서 처리합니다.

```python
import queue, threading

class ThreadPool:
    def __init__(self, n, max_queue=100):
        self.tasks = queue.Queue(maxsize=max_queue)
        for i in range(n):
            threading.Thread(target=self._worker, name=f"worker-{i}", daemon=True).start()

    def _worker(self):
        while True:
            func, args = self.tasks.get()      # 큐가 비면 여기서 잠듦 (CPU 안 씀)
            try:
                func(*args)
            finally:
                self.tasks.task_done()

    def submit(self, func, *args):
        self.tasks.put_nowait((func, args))    # 가득 차면 queue.Full → 503
```

`queue.Queue`는 안에 lock이 들어 있어서 여러 스레드가 동시에 넣고(`put`) 꺼내도(`get`) 안전합니다. 이런 걸 thread-safe라고 합니다. 우리가 lock을 따로 걸 필요가 없는 부분입니다.

**`http.server`와 연결하기**: 파이썬의 `ThreadingHTTPServer`는 요청마다 새 스레드를 만듭니다(요청마다 스레드 방식). 우리는 `HTTPServer`를 물려받은 클래스를 만들고, 요청을 받았을 때 불리는 함수 `process_request`를 우리 것으로 바꿔서(오버라이드) 그 안에서 `pool.submit(...)`으로 넘깁니다. 그러면 "HTTP 해석은 표준 라이브러리, 동시 처리는 직접 만든 Thread Pool" 구조가 됩니다.

### 3-3. 경쟁 상태(race condition): 실제로 깨지는 예

경쟁 상태는 두 스레드가 같은 데이터를 동시에 고칠 때, 누가 먼저 실행되느냐에 따라 결과가 달라지고 틀어지는 것입니다.

lock 없이 두 스레드가 동시에 `INSERT`하면:

**① ID 중복**
```
스레드 A: id = self.next_id      (100 읽음)
스레드 B: id = self.next_id      (100 읽음)   ← A가 증가시키기 전에 끼어듦
스레드 A: self.next_id = id + 1  (101)
스레드 B: self.next_id = id + 1  (101)
→ 두 레코드 모두 id 100. 하나는 인덱스에서 덮어써져 사라짐
```

**② 파일 위치 꼬임** (`f.tell()` = 지금 쓸 위치)
```
스레드 A: offset = f.tell()  → 500
스레드 B: offset = f.tell()  → 500
스레드 A: f.write(...)       → 500~530에 기록
스레드 B: f.write(...)       → 530~560에 기록
→ B의 인덱스는 500을 가리키지만 실제 B의 레코드는 530에 있음. 엉뚱한 레코드를 반환
```

**③ B+ 트리 나누기 도중 읽기**
노드를 반으로 나누는 도중(키는 옮겼는데 부모는 아직 갱신 안 됨)에 다른 스레드가 검색하면, 있는 키를 못 찾을 수 있습니다.

> 이 세 가지는 "읽기 → 계산 → 쓰기"가 **중간에 끊기지 않는 한 덩어리로 실행되지 않아서** 생깁니다(이렇게 끊기지 않는 걸 "원자적"이라고 함). lock은 이 덩어리를 한 번에 한 스레드만 실행하게 만듭니다. lock으로 감싼 부분을 임계 구역(critical section)이라고 부릅니다.

### 3-4. lock 전략

```python
class Engine:
    def __init__(self):
        self._lock = threading.Lock()
    def execute(self, sql):
        with self._lock:          # 들어갈 때 잠그고 나올 때 풂. 중간에 오류가 나도 with가 자동으로 풀어 줌
            return self._execute(sql)
```

| 전략 | 동작 | 장점 | 단점 |
| --- | --- | --- | --- |
| **엔진 전체에 lock 하나** (우리 기본) | 한 번에 SQL 한 문장만 | 단순, 확실, 교착 상태(아래 설명)가 생길 수 없음 | 읽기끼리도 기다림 |
| 읽기/쓰기 lock (RWLock) | 읽기는 여럿 동시, 쓰기는 혼자 | 읽기가 많을 때 빠름 | 구현 복잡. 읽기가 끝없이 들어오면 쓰기가 계속 못 들어가는 문제(starvation) 주의 |
| 테이블별 lock | 다른 테이블은 동시에 | 테이블 많으면 효과 | 여러 테이블 쓰면 교착 위험 |
| 실제 DB: 행 하나씩 잠그기, MVCC | 데이터 버전을 여러 개 두고, 읽기는 잠그지 않고 옛 버전을 읽음 | 동시 처리 최고 | 매우 복잡 |

**"lock이 하나면 Thread Pool이 의미가 있나?"** — 꼭 나오는 질문입니다. 답:
> "엔진 실행은 한 번에 하나지만, HTTP 요청 받기·본문 읽기·JSON 해석·응답 보내기는 lock 밖에서 병렬로 일어납니다. 그리고 lock 구조가 맞는지 먼저 확실히 한 뒤, 읽기/쓰기 lock으로 읽기 병렬화를 다음 단계로 둡니다."

**lock을 엔진 안에 두는 이유**: 서버 코드에 두면 CLI나 나중에 추가하는 진입점에서 빠뜨릴 수 있습니다. 데이터를 가진 쪽(엔진)이 자기 데이터를 지켜야 한다는 원칙입니다(캡슐화).

**교착 상태(deadlock)**: 스레드 A는 lock1을 쥐고 lock2를 기다리고, B는 lock2를 쥐고 lock1을 기다리면 둘 다 영원히 멈춤. lock이 하나뿐이면 원천적으로 안 생깁니다. lock을 여러 개 쓰게 되면 **항상 같은 순서로 잡기**가 해결책입니다.

### 3-5. 파이썬 GIL: 알아야 하는 만큼만

**GIL(Global Interpreter Lock)**: 우리가 쓰는 보통의 파이썬(CPython)은 한 순간에 한 스레드만 파이썬 코드를 실행합니다. 스레드가 여러 개여도 번갈아 가며 실행합니다.

자주 나오는 오해 두 가지:

1. **"GIL이 있으니 lock이 필요 없다"** → 틀림.
   파이썬 코드 한 줄은 안에서 더 잘게 쪼개진 명령(바이트코드) 여러 개로 실행되고, GIL은 그 잘게 쪼갠 명령 *하나*씩만 지켜 줍니다. `self.next_id += 1`은 읽기·더하기·쓰기 세 명령이라 그 사이에 다른 스레드로 바뀔 수 있습니다. 3-3의 문제는 GIL이 있어도 그대로 생깁니다.

2. **"GIL 때문에 스레드는 쓸모없다"** → 반만 맞음.
   계산만 하는 작업(파싱, 트리 탐색)은 동시에 실행되지 않습니다. 하지만 **입출력(I/O: 네트워크로 받기, 파일 읽기)을 기다리는 동안에는 GIL을 놓아서** 다른 스레드가 실행됩니다. 그래서 웹 서버처럼 I/O가 많은 일에는 스레드가 효과가 있습니다.

> 발표 한 줄: "파이썬은 GIL 때문에 CPU 작업이 진짜 병렬로 돌지는 않지만, 네트워크 I/O를 겹쳐 처리하는 효과가 있고, GIL과 무관하게 공유 데이터에는 lock이 필요합니다."
> (참고: 파이썬 3.13부터 GIL 없는 실험 빌드가 있습니다. 그 환경에서도 우리 lock 설계는 그대로 맞습니다.)

### 3-6. API 설계에서 생각할 것

- **왜 `POST /query` 하나인가**: SQL 안에 동작(INSERT인지 SELECT인지)이 이미 들어 있으므로, 흔한 웹 API처럼 `/users/1`, `/orders/5`로 주소를 나눌 필요가 없습니다. 실제 DB의 HTTP 인터페이스(ClickHouse, BigQuery 등)도 이런 형태가 많습니다.
- **SQL을 주소 뒤(`/query?sql=SELECT...`)에 안 붙이는 이유**: 주소 길이 제한이 있고, 주소는 서버 기록에 그대로 남고, 공백·따옴표를 특수하게 바꿔 적어야 해서 불편합니다.
- **상태 코드**(응답에 붙는 숫자): 보낸 쪽 실수(문법 오류)는 400, 서버가 바쁨은 503, 우리 코드 버그는 500. 요청을 보낸 쪽이 "고쳐서 보낼지, 잠시 뒤 다시 보낼지"를 판단할 수 있게 구분합니다.
- **보안 주의(발표 때 언급하면 좋음)**: 이 API는 SQL을 그대로 받으므로 아무나 쓰면 안 됩니다. 실제 서비스라면 로그인 같은 인증이 필요하고, 사용자가 입력한 글자에 SQL을 몰래 섞어 넣는 공격(SQL 인젝션)을 막아야 합니다. 그 방법이 **파라미터 바인딩**입니다. SQL에는 `WHERE id = ?`처럼 자리만 두고, 값은 따로 넘깁니다.

### 설명해 보기 (API 서버)
- [ ] 요청마다 스레드를 만드는 방식의 문제점은?
- [ ] Thread Pool에서 큐가 하는 역할은? 가득 차면?

- [ ] 교착 상태는 언제 생기고, 우리 구조에서는 왜 안 생기나?

## 4. 엣지 케이스 체크리스트

구현하면서 하나씩 테스트로 만들면 R17이 자동으로 채워집니다.

**파싱**
- [ ] 빈 파일, 공백·주석만 있는 파일
- [ ] 마지막 문장에 `;` 없음
- [ ] 키워드 소문자 `select * from users;`
- [ ] 문자열 안의 `;`, `,`, `''`, 한글, 줄바꿈
- [ ] 닫히지 않은 문자열 `'abc`
- [ ] 알 수 없는 문자 `@`
- [ ] 음수 `-5`, 아주 큰 수

**의미**
- [ ] 없는 테이블, 없는 열
- [ ] 열 수와 값 수 불일치
- [ ] 타입 불일치 (`age`에 `'abc'`)
- [ ] `INSERT`에 `id` 직접 지정
- [ ] `WHERE id = 'abc'`, `WHERE id = 0`, 없는 ID

**저장/인덱스**
- [ ] 빈 테이블에서 `SELECT`
- [ ] 첫 `INSERT`의 ID가 1
- [ ] 재시작 후 ID 이어짐, 인덱스 재구성
- [ ] 파일 마지막 줄이 깨져 있음 (쓰다가 죽은 경우) → 어떻게 할지 정하기
- [ ] B+ 트리: 정순·역순·무작위 삽입 모두 검색됨, 분할 경계(정확히 꽉 찼을 때)

**서버**
- [ ] 본문이 JSON이 아님, `sql` 키 없음, `sql`이 문자열이 아님
- [ ] 동시 `INSERT` 100개 → ID가 1\~100 빠짐없이, 중복 없이
- [ ] 동시 읽기·쓰기 섞어도 오류 없음
- [ ] 큐가 가득 찼을 때 503

## 5. 발표·면접 예상 질문 빠른 답

| 질문 | 한두 문장 답 |
| --- | --- |
| 전체 구조를 설명해 주세요 | SQL 문자열 → 토크나이저 → 파서 → 실행기 → 파일 저장소/B+ 트리. CLI와 API 서버가 같은 `execute`를 호출합니다. |
| 인덱스를 쓰면 얼마나 빨라졌나요? | (실측 숫자) + "데이터가 10배 늘 때 선형은 10배, 인덱스는 거의 그대로"라는 모양 |
| 왜 B+ 트리? | 순서 유지로 범위 조회가 되고, 넓적해서 얕습니다. 해시는 `=`만 빠릅니다. |
| 메모리 기반의 한계는? | 재시작 시 재구성 시간, 메모리 크기 제한. 인덱스 저장(설계 24단계)이나 디스크 페이지 기반으로 확장 가능합니다. |
| 다른 필드에도 인덱스를 걸려면? | 같은 B+ 트리를 열별로 하나 더 두면 됩니다. 단, 값이 중복될 수 있어 키 → 위치 *목록*으로 바꿔야 하고, `INSERT`마다 모든 인덱스를 갱신하는 비용이 늡니다. |
| 동시성은 어떻게 보장했나요? | 엔진 전체를 lock 하나로 감싸 쿼리를 한 번에 하나씩 실행합니다. 테스트로 동시 INSERT 시 ID 중복이 없음을 확인했습니다. |
| 가장 어려웠던 부분은? | (예) B+ 트리 분할에서 리프는 복사, 내부 노드는 올려보내는 차이 / 파일 offset과 한글 바이트 수 |
| AI가 짠 코드를 어떻게 검증했나요? | 단위 테스트, 손으로 그린 B+ 트리와 출력 비교, 경쟁 상태 재현 테스트 |

## 6. 더 알아보기 (시간 날 때)

과제에는 필요 없지만, 실제 DB가 어떻게 더 나아갔는지 궁금할 때 찾아볼 주제입니다.

| 주제 | 한 줄 설명 |
| --- | --- |
| 페이지와 버퍼 풀 | 실제 DB는 파일을 일정 크기 덩어리(페이지)로 나누고, 자주 쓰는 덩어리를 메모리에 올려 둠. 디스크 기반 B+ 트리는 노드 하나 = 페이지 하나 |
| WAL (Write-Ahead Log) | 데이터를 고치기 전에 "무엇을 고칠지"를 기록 파일에 먼저 씀. 중간에 꺼져도 그 기록을 보고 복구함 |
| MVCC | 데이터를 고칠 때 옛 버전을 남겨 두고, 읽는 쪽은 잠그지 않고 옛 버전을 읽게 함. PostgreSQL이 쓰는 방식 |
| LSM 트리 | 쓰기가 아주 많은 DB(RocksDB, Cassandra)가 B+ 트리 대신 쓰는 구조. 일단 메모리에 모았다가 파일에 한꺼번에 덧붙임 |
| 쿼리 옵티마이저 | 어떻게 찾을지 비용을 계산해 고르는 부분. 조건에 맞는 행이 대부분이면 목차보다 처음부터 읽는 게 더 빠를 수도 있음 |
