# 미니 DBMS 전체 그림

미니 DBMS가 하는 일을 가장 작은 예시로 처음부터 끝까지 따라가는 문서입니다.
미니 DBMS가 왜 필요한지와 세 Phase의 관계는 `OVERVIEW_DBMS.md`, 범위와 접점은 `DESIGN.md`를 참고합니다.

## 1. 한눈에 보기

```
외부 프로그램 (CLI의 SQL 파일 / HTTP 요청)
   │ SQL 문장 ("INSERT ...", "SELECT ... WHERE id = 3")
   ▼
서버: 요청 접수 → 작업 큐 → Thread Pool의 스레드가 꺼내서 처리      [Phase 3]
   ▼
lock: 한 번에 한 문장만 엔진에 진입                                 [Phase 3]
   ▼
엔진: 토크나이저 → 파서 → 실행기                                    [Phase 1]
   ├─ WHERE id = ? 이면 → B+ 트리로 파일 위치 찾기 → 그 줄만 읽기    [Phase 2]
   └─ 그 밖의 조건이면  → 파일을 처음부터 끝까지 읽기 (선형 탐색)     [Phase 1]
   ▼
테이블 파일: 한 줄에 레코드 하나, 끝에 추가만 함                     [Phase 1]
```

데이터 생성기와 성능 비교는 이 엔진을 사용하는 바깥쪽 프로그램입니다.

## 2. 장면별로 따라가기

테이블은 이미 있다고 가정합니다. `schema.json`에 다음과 같이 적혀 있고, 데이터 파일 `users.tbl`은 비어 있습니다.

```json
{ "users": [["id", "INT"], ["name", "TEXT"], ["age", "INT"]] }
```

```
users.tbl:  (비어 있음)
B+ 트리:    (비어 있음)
다음 ID:    1
```

### 장면 1: SQL 받기

`queries.sql` 파일에 SQL 문장이 적혀 있고, CLI로 처리기에 넘깁니다.

```sql
-- queries.sql
INSERT INTO users (name, age) VALUES ('현지', 25);
SELECT * FROM users WHERE id = 1;
```

```bash
python -m minidb run queries.sql
```

처리기는 파일을 읽어 문장을 하나씩 처리합니다. 문장은 `;`로 나뉘지만, `'a;b'`처럼 **문자열 안의 `;`**도 있을 수 있어서, 글자 그대로 `;`로 자르지 않고 다음 장면에서 토큰으로 자른 뒤에 나눕니다.

### 장면 2: 토큰으로 자르기

컴퓨터에게 SQL은 그냥 글자들입니다. 먼저 의미 있는 조각(토큰)으로 자릅니다.

```
INSERT | INTO | users | ( | name | , | age | ) | VALUES | ( | '현지' | , | 25 | ) | ;
키워드   키워드  이름   기호  이름  기호 이름 기호   키워드  기호  문자열  기호 숫자 기호 기호
```

- 키워드는 대소문자를 가리지 않습니다 (`insert`도 `INSERT`).
- 문자열은 작은따옴표로 감싸고, 안의 작은따옴표는 `''`로 씁니다 (`'It''s'`).
- `--` 뒤는 주석이라 버립니다.
- 규칙에 맞지 않는 글자(`@` 등)가 나오면 여기서 오류를 냅니다.

### 장면 3: 구조로 만들기 (파싱)

토큰이 문법에 맞는지 확인하면서, 실행기가 쓰기 좋은 구조로 바꿉니다.

```
INSERT INTO users (name, age) VALUES ('현지', 25);
   ↓
Insert(table="users", columns=["name", "age"], values=["현지", 25])

SELECT * FROM users WHERE id = 1;
   ↓
Select(table="users", columns=["*"], where=Where("id", "=", 1))
```

- 문법은 "INSERT 다음엔 INTO, 그다음엔 이름..."처럼 정해진 순서입니다. 앞에서부터 토큰을 하나씩 확인하며 기대한 것이 아니면 오류를 냅니다 (재귀 하강 파서).
- 파서는 **문법만** 봅니다. `users` 테이블이 실제로 있는지, `age`가 숫자인지는 다음 장면에서 실행기가 스키마를 보고 확인합니다.

### 장면 4: INSERT 실행

`Insert(users, [name, age], ["현지", 25])`를 받은 실행기가 하는 일입니다.

1. 스키마와 비교합니다: `users` 테이블이 있고, `name`은 TEXT, `age`는 INT로 맞습니다.
2. ID를 부여합니다: 다음 ID가 1이므로 `id = 1`, 다음 ID는 2가 됩니다.
3. 파일 끝의 위치를 기억한 뒤, 한 줄을 추가합니다. 파일이 비어 있으므로 위치는 0바이트입니다.
4. B+ 트리에 "ID 1 → 0바이트"를 등록합니다.

```
users.tbl:
  0바이트  [1, "현지", 25]

B+ 트리:  1 → 0
다음 ID:  2
```

같은 방식으로 두 명을 더 넣으면 이렇게 됩니다. 한 줄이 18바이트라 위치가 18씩 늘어납니다. (한글은 한 글자에 3바이트)

```
users.tbl:
   0바이트  [1, "현지", 25]
  18바이트  [2, "민수", 31]
  36바이트  [3, "지영", 28]

B+ 트리:  1 → 0,  2 → 18,  3 → 36
다음 ID:  4
```

- 파일 끝에 **추가만** 하므로, 이미 쓴 줄의 위치는 절대 바뀌지 않습니다. 그래서 B+ 트리에 적어 둔 위치가 계속 맞습니다.
- 한 줄을 JSON 배열로 쓰는 이유는 `"키보드, 무선"`처럼 쉼표가 든 값도 안전하게 저장되기 때문입니다.

### 장면 5: 다른 필드로 SELECT (선형 탐색)

`SELECT * FROM users WHERE name = '지영';`

`name`에는 인덱스가 없으므로 파일을 처음부터 끝까지 읽으며 비교합니다.

```
0바이트   [1, "현지", 25]   name이 "지영"인가? 아니오
18바이트  [2, "민수", 31]   아니오
36바이트  [3, "지영", 28]   예 → 결과에 추가
(끝까지 계속 읽음. 같은 이름이 또 있을 수 있으므로)
```

레코드가 3개면 3줄, 100만 개면 100만 줄을 읽습니다. 데이터가 늘어나는 만큼 그대로 느려집니다.

### 장면 6: ID로 SELECT (인덱스)

`SELECT * FROM users WHERE id = 3;`

조건이 `id = ?`이므로 실행기는 B+ 트리를 씁니다.

1. B+ 트리에서 3을 찾습니다 → 36바이트
2. 파일의 36바이트 위치로 바로 이동해서 그 한 줄만 읽습니다 → `[3, "지영", 28]`

다른 줄은 읽지 않습니다. 레코드가 100만 개여도 B+ 트리를 3~4층만 내려가고 한 줄만 읽습니다. 이것이 Phase 2의 핵심입니다.

```
결과: {"columns": ["id", "name", "age"], "rows": [[3, "지영", 28]], "used_index": true}
```

### 장면 7: B+ 트리가 자라는 모습

노드 하나에 키를 최대 3개까지 담는 작은 B+ 트리로, ID 1~6을 차례로 넣어 봅니다.

```
1, 2, 3 넣기:      [1 2 3]

4 넣기 → 넘침:     [1 2 3 4]를 반으로 나누고, 오른쪽의 첫 키(3)를 위로 복사
                      [3]
                     /   \
                 [1 2] ↔ [3 4]

5, 6 넣기 → 넘침:  [3 4 5 6]을 나누고 5를 위로 복사
                     [3 | 5]
                    /   |   \
                [1 2]↔[3 4]↔[5 6]
```

- 실제 값(파일 위치)은 **맨 아래 칸(리프)에만** 있고, 위쪽 칸은 "3 이상은 오른쪽으로" 같은 **길 안내용**입니다.
- 넘치면 반으로 나누고 위로 올리기 때문에, 트리는 아래가 아니라 **위로 자랍니다**. 그래서 모든 리프의 깊이가 항상 같습니다 (항상 균형).
- 리프끼리 옆으로 이어져 있어서, `id`가 2~5인 레코드처럼 범위를 찾을 때 시작 리프만 찾고 옆으로 읽으면 됩니다.

ID 3을 찾을 때: 맨 위 `[3 | 5]`에서 "3 이상 5 미만은 가운데" → `[3 4]`에서 3을 찾음 → 36바이트.

### 장면 8: 100만 건으로 비교하기

데이터 생성기가 `INSERT` 문장 100만 줄짜리 SQL 파일을 만들고, CLI로 실행해 넣습니다 (Phase 1 처리기를 그대로 사용).

그다음 두 방식의 시간을 잽니다.

| 조회 | 찾는 방식 | 읽는 줄 수 |
| --- | --- | --- |
| `WHERE id = 777777` | B+ 트리로 위치를 찾아 한 줄 | 1줄 |
| `WHERE name = 'user777777'` | 처음부터 끝까지 | 100만 줄 |

레코드 수를 1만 → 10만 → 100만으로 늘려 가며 재면, 선형 탐색은 10배씩 느려지고 인덱스는 거의 그대로입니다. 숫자 하나보다 이 **"늘어나는 모양"**이 인덱스의 효과를 잘 보여 줍니다.

### 장면 9: 껐다 켜기

B+ 트리는 메모리에만 있으므로 프로그램을 끄면 사라집니다. 하지만 원본인 테이블 파일은 남아 있습니다.

시작할 때 파일을 한 번 처음부터 읽으며 다시 만듭니다.

```
0바이트   [1, ...]  → B+ 트리에 1 → 0 등록
18바이트  [2, ...]  → 2 → 18 등록
36바이트  [3, ...]  → 3 → 36 등록
가장 큰 ID가 3 → 다음 ID는 4
```

파일이 원본이고 인덱스는 거기서 만들어 낸 것이라, 둘이 어긋날 일이 없습니다.

### 장면 10: 외부에서 사용하기

엔진은 프로그램 안의 객체이므로, 다른 프로그램이 쓰려면 미니 DBMS가 **서버**로 실행되어 네트워크 요청을 받아야 합니다. CLI와 서버는 같은 엔진 함수 `execute(sql)`을 부릅니다.

```
CLI           ──SQL──▶ ┐
                       ├─▶ execute(sql) ─▶ 엔진
다른 프로그램  ──HTTP──▶ 미니 DBMS 서버 ┘
             ◀──JSON──
```

| 동작 | 요청 | 응답 |
| --- | --- | --- |
| SQL 실행 | `POST /query` 본문 `{"sql": "SELECT * FROM users WHERE id = 3;"}` | 200 `{"results": [...], "elapsed_ms": 0.4}` |
| 잘못된 SQL | 같은 요청에 문법 오류, 없는 테이블·컬럼, 타입 불일치 | 400 `{"error": "설명"}` |
| 서버가 바쁨 | 작업 큐가 가득 참 | 503 |

미니 레디스는 동작마다 주소가 따로였지만(`/set`, `/get`, `/delete`), 미니 DBMS는 **SQL 자체가 동작을 표현**하므로 주소가 하나(`/query`)면 됩니다.

### 장면 11: 동시성

요청이 동시에 여러 개 들어옵니다. 두 가지를 정해야 합니다.

**첫 번째: 요청을 누가 처리하나 (Thread Pool)**

| 구조 | 방식 | 특징 |
| --- | --- | --- |
| 요청마다 새 스레드 | 요청이 오면 스레드를 만들고, 끝나면 버림 | 요청이 몰리면 스레드가 끝없이 늘어 서버가 버티지 못함 |
| **Thread Pool** | 스레드를 미리 N개 만들어 두고, 요청은 작업 큐에 넣으면 놀고 있는 스레드가 꺼내 처리 | 동시에 처리하는 수가 N개로 제한되어 버팀. 큐가 가득 차면 503 |

```
              ┌→ 작업 스레드 1 ─┐
요청 → 큐 ───┼→ 작업 스레드 2 ─┼→ 응답
              └→ 작업 스레드 N ─┘
```

**두 번째: 엔진 안이 망가지지 않게 (lock)**

여러 스레드가 동시에 `INSERT`하면 이런 일이 생깁니다.

```
스레드 A: 다음 ID 읽음 (4)
스레드 B: 다음 ID 읽음 (4)       ← A가 5로 바꾸기 전에 끼어듦
스레드 A: id=4로 저장, 다음 ID를 5로
스레드 B: id=4로 저장, 다음 ID를 5로
→ 두 레코드가 모두 ID 4. B+ 트리에서 하나가 덮어써져 사라짐
```

- 파일 끝 위치를 둘이 동시에 읽으면, 인덱스가 엉뚱한 줄을 가리킬 수도 있습니다.
- B+ 트리가 노드를 나누는 도중에 다른 스레드가 검색하면, 있는 키를 못 찾을 수도 있습니다.

그래서 엔진 실행 전체를 **lock 하나**로 감싸, 한 번에 한 문장만 엔진에 들어가게 합니다. 미니 레디스에서 쓴 방식과 같습니다.

**여러 문장에 걸친 안전성 (범위 밖)**

"재고 1 줄이기"와 "주문 추가"처럼 두 문장을 묶어야 하는 경우, 문장마다 lock을 걸어도 그 사이에 끼어들 수 있고, 중간에 꺼지면 하나만 반영됩니다. 실제 DB는 이것을 **트랜잭션**(전부 되거나 전부 안 되거나)으로 풉니다. 우리 과제에서는 구현하지 않고, 발표에서 실제 DB의 방식으로 설명합니다. 미니 레디스의 "증가 명령"이 같은 문제의 작은 버전이었습니다.

## 3. 과제 요구사항과의 대응

| 과제 항목 | 이 문서의 장면 |
| --- | --- |
| CLI로 SQL 파일 실행, 파싱 | 장면 1~3 |
| INSERT는 파일에 저장, SELECT는 파일에서 읽어 출력 | 장면 4, 5 |
| ID 자동 부여, B+ 트리 인덱스 등록 | 장면 4, 7 |
| `WHERE id = ?`에서 인덱스 사용 | 장면 6 |
| 100만 건 삽입, 인덱스 vs 선형 탐색 비교 | 장면 8 |
| API 서버, Thread Pool 병렬 처리 | 장면 10, 11 |
| 동시성 이슈 고려 | 장면 11 |
| 엣지 케이스 | 장면 2(문자열 안의 `;`, `''`), 3(문법 오류), 4(타입 불일치), 9(재시작) |

## 4. 팀이 정할 항목

| 항목 | 선택지 | 추천 |
| --- | --- | --- |
| 저장 포맷 | CSV / JSON Lines / 고정 길이 바이너리 | JSON Lines (쉼표·한글 안전, 줄 위치로 바로 찾기) |
| B+ 트리에 담는 값 | 레코드 전체 / 파일 위치 | 파일 위치 (메모리 절약, 파일이 원본) |
| B+ 트리 노드 크기(차수) | 작게 / 크게 | 각자 실험해 높이와 속도를 기록하고 비교 |
| `INSERT`에 `id`를 직접 넣으면 | 오류 / 무시 / 허용 | 오류 (자동 ID와 겹치는 문제 차단) |
| 동시성 구조 | 엔진 전체에 lock 하나 / 읽기·쓰기 lock | lock 하나로 시작, 읽기·쓰기 lock은 시간이 남으면 |
| Thread Pool | 직접 구현(`queue` + 스레드) / 표준 `ThreadPoolExecutor` | 직접 구현 (과제 핵심이라 원리를 설명할 수 있게) |
| 범위 검색 (`WHERE id > ?`) | 구현 / 생략 | 시간이 남으면 1순위 (B+ 트리를 고른 이유를 보여 줌) |
