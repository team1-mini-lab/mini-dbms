# 예시로 따라가기

`users` 테이블 하나로, SQL 문장이 들어와서 파일에 저장되고 다시 찾아지기까지를 처음부터 끝까지 따라가는 문서입니다.

> **읽기 전에**: 이 문서의 예시에는 두 종류의 내용이 섞여 있습니다.
> - **과제가 정한 것**: Phase 1·2·3에서 무엇을 만들지 ([과제 요구사항](../REQUIREMENTS.md))
> - **아직 제안인 것**: 그걸 어떻게 만들지. 저장 형식, HTTP와 `/query`, lock 같은 방식은 [설계](../DESIGN.md)에 제안으로 적혀 있고 팀이 확정하지 않았습니다. 예시는 그 제안대로 만들었을 때의 모습이고, 고를 수 있는 것은 맨 아래 4절에 모았습니다.

| 더 알고 싶은 것 | 문서 |
| --- | --- |
| 왜 데이터베이스가 필요하고, 세 Phase가 어떻게 이어지는지 | [전체 그림](./OVERVIEW.md) |
| 무엇을 어떤 순서로 만드는지 | [설계](../DESIGN.md) |

## 1. 한눈에 보기

SQL 문장 하나가 들어오면 위에서 아래로 이렇게 지나갑니다. 오른쪽은 그 부분을 몇 번째 Phase에서 만드는지입니다.

```
다른 프로그램 (터미널에서 실행한 SQL 파일, 또는 HTTP 요청)
   │ SQL 문장 ("INSERT ...", "SELECT ... WHERE id = 3")
   ▼
서버: 요청을 받아 대기 줄에 넣고, 쉬고 있는 스레드가 꺼내 처리     [Phase 3]
   ▼
lock: 처리기에는 한 번에 한 문장만 들어감                          [Phase 3]
   ▼
처리기: 토크나이저 → 파서 → 실행기                                  [Phase 1]
   ├─ WHERE id = ? 이면 → B+ 트리로 파일 위치를 찾아 그 줄만 읽음   [Phase 2]
   └─ 다른 조건이면     → 파일을 처음부터 끝까지 읽음 (선형 탐색)    [Phase 1]
   ▼
테이블 파일: 한 줄에 데이터 하나, 끝에 덧붙이기만 함                 [Phase 1]
```

100만 건 데이터를 만드는 프로그램과 성능 비교 프로그램은, 이 처리기를 바깥에서 부르는 별도 프로그램입니다.

## 2. 장면별로 따라가기

테이블은 이미 있다고 가정합니다. 테이블에 어떤 칸이 있는지는 `schema.json`에 적혀 있고, 데이터 파일 `users.tbl`은 비어 있습니다.

```json
{ "users": [["id", "INT"], ["name", "TEXT"], ["age", "INT"]] }
```

`users` 테이블에는 숫자 칸 `id`, 글자 칸 `name`, 숫자 칸 `age`가 있다는 뜻입니다.

```
users.tbl:  (비어 있음)
B+ 트리:    (비어 있음)
다음 id:    1
```

### 장면 1: SQL 받기

`queries.sql` 파일에 SQL 문장 두 개를 적고, 터미널에서 처리기에 넘깁니다.

```sql
-- queries.sql
INSERT INTO users (name, age) VALUES ('현지', 25);
SELECT * FROM users WHERE id = 1;
```

```bash
python -m minidb run queries.sql
```

처리기는 파일을 읽어 문장을 하나씩 처리합니다. 문장은 `;`로 나뉩니다. 그런데 `'a;b'`처럼 **글자 값 안에도 `;`가 들어갈 수 있습니다.** 그래서 파일을 `;` 글자로 바로 자르지 않고, 다음 장면에서 단어로 자른 뒤에 문장을 나눕니다.

### 장면 2: 단어로 자르기 (토크나이저)

컴퓨터에게 SQL은 그냥 글자의 나열입니다. 먼저 뜻이 있는 조각(토큰)으로 자릅니다.

```
INSERT | INTO | users | ( | name | , | age | ) | VALUES | ( | '현지' | , | 25 | ) | ;
키워드   키워드  이름   기호  이름  기호 이름 기호   키워드  기호  글자 값 기호 숫자 기호 기호
```

| 규칙 | 예 |
| --- | --- |
| 키워드는 대문자, 소문자를 가리지 않음 | `insert`도 `INSERT` |
| 글자 값은 작은따옴표로 감싸고, 안의 작은따옴표는 두 번 씀 | `'It''s'` → It's |
| `--` 뒤는 설명(주석)이라 버림 | `-- queries.sql` |
| 규칙에 없는 글자가 나오면 여기서 오류 | `@` |

### 장면 3: 구조로 만들기 (파서)

잘라 낸 단어들이 문법에 맞는지 확인하면서, 실행기가 쓰기 좋은 구조로 바꿉니다.

```
INSERT INTO users (name, age) VALUES ('현지', 25);
   ↓
Insert(table="users", columns=["name", "age"], values=["현지", 25])
"users 테이블의 name, age 칸에 '현지', 25를 넣어라"

SELECT * FROM users WHERE id = 1;
   ↓
Select(table="users", columns=["*"], where=Where("id", "=", 1))
"users 테이블에서 id가 1인 줄의 모든 칸을 보여 줘라"
```

- 문법은 "INSERT 다음엔 INTO, 그다음엔 테이블 이름..."처럼 순서가 정해져 있습니다. 파서는 앞에서부터 단어를 하나씩 확인하고, 기대한 단어가 아니면 오류를 냅니다. 이런 방식을 **재귀 하강 파서**라고 부릅니다.
- 파서는 **문법만** 봅니다. `users` 테이블이 실제로 있는지, `age`에 숫자가 들어왔는지는 다음 장면에서 실행기가 `schema.json`을 보고 확인합니다.

### 장면 4: INSERT 실행

`Insert(users, [name, age], ["현지", 25])`를 받은 실행기는 네 가지를 합니다.

1. `schema.json`과 비교합니다. `users` 테이블이 있고, `name`은 글자, `age`는 숫자로 맞습니다.
2. `id`를 붙입니다. 다음 `id`가 1이므로 `id = 1`이고, 다음 `id`는 2가 됩니다.
3. 파일 끝의 위치를 기억한 뒤 한 줄을 덧붙입니다. 파일이 비어 있으므로 위치는 0바이트입니다.
4. B+ 트리에 "id 1은 0바이트에 있음"을 적습니다.

```
users.tbl:
  0바이트  [1, "현지", 25]

B+ 트리:  1 → 0
다음 id:  2
```

같은 방식으로 두 명을 더 넣으면 이렇게 됩니다. 한 줄이 18바이트라 위치가 18씩 늘어납니다. (한글은 한 글자가 3바이트입니다)

```
users.tbl:
   0바이트  [1, "현지", 25]
  18바이트  [2, "민수", 31]
  36바이트  [3, "지영", 28]

B+ 트리:  1 → 0,  2 → 18,  3 → 36
다음 id:  4
```

- 파일 끝에 **덧붙이기만** 하므로, 이미 쓴 줄의 위치는 바뀌지 않습니다. 그래서 B+ 트리에 적어 둔 위치가 계속 맞습니다.
- 한 줄을 `[1, "현지", 25]`처럼 JSON 배열로 쓰는 이유는, `"키보드, 무선"`처럼 쉼표가 들어간 값도 깨지지 않고 저장되기 때문입니다. 쉼표로 칸을 나누는 CSV에서는 이 쉼표가 칸 구분과 헷갈립니다.

### 장면 5: id가 아닌 칸으로 찾기 (선형 탐색)

`SELECT * FROM users WHERE name = '지영';`

`name`에는 인덱스가 없어서, 파일을 처음부터 끝까지 읽으며 하나씩 비교합니다.

```
0바이트   [1, "현지", 25]   name이 "지영"인가? 아니오
18바이트  [2, "민수", 31]   아니오
36바이트  [3, "지영", 28]   예 → 결과에 넣음
(같은 이름이 또 있을 수 있으니 끝까지 계속 읽음)
```

데이터가 3개면 3줄, 100만 개면 100만 줄을 읽습니다. 데이터가 늘어나는 만큼 그대로 느려집니다.

### 장면 6: id로 찾기 (인덱스)

`SELECT * FROM users WHERE id = 3;`

조건이 `id = ?`이므로 실행기는 B+ 트리를 씁니다.

1. B+ 트리에서 3을 찾습니다 → 36바이트
2. 파일의 36바이트 위치로 바로 가서 그 한 줄만 읽습니다 → `[3, "지영", 28]`

다른 줄은 읽지 않습니다. 데이터가 100만 개여도 B+ 트리를 3~4층만 내려가고 한 줄만 읽습니다. 이것이 Phase 2의 핵심입니다.

```
결과: {"columns": ["id", "name", "age"], "rows": [[3, "지영", 28]], "used_index": true}
```

`used_index: true`는 "인덱스를 써서 찾았다"는 표시입니다.

### 장면 7: B+ 트리가 자라는 모습

한 칸(노드)에 키를 최대 3개까지 담는 작은 B+ 트리에 `id` 1~6을 차례로 넣어 봅니다.

```
1, 2, 3 넣기:      [1 2 3]

4 넣기 → 4개라 넘침: [1 2 3 4]를 반으로 나누고, 오른쪽의 첫 키(3)를 위로 복사
                      [3]
                     /   \
                 [1 2] ↔ [3 4]

5, 6 넣기 → 넘침:  [3 4 5 6]을 반으로 나누고 5를 위로 복사
                     [3 | 5]
                    /   |   \
                [1 2]↔[3 4]↔[5 6]
```

- 실제 값(파일 위치)은 **맨 아래 칸(리프)에만** 있습니다. 위쪽 칸은 "3 이상은 오른쪽으로" 같은 **길 안내**만 합니다.
- 넘치면 반으로 나누고 위로 올리기 때문에, 나무가 아래가 아니라 **위로 자랍니다.** 그래서 맨 아래 칸들의 깊이가 항상 같습니다(항상 균형).
- 맨 아래 칸끼리 옆으로 이어져 있습니다. `id`가 2~5인 것을 찾을 때, 2가 있는 칸만 찾고 옆으로 이어 읽으면 됩니다.

`id` 3을 찾을 때: 맨 위 `[3 | 5]`에서 "3 이상 5 미만은 가운데" → `[3 4]`에서 3을 찾음 → 36바이트.

### 장면 8: 100만 건으로 비교하기

데이터를 만드는 프로그램이 `INSERT` 문장 100만 줄짜리 SQL 파일을 만들고, 터미널에서 실행해 넣습니다. Phase 1 처리기를 그대로 씁니다.

그다음 두 방식의 시간을 잽니다.

| 조회 | 찾는 방법 | 읽는 줄 수 |
| --- | --- | --- |
| `WHERE id = 777777` | B+ 트리로 위치를 찾아 한 줄 | 1줄 |
| `WHERE name = 'user777777'` | 처음부터 끝까지 | 100만 줄 |

데이터를 1만 → 10만 → 100만 건으로 늘려 가며 재면, 선형 탐색은 10배씩 느려지고 인덱스는 거의 그대로입니다. 숫자 하나보다 이 **"늘어나는 모양"**이 인덱스의 효과를 더 잘 보여 줍니다.

### 장면 9: 껐다 켜기

B+ 트리는 메모리에만 있어서 프로그램을 끄면 사라집니다. 하지만 원본인 테이블 파일은 남아 있습니다.

그래서 켤 때 파일을 처음부터 한 번 읽으며 B+ 트리를 다시 만듭니다.

```
0바이트   [1, ...]  → B+ 트리에 1 → 0 등록
18바이트  [2, ...]  → 2 → 18 등록
36바이트  [3, ...]  → 3 → 36 등록
가장 큰 id가 3 → 다음 id는 4
```

파일이 원본이고 인덱스는 거기서 만들어 낸 것이라, 둘이 어긋날 일이 없습니다.

### 장면 10: 다른 프로그램에서 쓰기 (API 서버)

처리기는 한 프로그램 안의 코드라서, 다른 프로그램이 쓰려면 미니 DBMS가 **서버**로 떠 있으면서 HTTP 요청을 받아야 합니다. 터미널 실행과 서버는 같은 함수 `execute(sql)`을 부릅니다.

```
터미널의 SQL 파일 ─────────────────┐
                                   ├─▶ execute(sql) ─▶ 처리기
다른 프로그램 ──HTTP──▶ 미니 DBMS 서버 ┘
             ◀──JSON──
```

| 상황 | 요청 | 응답 |
| --- | --- | --- |
| SQL 실행 | `POST /query`, 본문 `{"sql": "SELECT * FROM users WHERE id = 3;"}` | 200 `{"results": [...], "elapsed_ms": 0.4}` |
| 잘못된 SQL | 같은 요청에 문법 오류, 없는 테이블·칸, 숫자 칸에 글자 | 400 `{"error": "무엇이 잘못됐는지"}` |
| 서버가 너무 바쁨 | 대기 줄이 가득 참 | 503 |

미니 레디스는 동작마다 주소가 따로였습니다(`/set`, `/get`, `/delete`). 미니 DBMS는 **SQL 문장 자체에 동작이 담겨 있어서** 주소가 `/query` 하나면 됩니다.

### 장면 11: 요청 여러 개가 동시에 올 때

정해야 할 것이 두 가지입니다.

**첫째: 요청을 누가 처리하나 (스레드 풀)**

| 방법 | 하는 일 | 특징 |
| --- | --- | --- |
| 요청마다 새 스레드 | 요청이 오면 스레드를 만들고, 끝나면 버림 | 요청이 몰리면 스레드가 끝없이 늘어 서버가 버티지 못함 |
| **스레드 풀** | 스레드를 미리 N개 만들어 두고, 요청을 대기 줄에 넣으면 쉬고 있는 스레드가 꺼내 처리 | 동시에 처리하는 수가 N개로 정해져 있어 버팀. 대기 줄까지 가득 차면 503 |

```
              ┌→ 스레드 1 ─┐
요청 → 대기 줄 ┼→ 스레드 2 ─┼→ 응답
              └→ 스레드 N ─┘
```

**둘째: 처리기 안이 망가지지 않게 (lock)**

lock 없이 두 스레드가 동시에 `INSERT`하면 이런 일이 생깁니다.

```
스레드 A: 다음 id를 읽음 (4)
스레드 B: 다음 id를 읽음 (4)       ← A가 5로 바꾸기 전에 끼어듦
스레드 A: id=4로 저장, 다음 id를 5로
스레드 B: id=4로 저장, 다음 id를 5로
→ 두 데이터가 모두 id 4. B+ 트리에서 하나가 덮어써져 사라짐
```

- 둘이 파일 끝 위치를 동시에 읽으면, 인덱스가 엉뚱한 줄을 가리킬 수도 있습니다.
- B+ 트리가 칸을 나누는 도중에 다른 스레드가 찾으면, 있는 키를 못 찾을 수도 있습니다.

그래서 처리기 실행 전체를 **lock 하나**로 감싸, 한 번에 한 문장만 처리기에 들어가게 합니다. 미니 레디스에서 쓴 방식과 같습니다.

**여러 문장을 하나로 묶는 것은 하지 않음**

"재고 1 줄이기"와 "주문 추가"처럼 두 문장을 함께 처리해야 할 때가 있습니다. 문장마다 lock을 걸어도 두 문장 사이에 다른 요청이 끼어들 수 있고, 중간에 꺼지면 하나만 반영됩니다. 실제 데이터베이스는 이것을 **트랜잭션**(전부 되거나, 전부 안 되거나)으로 풉니다. 이 과제에서는 만들지 않고, 발표에서 실제 데이터베이스의 방식으로 설명합니다.

## 3. 과제 요구사항이 어느 장면에 있나

| 과제 항목 | 장면 |
| --- | --- |
| 터미널에서 SQL 파일 실행, 파싱 | 1~3 |
| INSERT는 파일에 저장, SELECT는 파일에서 읽어 출력 | 4, 5 |
| id 자동 부여, B+ 트리에 등록 | 4, 7 |
| `WHERE id = ?`에서 인덱스 사용 | 6 |
| 100만 건 넣기, 인덱스와 선형 탐색 비교 | 8 |
| API 서버, 스레드 풀로 동시 처리 | 10, 11 |
| 동시성 문제 고려 | 11 |
| 엣지 케이스 | 2(글자 값 안의 `;`, `''`), 3(문법 오류), 4(숫자 칸에 글자), 9(껐다 켜기) |

## 4. 팀이 정할 것 (아직 제안)

위 예시는 오른쪽 "추천"대로 만들었을 때의 모습입니다. 바꾸면 예시도 같이 고칩니다.

| 항목 | 고를 수 있는 것 | 추천 |
| --- | --- | --- |
