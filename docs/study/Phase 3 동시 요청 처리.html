출발점 · 3단계에서 만든 서버
지금 서버는 요청을 몇 개씩 처리하고 있을까?
3단계 서버는 파이썬 기본 부품 HTTPServer를 그대로 썼습니다. HTTPServer는 연결이 하나 들어올 때마다 아래 함수를 부릅니다. 파이썬 안에 원래 들어 있는 코드입니다.
파이썬 원본 · socketserver.py
def process_request(self, request, client_address):     self.finish_request(request, client_address)  # 요청을 끝까지 처리     self.shutdown_request(request)                # 연결 닫기
이 코드에서 읽을 것
요청 하나를 끝까지 처리하고 나서야 함수가 끝납니다. 함수가 끝나야 다음 연결을 받습니다.
그래서
한 사람의 요청이 느리면 뒤에 온 사람은 전부 기다립니다. 동시에 처리되는 요청은 늘 1개입니다.
Phase 3의 목표: 요청 여러 개를 동시에 처리하는 서버. 그런데 동시에 처리하는 순간 생기는 문제가 하나 있습니다.

문제 확인 ①
INSERT 한 문장은 안에서 몇 단계를 거칠까?
우리 DB는 새 줄에 id를 자동으로 붙입니다. 엔진은 "다음에 줄 번호"를 메모리에 하나 들고 있습니다 (next_id).
①
다음 번호를 읽는다
next_id가 지금 1이면, 이번 줄의 id는 1
②
파일에 줄을 쓴다
id=1인 줄을 데이터 파일 끝에 붙임 (storage)
③
번호를 1 올린다
next_id를 2로 바꿈. 다음 INSERT는 2를 받음
④
목차에 적는다
"id 1은 파일의 몇 번째 자리" 를 index에 기록
혼자 실행할 때는 ①→②→③→④가 한 번에 쭉 이어집니다. 그러면 id는 1, 2, 3… 겹치지 않습니다. 질문: 두 요청이 이 세 단계를 동시에 밟으면?

lock = threading.Lock() with lock:      # 잠금. 이미 잠겨 있으면 풀릴 때까지 기다림     ...         # 이 안은 한 번에 한 스레드만 # with를 벗어나면 자동으로 풂 (오류가 나도)

16단계 · engine.py
execute 위의 @locked 한 줄은 무슨 일을 할까?
engine.py (실제 코드)
def locked(method):     @functools.wraps(method)     def wrapper(self, *args, **kwargs):         with self._lock:             return method(self, *args, **kwargs)     return wrapper class Engine:     def __init__(self, data_dir):         self._lock = threading.Lock()         ...     @locked     def execute(self, sql, stop_on_error=False):         ...  # 원래 본문 그대로
1 · @locked = 이 문장과 같음
execute = locked(execute) 아랫줄 함수(execute)가 method로 들어가고, 돌려받은 wrapper가 execute 자리에 들어갑니다.
2 · 그래서 engine.execute(sql)을 부르면
wrapper 실행 → lock 잠금 → 원래 execute 실행 → 끝나면 lock 풂
3 · functools.wraps
wrapper에 원래 이름(execute)과 설명을 붙여 줌. 원래 함수는 Engine.execute.__wrapped__로 볼 수 있음

16단계 · 정리
lock이 없어도 평소엔 왜 멀쩡해 보였을까?
0.011ms
INSERT 하나가 끝나는 데 걸리는 시간 (측정값)
5ms
파이썬이 실행할 스레드를 바꾸는 간격 sys.getswitchinterval()
파이썬은 스레드 여러 개를 번갈아 가며 조금씩 실행합니다. INSERT는 스레드가 바뀌기 전에 거의 항상 끝나 버려서, ①과 ③ 사이에서 딱 바뀌는 드문 순간에만 겹칩니다. 평소엔 안 보이다가 사용자가 많을 때 가끔 터지는 문제라 더 위험합니다. 그래서 확인 스크립트는 그 틈을 0.001초로 일부러 넓혀서 매번 드러나게 했습니다.
팀원이 지켜야 할 규칙: 엔진은 항상 engine.execute(...)로만 부릅니다. engine._run(...)이나 engine.storage.append(...)를 밖에서 직접 부르면 lock을 건너뜁니다.

HTTPServer에서 바꾼 곳은 정확히 어디일까?

def process_request(self, request, client_address):     """받는 스레드가 연결 하나를 받을 때마다 부름. 큐에 넣기만 한다."""     try:         self.jobs.put_nowait((request, client_address))   # 기다리지 않음. 꽉 차 있으면 바로 Full     except queue.Full:         self._reject_busy(request)         self.shutdown_request(request)

15단계 · 일하는 스레드
할 일이 없을 때, 일하는 스레드는 무엇을 하고 있을까?
server.py · _work
def _work(self):     while True:         job = self.jobs.get()  # 비어 있으면 여기서 기다림         if job is None:       # 서버를 끌 때 넣는 "그만" 신호             return         request, client_address = job         try:             self.finish_request(request, client_address)         except Exception:             self.handle_error(request, client_address)         finally:             self.shutdown_request(request)
queue.Queue가 뭔가요?
파이썬 기본 모듈 queue의 "먼저 넣은 것을 먼저 꺼내는 줄". 안에 lock이 들어 있어서 여러 스레드가 동시에 넣고 꺼내도 안전합니다.
get()
줄이 비어 있으면 스레드를 잠재웠다가, 누가 put 하면 깨웁니다. 그래서 일이 없을 때 CPU를 쓰지 않습니다.
put_nowait()
줄이 꽉 차 있으면 기다리지 않고 바로 queue.Full 오류를 냅니다.

15단계 · 넘칠 때와 멈출 때
줄이 꽉 차거나, 보내다 만 요청이 스레드를 붙잡으면?
① 줄이 꽉 찼을 때 → 503
스레드 4개가 모두 바쁘고 큐 16칸도 다 찼으면, 받는 스레드는 기다리지 않고 바로 503을 보냅니다. 동시에 받을 수 있는 건 4 + 16 = 20개, 21번째가 503입니다.
{"error": {"code": "busy",  "message": "서버가 바쁩니다. 잠시 후 다시 보내 주세요"}}
503을 보낸 뒤 linger_close로 "보내기만 먼저 닫고 남은 요청을 잠깐 읽어 버린 뒤" 닫습니다. 바로 닫으면 클라이언트가 503을 못 읽을 때가 있었습니다(2000번 중 522번).
② 클라이언트가 멈췄을 때 → 408
연결만 열고 요청을 아주 천천히 보내는 손님이 4명이면, 스레드 4개가 모두 받기만 기다리다 서버가 멈춥니다.

concurrent.futures.ThreadPoolExecutor도 안을 열어 보면 "큐 + 미리 만든 스레드"로 우리와 구조가 같습니다. 차이는 줄의 길이입니다.
ThreadPoolExecutor
직접 만든 PooledHTTPServer
안쪽 큐
길이 제한 없음
queue.Queue(maxsize=16)

끝없이 줄을 세움 → 메모리 증가, 응답은 한참 뒤

Semaphore 같은 장치를 따로 붙여야 함

읽을 것
스레드가 느린 연결 수보다 많으면 빠른 손님은 안 막히고, 같거나 적으면 막힙니다. 4개는 "느린 연결 3개까지 견딘다"는 뜻.
