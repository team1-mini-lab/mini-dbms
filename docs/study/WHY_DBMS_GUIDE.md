# 왜 DBMS인가 — 설명자료

> 한 줄 요약: 파일 방식은 데이터를 다루는 방법(형식, 찾기, 보호)을 **각 프로그램 안에 묶어둔다.** DBMS는 그 일을 **프로그램 밖의 전담 시스템 하나로 빼낸다.**
>
> 자세한 버전은 [WHY_DBMS.md](./WHY_DBMS.md), 레디스 편은 [WHY_REDIS_GUIDE.md](./WHY_REDIS_GUIDE.md)입니다.

---

## 1. 출발점: 파일은 좋은 도구다

막 문을 연 정글마켓에는 주문 프로그램 하나가 있습니다. 주문이 들어오면 `orders.csv`에 한 줄 추가하고, 주문 목록이 필요하면 파일을 처음부터 읽으며 조건에 맞는 줄을 고릅니다.

```python
def add_order(user, product, price):
    with open("orders.csv", "a") as f:
        f.write(f"{user},{product},{price}\n")

def find_orders(user):
    for line in open("orders.csv"):
        u, product, price = line.strip().split(",")
        if u == user:
            yield product, int(price)
```

설치할 것도 배울 것도 없고, 메모장으로 열어 확인할 수 있고, 주문이 하루 수십 건이면 처음부터 읽어도 빠릅니다. **프로그램 하나가 작은 파일을 쓴다면 여기서 끝이고, DBMS는 필요 없습니다.**

## 2. 조건: 함께 쓰는 프로그램이 늘고, 데이터가 커진다

정글마켓이 커지면서 회원, 배송, 정산, 마케팅 프로그램이 생기고 각 팀이 따로 만듭니다. 주문은 누적 100만 건이 되고, 세일 날에는 수백 명이 같은 순간에 주문합니다. 각 팀은 **자기 프로그램에 필요한 파일을 만들고, 남의 파일은 형식을 맞춰 읽습니다.** 코드는 1번과 같은 방식 그대로입니다.

> 조건은 문제가 터지는 **상황**이지 원인이 아닙니다. 같은 코드도 프로그램 하나, 작은 데이터에서는 멀쩡합니다.

## 3. 문제: 여섯 장면

### ① 주소를 바꿨는데 택배는 옛날 집으로 간다

kim의 주소가 회원 파일에도, 배송팀이 따로 복사해 둔 배송 파일에도 있습니다. kim이 이사해서 주소를 바꾸면 회원 프로그램은 **회원 파일만** 고칩니다. 배송 프로그램은 배송 파일의 옛 주소로 택배를 보냅니다. 같은 데이터가 여러 파일에 복사되어 있고, 회원 프로그램은 배송 파일이 있는지조차 모르기 때문입니다.

### ② 칸 하나 추가했더니 프로그램 네 개가 깨진다

주문팀이 `orders.csv`에 쿠폰 칸을 추가합니다. 1년 전에 만든 정산 프로그램은 "칸이 세 개"라고 가정하고 있어서 멈추고, 마케팅 스크립트는 셋째 칸을 가격으로 읽다가 쿠폰 코드를 매출로 더합니다. 상품 이름에 쉼표가 들어가도 마찬가지입니다. **몇 번째 칸이 가격인지라는 형식 지식이 프로그램마다 코드에 박혀** 있기 때문입니다.

### ③ 질문 하나에 프로그램 하나

마케팅팀이 "지난달 서울 30대가 가장 많이 산 상품 10개"를 묻습니다. 개발자가 회원 파일과 주문 파일을 반복문으로 엮는 코드를 이틀 걸려 짭니다. 다음 주에 "부산 20대는?"이라고 물으면 또 새 코드입니다. **어떻게 찾을지**를 질문마다 사람이 직접 짜야 하기 때문입니다.

### ④ 주문이 100만 건이 되자 조회가 느려진다

주문번호 하나를 찾으려면 첫 줄부터 최악 100만 줄을 읽고 비교합니다. 조회 한 번에 1초 안팎이 걸리고, 1초에 수백 명이 조회하면 서버가 버티지 못합니다. 파일은 순서대로 읽는 것밖에 모르기 때문입니다. 정렬해 두면 이진 탐색이 되지만, 주문이 들어올 때마다 100만 줄을 다시 정렬할 수는 없습니다.

### ⑤ 세일 날, 남은 1개를 두 명에게 판다

재고 파일에 `1`이 적혀 있을 때, kim의 주문과 lee의 주문이 거의 동시에 들어옵니다. 두 주문 프로그램이 모두 `1`을 읽고 "구매 가능"이라 판단한 뒤 각자 `0`을 씁니다. 1개를 2명에게 팔았습니다. 같은 파일에 동시에 줄을 추가하다 **두 줄이 섞인 깨진 줄**이 생기기도 합니다. 읽고, 판단하고, 쓰는 사이에 끼어들 수 있고, 순서를 정해 줄 누군가가 없기 때문입니다.

### ⑥ 저장하다 꺼지면 돈만 빠진다

주문 하나를 처리하려면 결제 파일, 재고 파일, 주문 파일 세 개를 고쳐야 합니다. 결제 기록을 쓴 직후 전원이 나가면, 고객 돈은 나갔는데 주문은 없고, 쓰던 재고 파일은 반만 남아 읽을 수조차 없습니다. 여러 파일의 변경을 **전부 되거나 전부 안 되거나**로 묶는 장치가 없기 때문입니다.

### 누가 겪고, 어떻게 드러나나

| 장면 | 누가 겪나 | 어떻게 드러나나 |
| --- | --- | --- |
| ① 주소 불일치 | 고객 | 엉뚱한 곳으로 배송 |
| ② 형식 변경 | 개발자 | 칸 하나 바꿀 때마다 여러 프로그램이 깨짐 |
| ③ 질문마다 코드 | 회사 | 데이터가 있어도 답을 얻는 데 며칠 |
| ④ 느린 검색 | 고객, 운영자 | 데이터가 늘수록 느려지고 서버가 버티지 못함 |
| ⑤ 동시에 쓰기 | 고객, 회사 | 초과 판매, 깨진 줄 |
| ⑥ 중간에 꺼짐 | 고객, 회사 | 돈과 주문이 안 맞음, 파일 손상 |

정리하면 **①②는 데이터가 어긋나거나 프로그램이 깨지는 문제, ③④는 데이터를 꺼내기 어렵고 느린 문제, ⑤⑥은 데이터 자체가 망가지는 문제**입니다.

## 4. 뿌리: 원인은 하나다

> **데이터를 다루는 방법(형식, 찾기, 보호)이 각 프로그램 안에 묶여 흩어져 있다.**

| 장면 | 같은 원인을 다르게 본 것 |
| --- | --- |
| ① 주소 | 프로그램마다 자기 파일을 가져서 같은 데이터가 여러 벌 |
| ② 형식 | 파일 형식 지식이 각 프로그램 코드에 |
| ③ 질문 | 찾는 방법이 각 프로그램 코드에 |
| ④ 검색 | 빨리 찾는 색인을 만들어도 모두가 함께 쓸 곳이 없음 |
| ⑤ 동시성 | 순서를 정하는 규칙을 각자 알아서 (= 아무도 안 함) |
| ⑥ 장애 | 여러 변경을 하나로 묶는 장치를 각자 알아서 (= 아무도 안 함) |

정산 프로그램의 `for line in open("orders.csv"): u, product, price = line.split(",")` 몇 줄 안에 데이터의 위치, 형식, 찾는 방법이 모두 들어 있고, 동시에 쓸 때와 꺼질 때의 대비는 없습니다. 그리고 다섯 프로그램이 이것을 각자 따로 들고 있습니다.

도서관에 비유하면, 사람마다 **자기 책장**에 책을 두는 상황입니다. 같은 책이 여러 책장에 있고, 남의 책장은 그 사람의 꽂는 방식을 알아야 찾을 수 있고, 처음부터 훑어야 하고, 두 사람이 같은 책을 동시에 가져갈 수도 있습니다.

레디스 편의 뿌리가 "상태가 각 **서버**에 묶여 있다"였다면, 이번에는 "데이터 다루는 법이 각 **프로그램**에 묶여 있다"입니다.

### 증상만 막으면 하나가 남는다

| 시도 | 막는 것 | 남는 것 |
| --- | --- | --- |
| 파일 읽기 공용 라이브러리 | ② 형식 지식이 한 곳에 | 바뀔 때마다 모든 프로그램 재배포. ④⑤⑥ 그대로 |
| 파일 잠금 (flock) | ⑤ 동시에 쓰기 | 파일 전체를 잠가 줄을 섬. 한 프로그램이라도 빼먹으면 무너짐 |
| 주문번호 순으로 정렬해 저장 | ④ 이진 탐색 | 추가마다 전체 재정렬. 다른 칸으로 찾으면 여전히 느림 |
| 매일 밤 백업 | ⑥ 일부 복구 | 백업 이후 데이터 손실. 반쪽 상태는 그대로 |

증상마다 막다 보면 모든 프로그램이 지켜야 할 공용 코드와 규칙이 점점 커집니다. 그걸 **프로그램 하나로 떼어 낸 것**이 DBMS입니다.

## 5. 해결: 데이터를 다루는 일을 프로그램 밖으로 뺀다

프로그램은 무엇이 필요한지만 말하고(SQL), 데이터를 다루는 일은 전담 시스템 한 곳이 맡습니다.

```
회원 · 주문 · 배송 · 정산 · 마케팅
              ↓  "무엇이 필요한지" (SQL)
            DBMS  (스키마 · 질의 처리 · 인덱스 · 동시성 제어 · 복구)
              ↓
         디스크의 파일
```

| 장면 | 풀리는 방식 |
| --- | --- |
| ① | 주소는 회원 테이블에 한 번만. 배송은 함께 조회(JOIN) → 고치면 모두 새 주소 |
| ② | 칸 번호가 아니라 이름(`price`)으로 요청 → 칸을 추가해도 기존 SQL 그대로 |
| ③ | SQL 한 문장으로 직접 질문, 질문이 바뀌면 문장만 바꿈 |
| ④ | DBMS가 인덱스(B+ 트리)를 관리 → 100만 건도 몇 번 비교로 |
| ⑤ | 모든 요청이 DBMS 한 곳을 거침 → lock으로 순서를 정해 1개면 한 명만 |
| ⑥ | 여러 변경을 트랜잭션 하나로 → 중간에 꺼지면 시작 전 상태로 |

DBMS도 결국 파일에 저장합니다. 달라진 것은 **그 파일을 DBMS만 직접 만지고**, 나머지는 모두 DBMS에게 부탁한다는 점입니다. 전담하는 곳의 후보는 셋입니다. 각 프로그램 안의 공용 라이브러리는 버전이 갈리고 동시성·복구는 여전히 각자라 탈락, 공유 폴더와 규칙 문서는 사람이 지켜야 해서 탈락, **데이터를 전담하는 별도 프로그램**이 형식, 색인, 순서, 복구를 한 곳에서 책임집니다. 이것이 DBMS입니다. 레디스가 상태와 서버를 분리했다면, DBMS는 **데이터와 프로그램을 분리**합니다.

프로그램이 "어떻게"가 아니라 "무엇을"만 말하게 된 것이 핵심입니다. 택시 기사에게 길을 하나하나 지시하는 대신 목적지만 말하는 것과 같습니다. 저장 방식이 바뀌어도 프로그램을 고치지 않아도 되는 이 성질을 **데이터 독립성**이라고 합니다.

## 6. DBMS 이전과 이후

1960년대에 GE의 IDS(이후 CODASYL이 1969~1971년 표준화한 **네트워크형 DB**)와 아폴로 계획의 로켓 부품 관리에서 출발한 IBM IMS(**계층형 DB**, 1968년 설치)가 데이터를 프로그램 밖으로 빼서 공유, 동시성, 복구를 맡았습니다. 하지만 데이터를 꺼내려면 "kim을 찾고 → 첫 주문 포인터를 따라가고 → 다음 주문 포인터를 따라가고..."처럼 **프로그램이 데이터 사이의 길을 직접 따라가야** 했습니다. 구조가 바뀌면 길이 바뀌어 프로그램을 고쳐야 했고, 미리 연결해 두지 않은 질문은 여전히 어려웠습니다. 데이터는 밖으로 뺐지만 찾아가는 길은 여전히 프로그램이 들고 있던 셈입니다.

1970년 IBM 연구소 코드(Codd)의 논문 "A Relational Model of Data for Large Shared Data Banks"가 제안한 **관계형 모델**은 데이터를 표로만 표현하고, 프로그램은 원하는 결과의 조건만 말하게 했습니다. 어떻게 찾을지는 DBMS가 정합니다. 이 아이디어가 SQL과 Oracle, DB2, MySQL, PostgreSQL로 이어집니다.

| 요구 | 파일 | 계층형·네트워크형 | 관계형 DBMS |
| --- | --- | --- | --- |
| 모든 프로그램이 같은 데이터 한 벌 | ✗ | ✓ | ✓ |
| 형식이 바뀌어도 프로그램 그대로 | ✗ | △ 길이 바뀜 | ✓ 이름으로 요청 |
| 새 질문을 코드 없이 | ✗ | ✗ 길 따라가는 코드 | ✓ SQL |
| 큰 데이터에서 빨리 찾기 | ✗ | ✓ 포인터 | ✓ 인덱스, DBMS가 길을 고름 |
| 동시에 써도 안전 | ✗ | ✓ | ✓ lock, MVCC |
| 중간에 꺼져도 반쪽 없음 | ✗ | ✓ | ✓ 트랜잭션, 로그 |
| 잘못된 값 막기 | ✗ 프로그램마다 | △ | ✓ 타입, 제약 조건 |

### 인덱스를 추가해도 SQL은 그대로

같은 `SELECT * FROM orders WHERE id = 987654`라도 DBMS는 인덱스가 있으면 인덱스로, 없으면 처음부터 읽습니다. 인덱스를 추가해도 SQL은 한 글자도 안 바뀌고 빨라집니다. 이 길을 고르는 부분이 **쿼리 플래너**입니다. 우리 과제의 실행기가 `WHERE id = ?`일 때만 B+ 트리를 쓰는 한 줄이 이것의 가장 단순한 형태입니다.

### 여러 변경을 DBMS 안에서 한 번에

장면 ⑤⑥은 **트랜잭션**으로 풉니다. 재고 차감, 결제 기록, 주문 추가를 `BEGIN ... COMMIT`으로 묶으면, COMMIT까지 와야 셋 다 반영되고 중간에 꺼지면 셋 다 없던 일이 됩니다. 트랜잭션이 지키는 네 성질이 **ACID**입니다.

| 성질 | 뜻 | 막는 장면 |
| --- | --- | --- |
| 원자성 (Atomicity) | 전부 되거나 전부 안 되거나 | ⑥ 돈만 빠짐 |
| 일관성 (Consistency) | 규칙(재고 ≥ 0)이 항상 지켜짐 | ⑤ 초과 판매 |
| 격리성 (Isolation) | 동시에 실행해도 하나씩 한 것과 같은 결과 | ⑤ 끼어들기 |
| 지속성 (Durability) | COMMIT된 것은 꺼져도 남음 | ⑥ 파일 손상 |

원칙은 **여러 변경을 프로그램이 따로 하지 말고, 트랜잭션 하나로 DBMS에 맡긴다**입니다. 레디스 편의 "읽고 쓰기를 레디스 안에서 한 번에"와 같은 생각입니다.

## 7. DBMS를 "쓴다"는 것의 의미

DBMS도 레디스처럼 **따로 돌아가는 서버 프로그램**입니다(SQLite처럼 프로그램 안에 들어가는 것도 있습니다). 앱은 네트워크로 접속해 SQL을 보내고, 파일을 직접 열던 코드가 SQL을 보내는 코드로 바뀝니다.

```python
conn = psycopg.connect("host=DB서버주소 dbname=jungle")

def find_orders(user):                                   # 장면 ②③④
    return conn.execute(
        "SELECT product, price FROM orders WHERE user_name = %s", (user,)
    ).fetchall()

def place_order(user, product, price):                   # 장면 ⑤⑥
    with conn.transaction():
        row = conn.execute(
            "UPDATE stock SET count = count - 1 "
            "WHERE product = %s AND count > 0 RETURNING count", (product,)
        ).fetchone()
        if row is None:
            raise SoldOut()                              # 아무것도 반영 안 됨
        conn.execute("INSERT INTO orders VALUES (%s, %s, %s)", (user, product, price))
```

값은 SQL 문자열에 붙이지 않고 따로 전달합니다(파라미터 바인딩). 이름에 `'`가 든 사용자와 SQL 인젝션을 막는 기본입니다. 정글마켓이 더 커지면 레디스 편의 구조가 됩니다: **앱 서버 → 레디스(빠른 사본) → DBMS(원본) → 디스크.**

## 8. 우리 과제: 무엇을 왜 만드나

DBMS는 연결 층, 질의 처리 층, 접근 방법(인덱스) 층, 저장 층, 트랜잭션 층으로 나뉩니다. 우리 과제의 세 Phase는 각 층을 가장 단순한 형태로 다시 만들어 보는 것이고, 여섯 장면 중 ②③④⑤를 직접 다시 풀어 봅니다.

DB에 오는 질문은 "이 키의 값 줘"만이 아니라 범위(`BETWEEN`), 정렬(`ORDER BY`), 최댓값이 흔합니다. 해시 테이블은 정확히 일치하는 키는 O(1)이지만 키를 뒤섞어 배치해서 범위를 못 찾고, 이진 트리는 정렬은 되지만 깊습니다. **B+ 트리**는 정렬을 유지하면서 노드 하나에 키를 수백 개 담아 3~4층이면 수억 건을 찾습니다. 그래서 거의 모든 관계형 DB의 기본 인덱스입니다.

아래 표는 DBMS의 기능을 우리 단계와 연결하고, 그렇게 정한 이유를 적은 것입니다. 자세한 결정은 [DESIGN.md](../DESIGN.md) 4번에 있습니다.

| DBMS의 기능 | 푸는 장면 | 우리 단계 | 우리 방식 | 이유 | 상태 |
| --- | --- | --- | --- | --- | --- |
| SQL 해석 | ②③ | 1 → 3, 4 | 임시 파서로 관통 후 토크나이저 + 재귀 하강 파서로 교체 | 문법 규칙 하나 = 함수 하나라 구현과 설명이 쉬움 | 예정 |
| 파일 저장 | | 1 → 5 | 한 줄에 레코드 하나인 JSON 배열, 추가만 함 | 쉼표·한글이 든 값도 안전, 줄 위치(offset)가 변하지 않아 인덱스가 계속 유효 | 예정 |
| 스키마, 무결성 | ② | 0, 6 | `schema.json`, 컬럼 수·타입 검사 | `CREATE TABLE`이 범위 밖이라 미리 정의 | 예정 |
| 인덱스 | ④ | 2 → 7, 8 | 임시 `dict` → 메모리 B+ 트리 (ID → 파일 위치) | 과제가 메모리 기반 요구. 위치만 저장해 메모리 절약 | 예정 |
| 플래너 | ④ | 2, 8 | `WHERE id = ?`면 인덱스, 아니면 선형 탐색 | 과제의 비교 조건과 일치. `EXPLAIN`은 17단계(선택) | 예정 |
| 성능 증명 | ④ | 9, 10 | 100만 건 생성, 1만·10만·100만에서 비교 | 숫자 하나보다 "늘어나는 모양"이 O(log N) vs O(N)을 보여 줌 | 예정 |
| 외부 연결 | | 2 → 11 | HTTP `POST /query` → 직접 만든 Thread Pool | 요청마다 스레드를 만들면 몰릴 때 서버가 버티지 못함 | 예정 |
| 동시성 제어 | ⑤ | 12 | 엔진 전체에 lock 하나 | 단순하고 확실함. 미니 레디스와 같은 방식. 읽기/쓰기 lock은 16단계(선택) | 예정 |
| 쿼리 결과 캐시 | | 18 | 미니 레디스로 `SELECT` 결과 캐시, `INSERT` 시 무효화 | 두 과제를 "DBMS 앞의 레디스" 구조로 연결 | 선택 |
| 트랜잭션, 복구, JOIN | ①⑥ | 하지 않음 | | 범위 밖 (DESIGN.md "하지 않을 것"). 발표에서 실제 DB의 방식으로 설명 | |

## 9. 언제 파일, 언제 DBMS?

| 데이터 성격 | 파일 | DBMS |
| --- | --- | --- |
| 한 프로그램만 쓰는 설정 | 적합 | 과함 |
| 쌓기만 하고 나중에 분석 (로그) | 적합 | 분석용 DB를 따로 쓰기도 함 |
| 이미지, 동영상 같은 큰 덩어리 | 적합 | 경로만 DB에 |
| 한 프로그램이지만 조건 검색 필요 | 직접 구현은 고생 | SQLite |
| 함께 쓰고, 동시에 바뀌고, 틀리면 안 됨 (주문, 결제, 재고) | 부적합 | 필요 |

기준은 **함께 쓰는 데이터**, **깨지면 안 되는 데이터**, **여러 방식으로 물어볼 데이터** 세 가지입니다.

## 10. DBMS도 공짜는 아니다, 그래서 이렇게 보완한다

| 비용 | 무엇이 문제인가 | 보완 |
| --- | --- | --- |
| 운영 비용 | 별도 서버, 백업, 업그레이드 | 클라우드 관리형 DB, 작은 서비스는 SQLite |
| 스키마 변경 | 큰 테이블의 칸 변경이 오래 걸리고 위험 | 마이그레이션 도구, 단계적 변경 |
| 늘리기 어려움 | 원본이 한 곳이고 트랜잭션 때문에 서버를 늘리기 어려움 | 읽기 복제본, **레디스 캐시로 DB 보호**, 샤딩. 이 한계에서 NoSQL이 등장 |
| 인덱스 비용 | 공간을 쓰고 `INSERT`마다 갱신해 쓰기가 느려짐 | 자주 찾는 칸에만, `EXPLAIN`으로 확인 |
| 요청 비용 | 네트워크 왕복, SQL 해석 | 커넥션 풀, prepared statement |

### 헷갈리기 쉬운 짝

- **DBMS도 파일에 저장합니다.** 차이는 저장 장소가 아니라 **파일을 누가 직접 만지느냐**입니다.
- **lock과 트랜잭션은 다릅니다.** lock은 동시에 끼어들지 못하게 하는 도구(격리성)이고, 트랜잭션은 거기에 중간에 꺼져도 반쪽이 없게(원자성, 지속성)까지 묶은 약속입니다. 우리 과제는 lock까지 만듭니다.

## 예상 질문

**Q. 파일에 잠금만 걸면 되지 않나요?** 동시에 쓰기(⑤)는 막히지만, 모든 프로그램이 빠짐없이 잠금을 지켜야 하고, 파일 전체를 잠가 모두가 줄을 섭니다. 형식(②), 질문(③), 검색(④), 장애(⑥)는 그대로입니다.

**Q. DBMS도 파일에 저장하는데 뭐가 다른가요?** 파일을 DBMS만 직접 만지고, 형식·색인·순서·복구를 한 곳에서 책임진다는 점이 다릅니다.

**Q. 해시 테이블이 더 빠른데 왜 B+ 트리를 쓰나요?** 해시는 `=`만 빠르고 범위·정렬을 못 합니다. DB에는 범위·정렬 질문이 흔해서 순서를 유지하는 B+ 트리를 씁니다. 레디스는 질문이 항상 "이 키의 값"이라 해시가 맞습니다.

**Q. 레디스가 있으면 DBMS는 필요 없나요?** 레디스는 빠른 사본이고 원본과 트랜잭션은 DBMS가 책임집니다. 레디스는 DBMS를 대체하는 게 아니라 그 앞에서 보호합니다.

**Q. 우리 미니 DBMS는 장면 ⑥(중간에 꺼짐)을 막나요?** 아니요. 트랜잭션과 로그(WAL)는 범위 밖입니다. 대신 추가만 하는 저장 방식이라 기존 레코드는 망가지지 않고, 마지막 한 줄만 깨질 수 있습니다. 실제 DB는 변경을 로그에 먼저 써서 이 문제를 풉니다.

**Q. lock 하나면 Thread Pool이 의미가 있나요?** 엔진 실행은 한 번에 하나지만, 요청 받기·JSON 해석·응답 보내기는 lock 밖에서 병렬로 일어납니다. 정확성을 먼저 확보하고 읽기/쓰기 lock으로 개선하는 순서입니다.
