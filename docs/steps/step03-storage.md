# 3단계: 저장소

## 목표

행을 테이블 파일에 쓰고, 다시 읽어 올 수 있게 한다.

이 단계가 끝나면 `table.append((1, "Kim", 3))`이 행을 `data/students.tbl` 끝에 쓰고 그 행이 파일의 몇 번째 바이트에서 시작하는지(오프셋)를 돌려준다. `table.scan()`은 파일의 모든 행을 `(오프셋, 행)` 쌍으로 처음부터 차례로 내놓고, `table.read_at(오프셋)`은 그 위치의 행 하나만 읽는다. 프로그램을 껐다 켜도 같은 행이 나온다. 저장소는 SQL이 무엇인지, 이 행이 어떤 SELECT의 결과가 될지 모른다. 그것은 4단계 실행기의 일이다.

## 이 단계의 위치

0단계 문서의 여섯 순서 중 **5번**이다.

| 순서 | 하는 일 |
| --- | --- |
| 1 | CLI가 파일에서 문장을 꺼낸다 (5단계) |
| 2 | 토크나이저가 문자열을 토큰으로 자른다 (1단계) |
| 3 | 파서가 토큰 열을 구조화된 객체로 만든다 (2단계) |
| 4 | 실행기가 무엇을 할지 정하고 저장소에 시킨다 (4단계) |
| **5** | **저장소가 파일을 읽고 쓴다 (3단계)** |
| 6 | CLI가 결과를 화면에 찍는다 (5단계) |

파서(2단계)와 저장소(3단계)는 서로를 모른다. 4단계 실행기가 둘을 처음 연결한다. 그래서 이 단계의 테스트에는 SQL이 한 줄도 나오지 않는다.

## 1. 왜 "파일에 쓴다"가 설계 문제인가

`("Kim", 3)`을 파일에 쓰라고 하면 바로 결정해야 할 것들이 생긴다.

| 질문 | 잘못 정하면 생기는 일 |
| --- | --- |
| 값과 값 사이를 무엇으로 나누나 | 쉼표로 나누면 `'Kim, Lee'`라는 이름이 두 값으로 읽힌다 |
| 행과 행 사이를 무엇으로 나누나 | 줄바꿈으로 나누면 값 안의 줄바꿈이 행을 쪼갠다 |
| 숫자 `3`과 문자열 `"3"`을 어떻게 구분하나 | 파일에는 둘 다 `3`으로 보인다 |
| 나중에 특정 행만 다시 읽으려면 | 행의 위치를 돌려주지 않으면 매번 처음부터 읽어야 한다 |
| 쓰다가 프로그램이 죽으면 | 반쪽짜리 행이 남고, 다음 행이 그 뒤에 이어 붙어 둘 다 깨진다 |

DBMS의 저장소 층은 이 질문들에 대한 답을 한곳에 모아 두고, 바깥에는 "행을 넣어라, 꺼내라"만 보여 준다.

## 2. 파일 포맷

DESIGN.md의 결정을 구체적으로 적는다. 행 `(1, "Kim", 3)`은 파일에 다음 바이트로 저장된다.

```
1<TAB>Kim<TAB>3<LF>
```

| 규칙 | 이유 |
| --- | --- |
| 한 행은 한 줄(`\n`으로 끝남) | `cat`으로 보고 `wc -l`로 셀 수 있다 |
| 값 사이는 탭 | 쉼표보다 실제 데이터에 드물게 나온다 |
| 값 안의 탭, 줄바꿈, 백슬래시는 `\t`, `\n`, `\\`로 바꿔 쓴다 | 구분자와 실제 데이터를 구분한다. 백슬래시 자체도 바꿔야 `\t`라는 두 글자를 저장할 수 있다 |
| INT는 십진수 문자열, TEXT는 이스케이프한 UTF-8 | 파일에는 둘 다 글자지만, 읽을 때 카탈로그의 타입을 보고 INT는 `int()`로 되돌린다 |
| 파일은 바이너리 모드로 다룬다 | 텍스트 모드에서는 `tell()`이 바이트 위치가 아니라서 오프셋을 믿을 수 없다 |

### 이스케이프가 꼭 필요한가

`INSERT INTO students (name, grade) VALUES ('Kim\tLee', 3)` 같은 입력은 드물지만, 드물다고 깨지면 안 된다. 이스케이프 없이 저장하면 이 행은 값이 네 개로 읽히고 "손상된 행"이 된다. 사용자 입력이 저장 포맷을 깨뜨릴 수 있으면 저장소가 아니다.

### 오프셋: 행의 주소

`append`가 돌려주는 오프셋은 그 줄이 시작하는 바이트 위치다. 첫 행은 0, 둘째 행은 첫 줄의 바이트 길이, 이런 식이다. `read_at(오프셋)`은 파일에서 그 위치로 바로 점프해 한 줄만 읽는다. 앞의 행들을 거치지 않는다.

Phase 1에서는 쓸 일이 거의 없다. Phase 2의 B+ 트리가 `(id → 오프셋)`을 기억했다가, `WHERE id = 500000`이 오면 50만 줄을 읽는 대신 `read_at` 한 번으로 끝내기 위한 준비다.

## 3. 인터페이스: 세 가지 연산

```python
table = storage.table("students")       # 카탈로그에 있는 테이블의 파일을 연다

offset = table.append((1, "Kim", 3))    # 행 추가 → 오프셋
for offset, row in table.scan():        # 전체 순회 → (오프셋, 행) 순서대로
    ...
row = table.read_at(offset)             # 특정 위치의 행 하나
```

행은 카탈로그의 컬럼 순서를 따르는 튜플이다. id도 포함한다. id 값을 정하는 것은 실행기의 일이고, 저장소는 받은 값을 그대로 쓴다.

실행기가 저장소에 시킬 수 있는 일은 이 셋뿐이다. "조건에 맞는 행을 찾아라"는 없다. 조건을 해석하는 것은 실행기의 일이고, 저장소는 행을 순서대로 내놓기만 한다. 경계를 이렇게 두어야 Phase 2에서 "인덱스로 찾은 오프셋을 `read_at`에 넘긴다"로 자연스럽게 이어진다.

## 4. 결정 세 가지

### 결정 1: 파일을 열어 둔 채 유지한다

연산마다 파일을 열고 닫는 대신, `TableFile` 객체가 파일 핸들을 들고 있다가 `close()`에서 닫는다. 이유는 Phase 2의 100만 건 삽입이다. 열고 닫기는 시스템 호출이라 100만 번 반복하면 그 비용이 지배적이 된다. Phase 3 서버는 프로세스가 살아 있는 내내 파일을 쓰므로 어차피 열어 둬야 한다.

대신 닫는 책임이 생긴다. `Storage`와 `TableFile`은 컨텍스트 매니저(`with`)로 쓸 수 있게 한다.

### 결정 2: INSERT마다 flush한다

`write()`는 Python의 버퍼에만 쓴다. `flush()`를 해야 운영체제로 넘어간다. Phase 1에서는 매 `append` 뒤에 `flush()`한다. CLI가 끝났는데 파일에 행이 없는 상황을 막는 것이 우선이다.

이것은 삽입 속도와 맞바꾼 선택이다. 10단계 벤치마크에서 flush를 미루는 옵션을 추가해 차이를 숫자로 본다. 참고로 `flush()`를 해도 운영체제 버퍼에 있을 뿐 디스크에 내려간 것은 아니다. 그것까지 보장하려면 `os.fsync()`가 필요하고 훨씬 느리다. DESIGN.md가 밝힌 대로 과제 범위 밖이다.

### 결정 3: 타입 변환은 저장소가 한다

파일에서 읽은 `b"3"`을 `3`으로 바꾸는 일을 누가 하는가. 저장소가 테이블 정의(`Table`)를 받아서 한다. 그러면 실행기가 받는 행은 바로 `grade > 2` 같은 비교에 쓸 수 있는 값이고, "INT는 십진수, TEXT는 이스케이프"라는 인코딩 규칙이 `storage.py` 한 파일에 모인다. 실행기가 하면 같은 규칙이 실행기에도 복제된다.

저장소가 카탈로그 파일(`schema.json`)을 읽는 것은 아니다. 이미 만들어진 `Table` 객체를 건네받을 뿐이다.

## 5. 쓰다 만 행

INSERT 도중 프로그램이 죽으면 파일 끝에 `\n`이 없는 줄이 남을 수 있다. 이것을 그대로 두면 두 가지 문제가 생긴다.

- 읽을 때 마지막 행의 값이 모자라 "손상된 행" 오류가 난다.
- 다음 `append`가 그 뒤에 이어 붙어서, 반쪽 행과 새 행이 한 줄이 된다. 멀쩡한 새 행까지 깨진다.

그래서 파일을 **열 때** 끝이 `\n`인지 확인하고, 아니면 마지막 `\n` 이후를 잘라 낸다. 잘린 것은 애초에 완성되지 않은 행이므로 데이터 손실이 아니다. 이것이 과제 범위 안에서 다루는 유일한 장애 처리다. 여러 문장에 걸친 복구(트랜잭션, WAL)는 하지 않는다.

## 6. 오류

모두 `StorageError`다.

| 상황 | 언제 발견 |
| --- | --- |
| 행의 값 수가 컬럼 수와 다르다 | 읽을 때 |
| INT 컬럼 자리에 숫자가 아닌 것이 있다 | 읽을 때 |
| 쓰려는 행의 값 수가 컬럼 수와 다르다 | 쓸 때 |
| 쓰려는 값의 타입이 컬럼 타입과 다르다 | 쓸 때 |
| 오프셋이 줄의 시작이 아니거나 파일 밖이다 | `read_at` |
| 닫힌 테이블에 연산을 시도한다 | 즉시 |

쓸 때의 검사는 실행기가 이미 했어야 하는 것이지만, 저장소도 자기 파일을 지킨다. 잘못된 행이 파일에 들어가면 그 뒤로는 읽을 때마다 오류가 난다.

## 7. 코드 구조 (`minidb/storage.py`)

- `encode_row(table, row) -> bytes`, `decode_row(table, line) -> tuple`: 포맷 규칙 전부. 파일을 모르는 순수 함수라 테스트하기 쉽다.
- `TableFile`: 테이블 파일 하나. `append`, `scan`, `read_at`, `close`. 열 때 쓰다 만 행을 정리한다.
- `Storage(data_dir, catalog)`: 테이블 이름으로 `TableFile`을 찾아 준다. 처음 요청될 때 열고, `close()`에서 모두 닫는다. 없는 테이블은 카탈로그가 `TableNotFoundError`를 낸다.

`scan()`은 제너레이터다. 100만 행을 리스트로 만들지 않고 한 줄씩 내놓는다. 단, 순회 도중에 같은 테이블에 `append`하면 안 된다. Phase 1에서는 그런 일이 없고, Phase 3에서는 잠금이 막는다.

## 완료 기준

```sh
pytest tests/test_storage.py
```

- 탭, 줄바꿈, 백슬래시, 한글, 빈 문자열이 들어간 값이 쓰고 읽었을 때 같다.
- `append`가 돌려준 오프셋으로 `read_at`하면 그 행이 나온다. `scan`의 오프셋과도 일치한다.
- 닫았다 다시 열어도 같은 행이 같은 순서로 나온다.
- 끝에 `\n`이 없는 파일을 열면 그 줄이 사라지고, 이어서 `append`한 행은 온전하다.
- 손상된 행과 잘못된 오프셋은 `StorageError`다.
