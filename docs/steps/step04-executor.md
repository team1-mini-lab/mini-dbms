# 4단계: 실행기

## 목표

파서가 만든 문장 객체를 받아, 카탈로그로 뜻을 확정하고, 저장소에 실제 동작을 시킨다.

이 단계가 끝나면 `Executor.execute(Insert(...))`가 id를 부여해 행을 파일에 쓰고 그 id를 돌려주며, `Executor.execute(Select(...))`가 조건에 맞는 행을 골라 요청한 컬럼만 추려 돌려준다. 파서와 저장소가 처음으로 연결되어, SQL 문자열에서 파일까지 Phase 1의 흐름이 끝까지 이어진다. 아직 없는 것은 파일을 읽어 화면에 찍는 CLI뿐이다.

## 이 단계의 위치

0단계 문서의 여섯 순서 중 **4번**이다.

| 순서 | 하는 일 |
| --- | --- |
| 1 | CLI가 파일에서 문장을 꺼낸다 (5단계) |
| 2 | 토크나이저가 문자열을 토큰으로 자른다 (1단계) |
| 3 | 파서가 토큰 열을 구조화된 객체로 만든다 (2단계) |
| **4** | **실행기가 무엇을 할지 정하고 저장소에 시킨다 (4단계)** |
| 5 | 저장소가 파일을 읽고 쓴다 (3단계) |
| 6 | CLI가 결과를 화면에 찍는다 (5단계) |

입력은 2단계의 `Insert`/`Select` 객체, 출력은 `QueryResult`다. 실행기는 0단계 카탈로그와 3단계 저장소를 둘 다 들고 있다. 이 셋을 아는 유일한 층이다.

## 1. 파서의 출력과 저장소 사이에 남은 일

파서는 `Select(table="students", columns=None, where=Condition("grade", ">", 2))`를 넘긴다. 저장소는 `scan()`으로 행을 내놓는다. 그 사이에 아무도 하지 않은 일이 남아 있다.

| 남은 일 | 누가 알아야 하나 |
| --- | --- |
| `students`가 있는 테이블인가 | 카탈로그 |
| `columns=None`은 실제로 어떤 컬럼들인가 | 카탈로그 |
| `grade`가 있는 컬럼인가, 행 튜플의 몇 번째인가 | 카탈로그 |
| `grade > 2`에서 `2`를 INT와 비교해도 되는가 | 카탈로그 |
| 어떤 행이 조건에 맞는가 | 행을 하나씩 보며 판단 |
| INSERT에서 id는 얼마를 줄 것인가 | 지금까지의 최대 id |
| `(name, grade)` 순서로 들어온 값을 파일 순서 `(id, name, grade)`로 바꾸기 | 카탈로그 |

파서는 카탈로그를 모르기로 했고(2단계), 저장소는 SQL을 모르기로 했다(3단계). 이 일들은 둘 다 아는 층이 해야 한다. 그것이 실행기다. 실행기가 하는 일은 결국 **해석**(None을 실제 컬럼으로), **검증**(존재하는가, 타입이 맞는가), **절차**(어떤 순서로 저장소를 부를까) 세 가지다.

## 2. INSERT의 절차

`INSERT INTO students (grade, name) VALUES (3, 'Kim');`를 예로 든다.

1. 카탈로그에서 `students`를 찾는다. 없으면 `TableNotFoundError`.
2. 컬럼 목록을 확정한다. 지정했으면 각각이 존재하는지 확인하고(`ColumnNotFoundError`), `id`가 끼어 있으면 거절한다(`ExecutionError`). 생략했으면 `user_columns`(id를 뺀 스키마 순서)로 본다.
3. 값 수가 컬럼 수와 같은지 확인한다. 컬럼을 지정한 경우는 파서가 이미 봤지만, 생략한 경우는 스키마를 알아야 하므로 여기서 본다.
4. 지정하지 않은 사용자 컬럼이 있으면 거절한다. NULL이 없으므로 모든 컬럼에 값이 있어야 한다.
5. 값마다 타입을 확인한다. INT 컬럼에 문자열, TEXT 컬럼에 숫자면 `TypeMismatchError`.
6. 다음 id를 받는다.
7. 행을 스키마 순서로 조립한다. 예시는 `(1, "Kim", 3)`이 된다. 사용자가 쓴 순서는 여기서 사라진다.
8. 저장소에 `append`한다.
9. `QueryResult(columns=("id",), rows=[(1,)])`를 돌려준다.

1~5가 전부 끝난 뒤에 6~8을 한다. 검증에 실패한 INSERT는 id를 소비하지도, 파일을 건드리지도 않는다.

## 3. SELECT의 절차

`SELECT name FROM students WHERE grade > 2;`를 예로 든다.

1. 카탈로그에서 `students`를 찾는다.
2. 출력 컬럼을 확정한다. `*`면 모든 컬럼, 아니면 각각 존재하는지 확인한다. 같은 컬럼을 두 번 적는 것은 허용한다.
3. 조건이 있으면 컬럼이 존재하는지, 비교값의 타입이 컬럼 타입과 맞는지 확인한다. `grade > 'a'`는 `TypeMismatchError`다.
4. 저장소를 `scan`하며 행마다 조건을 평가한다. 맞는 행만 남긴다.
5. 남은 행에서 출력 컬럼만 순서대로 뽑는다.
6. `QueryResult(columns=("name",), rows=[("Kim",), ...])`를 돌려준다.

4번이 **전체 스캔**(선형 탐색)이다. 조건이 `id = 1`이어도 모든 행을 읽는다. Phase 2의 9단계에서 "조건이 `id = ?`이면 scan 대신 인덱스로 오프셋을 찾아 `read_at`"으로 바뀌는 지점이 바로 여기다. 그때 바뀌는 것은 4번뿐이다.

### 비교 규칙

| 컬럼 타입 | 비교 | 예 |
| --- | --- | --- |
| INT | 정수 비교 | `grade > 2` |
| TEXT | 문자열 비교. 대소문자 구분, 코드 포인트 순서 | `name < 'L'`은 `'Kim'`에 참, `'kim'`에 거짓 |

여섯 연산자 모두 두 타입에 쓸 수 있다. 조건의 값은 파서가 숫자 또는 문자열로 넘기므로, 타입 검사는 "값이 int인데 컬럼이 TEXT인가, 또는 그 반대인가"만 보면 된다.

## 4. 결정 세 가지

### 결정 1: 다음 id는 테이블을 처음 건드릴 때 한 번 센다

id는 지금까지 부여된 최대값 + 1이다. 최대값은 파일에만 있으므로 어딘가에서 파일을 읽어야 한다. INSERT마다 `scan`하면 100만 건 삽입이 100만 × 평균 50만 행 읽기가 되어 끝나지 않는다.

대신 실행기가 테이블별로 `다음 id` 카운터를 메모리에 들고, 그 테이블을 **처음 사용할 때 한 번만** `scan`해 최대 id를 찾는다. 이후 INSERT는 카운터만 올린다. 파일이 비어 있으면 1부터다.

이 "시작할 때 한 번 훑기"는 8단계에서 B+ 트리를 재구성할 때 같은 순회를 그대로 쓴다. id와 오프셋을 함께 얻기 때문이다.

파일의 id가 연속일 필요는 없다. 사람이 파일을 편집해 id가 1, 5, 9라면 다음은 10이다.

### 결정 2: 실행 오류가 나면 거기서 멈춘다

파싱 오류는 전체를 거부하기로 했다(2단계). 실행 오류는 파싱으로 미리 알 수 없다. 두 번째 문장이 없는 테이블을 가리켜도, 첫 문장은 이미 실행된 뒤다.

선택지는 "오류 문장만 건너뛰고 계속"과 "거기서 멈춤"이다. 멈추는 쪽을 택한다. 세 번째가 실패했는데 네 번째 INSERT가 들어가면, 사용자는 파일에 어떤 문장이 반영됐는지 추적하기 어렵다. 멈추면 "앞의 n개는 반영, 그 뒤는 미반영"으로 분명하다.

이미 실행된 앞 문장은 되돌리지 않는다. 되돌리려면 트랜잭션이 필요하고, 그것은 DESIGN.md가 범위 밖으로 둔 영역이다. README에 한계로 적는다.

실행기 자체는 문장 하나를 실행할 뿐이다. "멈춤"은 문장을 차례로 넘기는 쪽(5단계 CLI)이 첫 예외에서 반복을 끝내는 것으로 구현된다.

### 결정 3: INSERT도 같은 `QueryResult`를 돌려준다

SELECT의 결과는 컬럼과 행이 자연스럽다. INSERT는 "성공" 또는 "부여된 id"가 전부라 모양이 다르다. 그래도 둘 다 `QueryResult(columns, rows)`로 통일한다. INSERT는 컬럼이 `("id",)`이고 행이 하나다.

이유는 결과를 받는 쪽이다. CLI(5단계)와 서버(13단계)가 결과 타입 하나만 다루면 되고, 사용자는 방금 넣은 행의 id를 응답에서 바로 알 수 있다. 실제 DBMS들도 `INSERT ... RETURNING id`로 같은 모양을 제공한다.

## 5. 실행기가 검사하는 것

2단계의 기준은 "카탈로그 없이 알 수 있으면 파서, 아니면 실행기"였다. 실행기 쪽 목록이다.

| 검사 | 오류 |
| --- | --- |
| 테이블이 존재하는가 | `TableNotFoundError` |
| 컬럼이 존재하는가 (SELECT 목록, INSERT 목록, WHERE) | `ColumnNotFoundError` |
| INSERT에 `id`를 지정하지 않았는가 | `ExecutionError` |
| 컬럼 생략 INSERT의 값 수가 사용자 컬럼 수와 같은가 | `ExecutionError` |
| 모든 사용자 컬럼에 값이 있는가 | `ExecutionError` |
| INSERT 값과 WHERE 값의 타입이 컬럼 타입과 맞는가 | `TypeMismatchError` |

`ExecutionError`는 이 단계에서 `errors.py`에 추가한다. "문법은 맞고 테이블과 컬럼도 있지만 이 문장은 실행할 수 없다"는 경우를 위한 것으로, 기존 종류 중 어디에도 맞지 않는다.

## 6. 코드 구조 (`minidb/executor.py`)

- `QueryResult(columns, rows)`: 불변 데이터 클래스. `rowcount` 속성을 둔다.
- `Executor(catalog, storage)`:
  - `execute(stmt) -> QueryResult`: 문장 종류를 보고 `_execute_insert` 또는 `_execute_select`로 보낸다.
  - `_next_id(table)`: 결정 1의 카운터.
  - `_resolve_insert_row(table, stmt) -> Row`: 2절의 2~5번과 7번. 검증과 조립을 한 함수에 모아, 저장소를 부르기 전에 끝나게 한다.
  - `_make_predicate(table, condition)`: 3절의 3번. 조건을 검증하고 "행을 받아 참/거짓을 돌려주는 함수"를 만든다. 4번의 반복문은 이 함수를 행마다 부른다.

실행기는 파일 경로나 포맷을 모르고, SQL 문자열도 모른다. 테스트에서는 편의상 `parse()`로 문장을 만들어 넘기지만, 실행기 자체는 `Insert`/`Select` 객체만 받는다.

- INSERT가 1부터 id를 부여하고, 컬럼 순서를 바꿔 써도 파일에는 스키마 순서로 들어간다.
- 실행기를 새로 만들어도(재시작) id가 이어진다. 파일의 id가 불연속이어도 최대값 + 1이다.
- SELECT가 `*`, 컬럼 목록, 여섯 연산자, INT와 TEXT 비교, 빈 결과를 올바르게 돌려준다.
- 5절의 검사가 각각 지정한 오류를 내고, 실패한 INSERT는 파일을 건드리지 않고 id도 소비하지 않는다.
