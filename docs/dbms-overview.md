# DBMS는 왜 필요한가: 미니 DBMS 과제를 위한 큰 그림

미니 DBMS 과제(Phase 1~3)를 구현하기 전에, DBMS가 어떤 문제를 풀기 위해 등장했고 각 Phase가 그중 무엇을 맡는지 정리한 문서입니다.

## 한눈에 보기

| 구분 | 푸는 문제 | DBMS의 답 | 과제 범위 |
| --- | --- | --- | --- |
| Phase 1 | 프로그램이 데이터의 저장 방식을 알아야만 함 | SQL 처리기 (파싱 → 실행 → 저장) | 포함 |
| Phase 2 | 데이터가 많아지면 검색이 느림 | B+ 트리 인덱스 | 포함 |
| Phase 3 | 여러 사용자가 동시에 쓰면 데이터가 깨짐 | 서버 + 스레드 풀 + 잠금 | 포함 |
| 그 너머 | 작업 도중 장애가 나면 데이터가 어중간해짐 | 트랜잭션, 로그 기반 복구 | 미포함 (일부 엣지 케이스만) |

## 1. DBMS 이전: 프로그램이 파일을 직접 다루던 시절

1960년대에는 프로그램마다 자기 데이터를 자기 파일에 직접 저장했습니다. 은행이라면 예금 프로그램과 대출 프로그램이 각자 고객 파일을 따로 갖는 식이었고, 규모가 커지면서 다음 문제들이 반복됐습니다.

- **중복과 불일치**: 같은 고객 주소가 여러 파일에 있어서, 한쪽만 고치면 어느 것이 맞는지 알 수 없습니다.
- **프로그램과 데이터의 강한 결합**: 파일 형식이 코드에 박혀 있어서, 필드 하나를 추가하면 그 파일을 읽는 모든 프로그램을 고쳐야 합니다.
- **조회의 어려움**: 새로운 질문이 생길 때마다 프로그램을 새로 짜야 합니다.
- **느린 검색**: 데이터가 많아지면 파일을 처음부터 끝까지 읽는 방식으로는 감당이 안 됩니다.
- **동시 접근**: 두 사람이 같은 값을 동시에 읽고 수정하면 한쪽 변경이 사라집니다.
- **장애**: 여러 단계로 이루어진 작업 도중 전원이 나가면 데이터가 어중간한 상태로 남습니다.

### DBMS의 핵심 아이디어

이 문제들을 프로그램마다 따로 풀지 말고, **데이터 관리를 전담하는 소프트웨어 하나가 맡게 하자**는 것이 DBMS입니다. 응용 프로그램은 파일을 직접 건드리지 않고 DBMS에 요청만 합니다.

초기 DBMS(IBM의 IMS 등)는 데이터가 저장된 경로를 프로그래머가 직접 따라가야 했습니다. 1970년 에드거 커드가 제안한 **관계형 모델**이 두 가지를 바꿨습니다.

1. **데이터 독립성**: 사용자는 데이터를 테이블이라는 논리적 모습으로만 보고, 실제 저장 방식은 DBMS가 숨깁니다.
2. **선언적 질의**: "어떻게 찾을지"가 아니라 "무엇을 원하는지"만 말합니다. 이것이 SQL입니다.

## 2. Phase 1: SQL 처리기

**문제**: 데이터를 쓰는 쪽이 데이터가 저장된 방식을 알아야만 했다.
**답**: 그 사이에 SQL 처리기라는 층을 끼워 넣는다.

### 문제의 모습

DBMS가 없을 때 "3학년 학생만 출력"하는 프로그램은 대략 이렇습니다.

```c
FILE *f = fopen("students.dat", "rb");
struct { int id; char name[20]; int grade; } s;   // 파일 구조를 코드가 알고 있음
while (fread(&s, sizeof(s), 1, f))
    if (s.grade == 3) printf("%s\n", s.name);     // 찾는 방법도 직접 작성
```

- **결합**: 파일의 바이트 배치를 프로그램이 알고 있습니다. 필드를 추가하면 이 파일을 읽는 모든 프로그램이 깨집니다.
- **질문마다 새 프로그램**: 조건이 바뀌면 코드를 고쳐 다시 컴파일해야 합니다.

### 답 1: 논리적 모습과 물리적 저장의 분리

사용자에게는 테이블(행과 열)만 보여 주고, 실제 파일이 CSV인지 바이너리인지는 숨깁니다. 이를 가능하게 하는 것이 **스키마(카탈로그)** 입니다. 테이블에 어떤 컬럼이 어떤 타입으로 있는지를 DBMS가 따로 보관하고, 그 정보를 보고 파일을 해석합니다.

> 과제에서 "테이블은 이미 존재한다고 가정"한다는 것은 `CREATE TABLE`을 구현하지 않아도 된다는 뜻입니다. 스키마 정보 자체는 처리기가 읽을 수 있는 형태로 어딘가에 있어야 합니다.

### 답 2: 질문을 프로그램이 아닌 문장으로 받는다

질문을 표현하는 언어(SQL)를 정하고, 그 언어를 해석하는 범용 프로그램 하나를 만듭니다.

```sql
SELECT name FROM students WHERE grade = 3;
```

파일 이름도, 바이트 배치도, 반복문도 없습니다.

### 처리기 내부의 세 단계

| 단계 | 하는 일 | 숨기는 것 |
| --- | --- | --- |
| 파서 | SQL 문자열을 구조화된 데이터로 변환 | SQL 문법, 공백, 대소문자, 따옴표 |
| 실행기 | 구조화된 결과를 보고 저장소에 무엇을 시킬지 결정 | 질의를 수행하는 절차 |
| 저장소 | 행을 파일에 쓰고 읽기 | 파일 형식, 바이트 배치 |

실행기는 SQL 문자열을 직접 보지 않고, 저장소는 SQL이 뭔지 모릅니다. 이 경계가 깨끗할수록 Phase 2와 3이 쉬워집니다.

### 참고: DBMS마다 SQL이 다른 이유

차이가 드러나는 곳은 파서지만, 원인은 세 종류입니다.

- **문법만 다른 경우**: 같은 일을 시키는데 표기가 다릅니다. 앞의 10건만 가져올 때 MySQL과 PostgreSQL은 `LIMIT 10`, SQL Server는 `TOP 10`, 표준과 Oracle은 `FETCH FIRST 10 ROWS ONLY`를 씁니다. 표준(1986년)보다 제품이 먼저 나온 결과입니다.
- **기능이 달라서 문법도 다른 경우**: ID 자동 부여가 MySQL은 `AUTO_INCREMENT`, PostgreSQL은 `SERIAL`이나 `IDENTITY`입니다. 내부 엔진의 차이가 문법으로 드러난 것입니다.
- **문법은 같은데 결과가 다른 경우**: Oracle은 빈 문자열을 NULL로 취급합니다. 문자열 비교의 대소문자 구분 여부도 제품마다 다릅니다. 이것은 실행기의 차이입니다.

과제에서도 "나만의 방언"을 정하게 됩니다(따옴표 종류, 키워드 대소문자, 세미콜론 필수 여부, 문자열 비교 규칙). README에 명시해 두면 테스트 기준이 됩니다.

### 설계 시 고민할 점

1. **저장 포맷**: CSV는 디버깅이 쉽지만 값 안의 쉼표와 줄바꿈을 처리해야 합니다. 고정 길이 바이너리는 N번째 행의 위치를 바로 계산할 수 있지만 문자열 길이에 제한이 생깁니다.
2. **행의 위치 반환**: INSERT할 때 그 행의 파일 내 위치(오프셋)를 돌려받을 수 있게 해 두면 Phase 2의 인덱스와 바로 연결됩니다.
3. **저장소 인터페이스**: "행 추가", "전체 순회", "특정 위치의 행 읽기" 정도로만 실행기와 대화하게 합니다.
4. **결과는 반환, 출력은 분리**: 실행 결과를 화면에 바로 찍지 말고 데이터로 반환합니다. 오류도 프로그램을 종료시키지 말고 반환합니다. Phase 3에서 서버가 그대로 가져다 쓸 수 있습니다.

## 3. Phase 2: B+ 트리 인덱스

**문제**: 데이터가 많아지면 찾는 데 너무 오래 걸린다.

**답**: 데이터와 별도로, 찾기 전용 자료구조(인덱스)를 유지한다.

### 문제의 모습

Phase 1의 SELECT는 파일을 처음부터 끝까지 읽습니다(선형 탐색). 100만 건 중 한 건을 찾는 데도 100만 건을 읽고, 데이터가 10배면 시간도 10배입니다. 책 뒤의 "찾아보기"처럼 **키 → 위치**를 따로 정리해 둔 것이 인덱스입니다.

### 왜 B+ 트리인가

| 후보 | 아쉬운 점 |
| --- | --- |
| 정렬된 배열 + 이진 탐색 | 중간에 삽입하면 뒤를 전부 밀어야 함 |
| 해시 테이블 | 범위 검색과 정렬 불가 |
| 이진 탐색 트리 | 100만 건이면 높이 약 20. 노드 하나가 디스크 읽기 한 번이면 20번 읽음 |
| **B+ 트리** | 구현이 복잡함 |

B+ 트리는 **한 노드에 키를 많이 담아 트리를 납작하게** 만듭니다. 노드당 키가 100개면 3단계로 100³ = 100만 건을 구분합니다. 실제 DBMS는 노드 하나를 디스크 페이지 하나에 맞춥니다. 과제는 메모리 기반이지만 구조는 같습니다.

### 구조

```
                 [ 30 | 60 ]                 ← 내부 노드: 길 안내용 키만
               /      |      \
   [10|20] → [30|40|50] → [60|70|80]         ← 리프 노드: 키 + 행의 위치
     ↓ ↓       ↓  ↓  ↓       ↓  ↓  ↓            리프끼리 옆으로 연결
   파일의 각 행 위치(오프셋)
```

- **내부 노드**는 방향만 알려 줍니다.
- **리프 노드**에만 실제 값(행의 파일 위치)이 있습니다.
- **리프끼리 연결**되어 범위 검색은 시작점만 찾고 옆으로 따라갑니다.

삽입 시 노드가 꽉 차면 **둘로 쪼개고 가운데 키를 부모로 올립니다**. 루트가 쪼개지면 높이가 1 늘어납니다. 트리가 위로 자라기 때문에 모든 리프의 깊이가 항상 같고, 어떤 키든 검색 시간이 일정합니다.

### Phase 1과의 연결

- **INSERT**: 저장소가 행을 쓰고 위치를 돌려주면, 실행기가 `(id, 위치)`를 B+ 트리에 등록합니다.
- **SELECT**: 실행기가 조건을 보고 경로를 고릅니다. `WHERE id = ?`면 인덱스로 한 행만 읽고, 그 외에는 전체 스캔합니다.

SQL 문장은 그대로인데 실행 방식만 달라집니다. 이 경로 선택이 쿼리 옵티마이저의 가장 단순한 형태입니다.

### 설계 시 고민할 점

1. **재시작 시 인덱스 복구**: 인덱스는 메모리에만 있으므로, 시작할 때 파일을 훑어 다시 만들고 다음 ID도 이때 정합니다.
2. **100만 건 삽입 속도**: INSERT마다 파일을 열고 닫으면 매우 느립니다. 쓰기 버퍼링과 데이터 생성 스크립트가 필요합니다.
3. **공정한 성능 비교**: 둘 다 결과가 1건인 질의로, 여러 번 반복해 평균을 냅니다. 찾는 행의 위치(앞, 중간, 뒤)에 따른 선형 탐색 시간 차이도 함께 보여 줍니다.
4. **인덱스의 비용**: 삽입이 느려지고 메모리를 씁니다. 인덱스 유무에 따른 삽입 시간도 측정해 둡니다.
5. **테스트 편향**: 자동 증가 ID는 항상 가장 오른쪽 리프에만 삽입됩니다. B+ 트리 단위 테스트에서는 무작위 순서 삽입도 확인합니다.

## 4. Phase 3: API 서버와 동시성

**문제**: 여러 사용자가 동시에 같은 데이터를 쓰면 깨진다.

**답**: 데이터를 한 프로세스(서버)가 독점하고, 그 안에서 동시 접근을 통제한다.

### 문제 1: CLI 방식은 혼자 쓸 때만 안전하다

CLI 처리기는 실행할 때마다 프로세스가 뜨고 각자 인덱스를 만듭니다. 두 사람이 동시에 실행하면 서로의 INSERT를 모르고, 같은 ID를 부여하고, 파일 쓰기가 뒤섞입니다.

그래서 DBMS는 **서버**로 동작합니다. 엔진을 가진 프로세스는 하나만 떠 있고, 클라이언트는 네트워크로 요청만 보냅니다.

### 문제 2: 요청을 어떻게 동시에 처리할 것인가

| 방식 | 문제점 |
| --- | --- |
| 한 번에 하나씩 | 오래 걸리는 요청 하나가 뒤의 모든 요청을 막음 |
| 요청마다 스레드 생성 | 생성 비용이 들고, 폭주하면 스레드가 무한정 늘어남 |
| **스레드 풀** | 미리 만든 N개의 스레드가 대기열에서 작업을 꺼내 처리. 자원 사용량에 상한이 있음 |

```
클라이언트들 ──요청──▶ [ 접수 스레드 ] ──▶ [ 작업 대기열 ] ──▶ [ 워커 1..N ] ──▶ DB 엔진
                                                                    │        (Phase 1+2)
            ◀──────────────── 응답 ─────────────────────────────────┘
```

### 문제 3: 스레드들이 엔진 내부를 동시에 건드린다

- **ID 중복**: 두 INSERT가 동시에 카운터를 읽으면 같은 ID를 받습니다.
- **트리 손상**: 두 스레드가 같은 리프를 동시에 분할하면 포인터가 꼬입니다.
- **읽는 중 변경**: SELECT가 트리를 내려가는 도중 INSERT가 그 노드를 쪼개면 엉뚱한 곳을 읽습니다.

이런 버그는 가끔만 터져서 테스트로 잡기 어렵습니다.

### 답: 잠금

1. **전역 뮤텍스**: 한 번에 한 스레드만 엔진에 들어갑니다. 안전하지만 사실상 직렬 처리입니다.
2. **읽기-쓰기 잠금**: SELECT끼리는 동시에, INSERT는 혼자 실행합니다.
3. **더 세밀한 잠금**: 테이블별, 노드별 잠금, 그리고 실제 DBMS의 MVCC(읽기가 쓰기를 기다리지 않는 방식)로 이어집니다.

과제에서는 **테이블 단위 읽기-쓰기 잠금**이 난이도와 병렬성의 균형점입니다. INSERT의 세 동작(ID 부여, 파일 쓰기, 인덱스 등록)은 반드시 **하나의 잠금 구간 안에** 있어야 합니다.

### 설계 시 고민할 점

1. **엔진과 서버의 접점**: "SQL 문자열을 받아 결과를 돌려주는 함수 하나"로 둡니다.
2. **API 형태**: 가장 단순한 것은 SQL을 본문에 담아 보내고 JSON으로 받는 엔드포인트 하나입니다. 성공, 문법 오류, 없는 테이블 등의 구분 방법을 정합니다.
3. **대기열이 가득 찼을 때**: 거절 응답을 보내는 쪽이 서버를 보호합니다.
4. **동시성 테스트**: 여러 클라이언트가 동시에 INSERT한 뒤 전체 건수와 ID 중복 여부를 확인합니다. 잠금을 빼면 실패하는 것까지 보이면 더 좋습니다.
5. **안전한 종료**: 처리 중인 요청을 마치고 파일을 온전히 닫습니다.

## 5. 과제 너머: 트랜잭션과 장애 복구

### 동시성과는 다른 문제

| | 동시성 | 장애 복구 |
| --- | --- | --- |
| 원인 | 여러 작업이 같은 시간에 실행됨 | 작업이 도중에 끊김 |
| 사용자가 한 명뿐이어도 생기나 | 아니요 | 예 |
| 잠금으로 해결되나 | 예 | 아니요 |
| 대표적 해법 | 잠금, MVCC | 로그 선행 기록(WAL) |

계좌 이체("A에서 10만 원 빼기" + "B에 10만 원 넣기")로 보면:

- **장애 문제**: 혼자 쓰는데 첫 문장 직후 전원이 나가면 10만 원이 사라집니다. 잠금은 도움이 안 됩니다.
- **동시성 문제**: 장애는 없는데, 두 문장 사이에 다른 사용자가 합계를 조회하면 10만 원이 빈 값을 봅니다.

### 트랜잭션이 둘을 묶는다

트랜잭션은 "여러 문장을 하나의 작업으로 취급하겠다"는 선언입니다. 이 단위에 대해 DBMS가 보장하는 성질이 ACID입니다.

| 성질 | 의미 | 담당 |
| --- | --- | --- |
| 원자성 (Atomicity) | 전부 반영되거나 전부 취소 | 장애 복구 |
| 일관성 (Consistency) | 데이터가 규칙에 맞는 상태를 유지 | 나머지 셋의 결과 |
| 격리성 (Isolation) | 진행 중인 중간 상태를 남이 보지 못함 | 동시성 제어 |
| 지속성 (Durability) | 완료된 것은 장애 후에도 남음 | 장애 복구 |

### 복구의 기본 원리: 로그 선행 기록 (WAL)

데이터를 고치기 전에 "무엇을 고칠 것인지"를 로그 파일에 먼저 기록합니다. 재시작할 때 로그를 읽어, 완료된 트랜잭션은 다시 반영하고 미완료 트랜잭션은 되돌립니다.

### 과제와의 관계

Phase 3의 잠금은 **문장 하나**를 보호할 뿐, 여러 문장을 묶는 개념은 없습니다. 여러 문장에 걸쳐 잠금을 유지하면 교착 상태 같은 새 문제가 생기므로 과제 범위 밖입니다.

그래도 장애 문제의 작은 버전은 과제 안에서 만납니다.

- **반쯤 쓰인 행**: INSERT 도중 프로그램이 죽으면 파일 끝에 잘린 행이 남을 수 있습니다. 재시작 시 마지막 행이 온전한지 확인하고, 깨졌으면 버립니다.
- **"저장됐다"의 기준**: 파일에 썼어도 운영체제 버퍼에만 있다가 전원이 나가면 사라집니다. 매번 디스크까지 강제로 내려쓰면 안전하지만 느립니다. 삽입 속도와 맞바꾸는 선택입니다.

이 두 가지를 처리하고, README에 "트랜잭션과 WAL은 미구현"이라고 한계를 밝혀 두는 것이 과제 범위에서 적절한 선입니다.

## 6. 전체 흐름 요약

| 단계 | 해결한 문제 | 남는 한계 |
| --- | --- | --- |
| Phase 1 | 저장 방식과 프로그램의 결합 | 느림 |
| Phase 2 | 검색 속도 | 한 사람만 쓸 수 있음 |
| Phase 3 | 동시 사용 | 장애 시 복구, 여러 문장을 묶는 트랜잭션 없음 |
| 그 너머 | 트랜잭션, WAL | 실제 DBMS의 영역 |

각 Phase는 앞 단계의 한계를 하나씩 풀어 갑니다. 그리고 Phase 1에서 파서, 실행기, 저장소의 경계를 깨끗하게 나눠 두는 것이 뒤 단계 전체를 쉽게 만드는 가장 중요한 결정입니다.
